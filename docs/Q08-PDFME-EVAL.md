# Q-08 평가: pdfme 기반 채택 가능성 (2026-08-18)

> OPEN-QUESTIONS Q-08의 판단 자료. 프로토타입 코드: `prototypes/pdfme-eval/`
> 대상: pdfme v6.1.12 (`@pdfme/generator`, `@pdfme/common`, `@pdfme/schemas`), Node 22

## 실험 내용

A4 빈 용지 기준(`basePdf: {width:210, height:297, padding}`) 템플릿에
한글 제목 + 플레이스홀더 텍스트 + 40행 동적 테이블을 넣고 Noto Sans KR(10.4MB 가변 TTF)로 생성.
템플릿 루트에는 pdfme 스펙에 없는 우리 고유 필드(`voucherMeta`: 스키마버전·스냅샷·서명 자리)를 추가.

## 결과: 검증 항목 전부 통과

| 검증 항목 | 관련 ADR | 결과 |
|---|---|---|
| 자동 페이지 분할 (40행 → 2페이지) | ADR-011 | ✅ 30행/10행으로 정확히 분할 |
| 페이지 분할 시 헤더 반복 (`repeatHead`) | ADR-011 | ✅ 2페이지에 헤더 재출력 |
| 한글 렌더링 (제목·표 본문) | ADR-012 | ✅ 완벽 |
| 한글 폰트 서브세팅 | ADR-012 | ✅ 10.4MB 폰트 → PDF 20KB (자동 서브세팅) |
| 템플릿 루트 확장 필드 수용 | ADR-007/008/009 | ✅ `checkTemplate`·`generate` 모두 통과 (Zod passthrough) |
| 플레이스홀더 치환 `{issuerName}` | ADR-006 | ✅ 입력 변수로 치환 |
| **표현식 평가** `{1 + 2 * 3}` → `7` | ADR-010 | ✅ 산술·메서드 호출 평가됨 |
| 표현식 샌드박스 (`{process}` 접근) | ADR-010 | ✅ 차단됨 (치환 안 되고 원문 유지) |
| 생성 속도 (2페이지, 40행, CJK 폰트) | — | ✅ ~260ms (Node) |
| 브라우저/Node 동일 코드 | ADR-012 | ✅ 순수 JS — Node에서 그대로 동작 확인 |

주의점 (평가에서 발견):

- 테이블 스키마는 스타일 속성(`lineHeight`, `verticalAlignment`, `padding` 등)이 **모두 채워져 있어야** 정상 동작. 일부만 넣으면 조용히 레이아웃이 깨지거나(행 겹침) 크래시. → 우리가 감싼다면 **기본값 병합 계층 필수**
- 자동 페이지 분할은 `basePdf`가 빈 용지 정의(`{width,height,padding}`)일 때만 동작 (기존 PDF 위에 얹는 모드에서는 불가) — 우리 용도(빈 용지에서 시작)에는 문제 없음

## 우리 요구와의 갭 (pdfme가 안 주는 것)

| 우리 요구 | pdfme 현황 | 우리가 만들 것 |
|---|---|---|
| 위변조 서명·암호화 (ADR-009) | 없음 | 서명/검증 계층 (JWS) |
| 양식 스냅샷 내장 (ADR-008) | 개념 없음 (템플릿=파일) | 전표 파일 포맷(템플릿 스냅샷 + 데이터 + 서명)을 pdfme 템플릿의 **상위 개념**으로 정의 |
| 엑셀 스타일 수식 `SUM(items.amount)` (ADR-010) | JS 표현식 스타일 `{a + b}` (샌드박스) | 엑셀 문법 → 표현식 변환 또는 자체 평가기. pdfme 표현식을 하부 실행기로 재활용 가능성 있음 |
| Web Component 배포 (ADR-003) | 디자이너/뷰어가 React 기반 (`@pdfme/ui`) | Lit 기반 자체 UI (ADR-015). 단, 생성 엔진은 UI와 무관하게 사용 가능 |
| 저장소 어댑터 (ADR-006) | 없음 (파일 다루기는 호스트 몫) | 어댑터 계층 |
| 권한 인터페이스 (ADR-004) | 없음 | mode/permissions 속성 |
| 발행 시 이미지 내장 (ADR-014) | image 스키마는 base64 지원 | 발행 파이프라인(URL→base64 변환) |
| i18n/한국어 UI (ADR-013) | 디자이너 UI는 영어 중심 | 자체 UI라 무관 |

## 결론 및 권고

**권고: "엔진 채택, 껍데기 자체 개발" (Q-08 선택지 3에 가까운 절충)**

- `@pdfme/generator`+`@pdfme/schemas`+`@pdfme/common`을 **core의 PDF 생성·레이아웃 하부 엔진으로 채택** — 자동 페이지 분할·CJK·서브세팅·표현식 샌드박스라는 최고 난도 구간이 검증된 상태로 확보됨 (MIT 라이선스)
- 우리 파일 포맷(전표 = 템플릿 스냅샷 + 데이터 + 서명 + 메타)은 pdfme 템플릿을 **내부에 포함하는 상위 포맷**으로 정의 — pdfme에 종속되는 것은 "렌더링 표현"이며, 우리 포맷의 진실의 원천은 우리 스키마
- UI(디자이너/뷰어/작성폼)는 ADR-003/015대로 Lit 기반 Web Component로 자체 개발. pdfme의 React UI는 쓰지 않되 설계 참고자료로 활용
- 리스크 관리: pdfme 의존을 core 내부의 렌더러 인터페이스 뒤에 두어 외부에 공개하지 않으며, 최악의 경우(프로젝트 중단 등) 자체 렌더러로 교체 가능한 구조를 유지

이 권고가 채택되면 ADR-016으로 기록하고, "레이아웃 엔진을 밑바닥부터 자체 개발"을 전제로 한
ADR-012의 해당 부분(렌더 트리 직접 구현)을 조정한다 (파이프라인 원칙 자체는 유지 — 실행자가 pdfme로 바뀌는 것).
