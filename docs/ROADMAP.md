# 로드맵

SlipKit의 현재 개발 단계와 앞으로 진행할 작업을 정리합니다.

완료된 설계의 배경은 [설계 결정 기록](./DECISIONS.md), 현재 기능 요구사항은 [요구사항](./REQUIREMENTS.md), 파일 형식은 [파일 형식 명세](./SPEC.md)를 참고합니다.

최종 갱신: 2026-09-02

## 현재 단계

SlipKit은 핵심 기능 구현을 마치고 첫 공개 전 품질 검토를 진행하고 있습니다.

> [!IMPORTANT]
> `@omdc-slipkit/*` 패키지는 아직 npm 레지스트리에 배포되지 않았습니다.
>
> 현재 파일 스키마는 공개 전 개발 버전인 `0.1.0`입니다. 공개 이후의 호환성 정책과 패키지 버전은 별도로 확정합니다.

| 영역 | 상태 | 현재 작업 |

| 핵심 기능 | 완료 | 공개 전 회귀 검증 |
| 사용자 인수 검토 | 완료 | 메시지 로케일화까지 반영 |
| 주요 문서 정리 | 완료 | 비가이드 문서 재검토 완료 |

## 완료된 기반 기능

다음 기능은 구현을 완료했으며, 이후 작업에서는 기능 추가보다 정확성과 사용성을 우선해 검토합니다.

### 패키지와 공개 API

- DOM에 의존하지 않는 `@omdc-slipkit/core`
- Lit 기반 `@omdc-slipkit/elements`
- React와 Vue용 얇은 래퍼
- Core 공통 설정 진입점 `createSlipKit`
- 독립적으로 사용할 수 있는 파싱, 검증, 수식과 전표 조립 API

### 양식과 전표

- JSON 기반 `.slip` 파일 형식
- 양식과 전표 구분
- 전표에 양식 스냅샷 내장
- 파라미터와 목록 하위 필드 정의
- 다중 페이지 양식
- 전표 작성과 발행 후 입력 잠금
- `buildVoucher`를 이용한 전표 조립

### 디자이너

- 텍스트, 이미지, 선, 도형, 필드, 그리드와 바코드 요소
- 요소와 파라미터를 분리한 편집 구조
- 다중 페이지 편집
- 실행 취소와 다시 실행
- 복사와 붙여넣기
- 스냅과 정렬 보조
- 양식 미리보기
- 행 번호 선택으로 행 구간 역할 지정, 페이지 방식 선택과 출력 페이지 미리보기
- 셀 이름 편집과 셀·그리드 편집 분리
- 셀 기본 테두리, 셀별 테두리와 그리드 테두리의 독립 설정
- 자동 병합
- 파라미터 또는 수식을 사용하는 값 소스
- 필드·바코드·그리드 셀·조건부 서식 규칙에서 여는 수식 편집 모달
- 텍스트·필드 요소, 그리드 공통과 그리드 셀의 폰트 선택
- 캔버스와 인라인 셀 편집에 고른 폰트를 그대로 적용

### 수식과 렌더링

- 임의 코드 실행을 사용하지 않는 자체 수식 파서
- 편집 대상을 확정해 열고 모달이 열려 있는 동안 대상을 계속 확인하는 수식 편집
- 캔버스·인라인 검사·수식 모달이 함께 쓰는 계산 문맥과 검사
- 인자·반환값 설명을 갖춘 함수 도움말과 이름·설명 검색
- 엄격한 값 타입과 명시적 형 변환
- 예약 참조 `@item`·`@group`·`@page`·`@all`·`@carried` (그룹·페이지 소계와 누계)
- 브라우저 PDF 생성
- 밀리미터 기반 용지 좌표계
- pdfme에 의존하지 않는 페이지 계획 계층 — 화면과 PDF가 같은 계획을 사용
- PDF에 사용할 폰트의 호스트 공급
- 등록된 변형 폰트로만 표현하는 굵게·기울임 — 캔버스와 PDF가 같은 폰트를 선택
- 등록되지 않은 `fontName`은 값을 지우지 않고 대체 폰트로 렌더링

### 저장과 파일 보호

- IndexedDB 저장소
- 파일 내려받기와 열기 (파일 교환)
- AES-256-GCM 파일 암호화
- 저장 시 암호화 선택과 암호화 봉투 자동 감지
- 현재 키와 이전 키를 이용한 키 교체

### 언어와 문서

- 한국어, 영어와 일본어 UI (기본 영어)
- 로케일에 따른 오류 메시지 언어 전환 (기본 영어)
- 설정된 로케일에 맞게 생성되는 동봉 프리셋
- 영어(기준), 한국어와 일본어 사용자 가이드 — 접미사가 없는 `*.md`가 영어판
- 기본 한국어·일본어 렌더링 폰트
- 파일 형식 명세와 JSON Schema

### MCP·AI 연동 (ADR-061)

- 도구 7종을 제공하는 로컬 stdio MCP 서버 `@omdc-slipkit/mcp`
- 작업 디렉터리 안으로 제한한 파일 접근과 `FileSystemStorage` 어댑터
- `slipkit-mcp.json` 설정 파일 (작업 디렉터리, 로케일, 커스텀 폰트, 암호화 키 환경변수 이름, PDF 링크 포트)
- 요약 기본 읽기와 base64 데이터 제외, 요소 id를 지목하는 부분 수정
- 연결 방법과 안전 범위는 [MCP 사용 가이드](guide/mcp.ko.md)와 영어·일본어판 참고

### 조건부 서식 (ADR-062·063)

- 텍스트 요소, 필드 요소와 그리드 셀의 `conditionalFormats` 규칙
- 조건이 참인 규칙을 선언 순서대로 합성하는 색·글자 강조 재정의 (글자색·배경색·테두리색·굵게·기울임·밑줄·취소선)
- 반복 그리드의 행별 평가와 디자이너 캔버스의 샘플 값 미리보기
- 디자이너, 작성 폼, 뷰어와 PDF가 같은 core 평가 결과를 사용

### 그리드 행 구간과 페이지 방식 (ADR-065)

- 행 구간(`bands`) 7종 역할 — 데이터 앞·뒤, 페이지별 위·아래, 그룹 시작·종료, 항목
- 자동 확장(`minItems`)과 고정 페이지(`itemsPerPage`)의 페이지 방식
- `groupBy` 그룹과 이월 시 그룹 시작 다시 표시
- 페이지 흐름 영역(`flowArea`)과 요소 출력 페이지 배치(`pagePlacement`)
- 그리드 크기를 저장하지 않고 열·행 트랙 합에서 계산
- 셀 편집용 이름(`name`)

## 우선 작업: 소스 코드 검토

데모 검토 이후 패키지별 소스 코드를 다시 확인합니다.

새 기능을 늘리기보다 이해하기 어려운 구조, 예외 입력과 실제 사용 중 발생할 수 있는 문제를 찾는 데 집중합니다.

### `core`

- 공개 API의 역할과 이름
- 스키마 검증과 의미 검증의 경계
- 손상되거나 외부에서 생성된 `.slip` 처리
- 수식 파서와 평가기의 경계 조건
- 그리드 확장과 페이지 분할
- 암호화 봉투 검증과 오류 구분
- 순수 함수와 `createSlipKit` 인스턴스의 역할 중복
- 불필요한 변환과 깊은 복사

### `elements`

디자이너의 상태와 선택 대상 관리는 `packages/elements/src/designer/`로 나누어 정리했습니다.

- `designer/*.ts` — 화면 상태에 의존하지 않는 계산 (좌표·크기·스냅, 색 변환, 스타일 CSS 변환,
  그리드 구조 변경, 파라미터 요약, 이미지 수집, 수식 계산 문맥·검사·편집 대상)
- `designer/controllers/*.ts` — 상태를 가진 부분 (모달, 수식·샘플 초안, 저장·목록,
  그리드 선택과 조작, 캔버스 포인터, 팝오버, 색 선택기, 모달 초점)
- `designer/render/*.ts` — 화면 조각 (툴바, 사이드바, 캔버스, 속성 패널, 모달, 수식 모달)
- `slip-designer.ts` — 외부 프로퍼티, 최상위 상태 조정과 전체 배치

각 모듈은 컴포넌트 전체가 아니라 목적별 인터페이스만 받고, 의존 방향은
상태 비의존 연산 → 컨트롤러 → 렌더 모듈 → 컴포넌트 한 방향입니다.

남은 검토 항목입니다.

- 실행 취소와 다시 실행의 일관성
- 빠른 연속 조작과 비동기 작업의 경합
- 저장과 불러오기 실패 처리
- 좁은 화면, 확대와 키보드 조작
- 로케일별 문구 길이와 레이아웃
- 이미지와 대용량 데이터 처리

### React와 Vue 래퍼

- Web Component 속성 전달
- 이벤트 등록과 해제
- 객체와 함수 속성의 갱신
- 컴포넌트 생명주기
- 프레임워크별 타입 정의
- 래퍼가 불필요한 상태를 별도로 갖는지 여부

### 렌더링

- 화면과 PDF의 위치·크기 차이
- 글꼴에 따른 줄바꿈 차이
- 긴 글, 이모지, 개행과 빈 값
- 음수, 소수와 매우 큰 숫자
- 페이지 경계의 반복 그리드
- 이미지와 바코드 렌더링 실패
- 미리보기와 최종 PDF의 동작 차이

## 이후 작업: 기본설계 문서 작성

소스 코드 검토가 끝나면 현재 구현과 기존 요구사항·명세·설계 결정을 근거로 기본설계 문서를 작성합니다.

문서의 목적은 소스 코드 작성 방법을 설명하는 것이 아니라, 각 화면과 기능의 입력·처리·분기·출력 및 서로의 관계를 문서만으로 파악할 수 있게 하는 것입니다.

### 문서 구성

하나의 파일에 모든 내용을 모으지 않고 역할과 설계 대상별로 분리합니다.

- 공통 설계: 시스템 개요, 패키지 책임, 용어와 공통 처리
- 화면 설계: 디자이너, 작성폼, 뷰어 및 독립적인 모달·화면 상태
- 기능 설계: 파싱, 검증, 마이그레이션, 수식 평가, 전표 발행, PDF 렌더링, 저장과 암호화
- 데이터 설계: `.slip` 봉투, 양식, 전표, 파라미터와 요소 구조
- 인터페이스 설계: core 공개 API, 저장소 어댑터, Web Component 이벤트와 프레임워크 래퍼
- 오류 설계: 오류 분류, 발생 조건, 표시 방식과 복구 흐름
- 문서 관리: 설계 문서 색인과 요구사항·화면·기능·데이터 간 추적표

화면과 기능은 `SCR-001`, `FNC-001`과 같은 식별자를 부여하고 각각 별도 파일로 작성합니다. 버튼이나 소스 함수마다 나누지 않고 독립적인 목적과 처리 흐름을 가진 단위를 기준으로 분리합니다.

### 개별 설계서 내용

화면 설계서에는 화면 목적, 진입·종료 조건, 구성, 입력·출력 항목, 이벤트, 상태별 표시, 검증, 오류 처리, 화면 전이와 호출 기능을 기록합니다.

기능 설계서에는 기능 목적, 호출 조건, 입력·출력, 사전 조건, 정상·분기·오류 처리 흐름, 데이터 변경, 하위 기능과 관련 화면·데이터·인터페이스를 기록합니다. 처리 흐름은 설명문보다 흐름도, 시퀀스 다이어그램, 상태 전이도와 표를 우선합니다.

### 예상 범위

- 공통 설계 5~8개
- 화면 설계 15~25개
- 기능 설계 20~35개
- 데이터·인터페이스·오류 설계 10~15개
- 문서 색인과 추적표 3~5개

전체 예상 범위는 약 50~80개 파일입니다. 실제 파일 수는 설계 대상 목록을 먼저 작성한 뒤 조정합니다.

### 완료 조건

- 주요 사용자 흐름과 내부 처리 흐름을 소스 코드를 읽지 않고 파악할 수 있습니다.
- 각 화면에서 호출하는 기능과 사용하는 데이터·인터페이스를 추적할 수 있습니다.
- 정상 처리뿐 아니라 주요 분기와 오류 처리도 확인할 수 있습니다.
- 기존 `REQUIREMENTS.md`, `SPEC.md`, `DECISIONS.md` 및 실제 구현과 모순되지 않습니다.
- 문서 색인에서 전체 설계 범위와 작성 상태를 확인할 수 있습니다.

## 공개 준비

문서, 데모와 소스 코드 검토가 끝나면 첫 공개 여부를 판단합니다.

### 공개 전 확인

- [ ] 영어 문서의 내용 확정
- [ ] 한국어판과 일본어판 동기화
- [ ] 문서 내부 링크 확인
- [ ] 가이드 예제와 실제 공개 API 대조
- [ ] 데모 애플리케이션 빌드와 실행 확인
- [ ] JSON Schema와 런타임 스키마 일치 확인
- [ ] 패키지 공개 파일 목록 확인
- [ ] 라이선스와 동봉 폰트 라이선스 확인
- [ ] 변경 사항과 알려진 제한 정리
- [ ] 치명적이거나 높은 우선순위의 미결 문제 해소
- [ ] 전체 검증 명령 통과

전체 검증은 다음 명령을 기준으로 합니다. 실행 순서는 루트 `package.json`의 `verify` 스크립트에 있습니다.

```bash
pnpm verify
```

> [!NOTE]
> 검증 명령 통과만으로 공개 준비가 끝나는 것은 아닙니다. 데모 실행과 주요 사용자 흐름은 실제 브라우저에서도 확인해야 합니다.

## 보류 항목

현재 공개 범위에는 포함하지 않지만, 필요성이 확인되면 다시 검토합니다.

### 페이지별 소계와 이월

반복 그리드가 여러 페이지로 나뉠 때 페이지별 소계와 다음 페이지 이월 금액을 표시하는 기능입니다.

페이지 분할과 수식 평가 순서에 영향을 주며 현재 양식은 반복 없는 그리드 등으로 우회할 수 있어 보류합니다.

### 동봉 프리셋 확충

기본 제공 양식 종류를 늘리는 작업입니다.

호스트가 자체 프리셋을 공급할 수 있으므로 라이브러리에 많은 업무별 양식을 포함하는 작업은 우선하지 않습니다.

### 캔버스와 PDF의 줄바꿈 측정 차이

캔버스는 CSS로, PDF는 fontkit 측정으로 줄을 나눕니다. 같은 폰트를 써도 같은 너비에서 줄바꿈 위치가 달라질 수 있습니다.

폰트와 변형 선택의 불일치는 ADR-069로 해소했습니다. 남은 것은 측정 방식의 차이이며, 캔버스에서 fontkit 측정 결과를 쓰려면 계산 비용과 편집 반응 속도를 함께 따져야 합니다.

### 배경 그라디언트

화면과 PDF에서 같은 결과를 만들 수 있는지 먼저 검증해야 합니다. PDF 변환 계층이 지원하지 않는다면 화면에만 추가하지 않습니다.

## 유지보수 백로그

다음 항목은 공개를 반드시 막는 작업은 아니지만 지속적으로 검토합니다.

- 뷰어와 디자이너의 PDF 미리보기 로직 공통화
- 실행 취소 스냅샷의 전체 바이트 상한
- 패키지 사이 테스트 헬퍼 공통화
- 로컬 파일 선택 취소 감지 개선
- 중복된 편집 모달 진입점 확인
- 대용량 양식과 이미지의 성능 측정
- 키보드 조작과 접근성 개선
- 오류 메시지와 복구 방법 정리

백로그 항목이 실제 사용자 문제나 공개 차단 문제로 확인되면 현재 작업으로 올리고 구체적인 완료 조건을 추가합니다.

## 향후 검토: MCP·AI 연동 확장

MCP 서버의 1차 범위는 ADR-061에서 확정해 구현을 완료했습니다. 다음 사항은 1차 범위에 포함하지 않으며 필요성이 확인되면 다시 검토합니다.

- 기존 양식 변경 이력과 되돌리기
- 민감한 전표 데이터의 전달 범위
- 호스트 애플리케이션과 AI 서비스의 책임 경계

## 로드맵 관리 원칙

- 현재 진행 중인 작업과 다음 작업이 위쪽에서 바로 보이게 유지합니다.
- 완료 작업의 상세 구현 이력은 Git 기록과 ADR에 남깁니다.
- 새로운 설계 쟁점은 결정하기 전에 `OPEN-QUESTIONS.md`에 기록합니다.
- 결정이 확정되면 `DECISIONS.md`와 관련 요구사항을 함께 갱신합니다.
- 기능을 추가할 때는 실제 사용 사례와 완료 조건을 먼저 정의합니다.
- 작업 순서나 범위가 바뀌면 상태와 다음 작업을 갱신합니다.
