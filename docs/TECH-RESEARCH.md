# 기술 조사 기록

SlipKit의 주요 기술을 선택할 때 확인한 외부 기술의 특성, 프로젝트에서의 적용 범위와 재검토 조건을 기록합니다.

확정된 설계와 변경 이력은 [설계 결정 기록](./DECISIONS.md), 현재 구조는 [아키텍처](./ARCHITECTURE.md), 예정 작업은 [로드맵](./ROADMAP.md)을 참고합니다.

최종 갱신: 2026-08-26

## 문서 원칙

이 문서는 기술 유행이나 라이브러리 순위를 정리하는 문서가 아닙니다.

다음 내용을 중심으로 유지합니다.

- SlipKit에서 실제로 검토하거나 사용하는 기술
- 기술 선택에 영향을 준 공식 기능과 제약
- SlipKit이 해당 기술에 의존하는 범위
- 다른 기술을 선택하지 않은 이유
- 현재 선택을 다시 검토해야 하는 조건

GitHub 스타 수, 주간 다운로드 수와 같은 변동 지표는 선택 근거로 사용하지 않습니다.

> [!IMPORTANT]
> 이 문서는 조사 결과를 기록하지만 새로운 설계를 확정하지는 않습니다.
>
> 조사 결과로 설계를 바꿔야 한다면 먼저 [미결 사항](./OPEN-QUESTIONS.md)에서 쟁점을 정리하고, 결정된 뒤 `DECISIONS.md`에 ADR로 기록합니다.

## 확인 기준

외부 기술에 관한 설명은 가능한 한 다음 순서로 확인합니다.

1. 공식 문서와 명세
2. 공식 저장소와 릴리스 기록
3. 프로젝트에 설치된 패키지와 잠금 파일
4. SlipKit의 테스트와 직접 검증 결과
5. 필요한 경우에만 보조 자료

라이브러리 버전과 기능은 시간이 지나면 달라질 수 있으므로 의존성을 올릴 때 관련 내용을 다시 확인합니다.

## 1. PDF 생성 엔진

### 요구 조건

SlipKit의 PDF 생성 엔진은 다음 조건을 만족해야 합니다.

- 브라우저에서 서버 왕복 없이 PDF 생성
- Node.js에서도 같은 핵심 코드 사용
- 밀리미터 기반 좌표 배치
- 사용자 폰트 임베딩
- 한국어와 일본어를 포함한 유니코드 출력
- 벡터 텍스트 유지
- 이미지, 선, 도형, 표와 바코드 출력
- 여러 페이지 생성
- SlipKit 파일 형식과 PDF 엔진 형식의 분리

### pdfme 조사 결과

[pdfme](https://github.com/pdfme/pdfme)는 TypeScript 기반 PDF 생성기와 React 기반 UI를 제공하는 MIT 라이선스 프로젝트입니다. 공식 문서에 따르면 생성기는 브라우저와 Node.js에서 동작하며 JSON 템플릿을 사용합니다.

pdfme는 텍스트, 이미지, 도형, 바코드와 표 등의 스키마를 제공하고, 일부 동적 요소의 높이 변경과 페이지 분할도 지원합니다. 다만 자동 페이지 분할은 빈 용지 기반 템플릿 등 정해진 조건에서 동작합니다.

관련 공식 자료:

- [pdfme 공식 저장소](https://github.com/pdfme/pdfme)
- [pdfme 지원 기능](https://pdfme.com/docs/supported-features)
- [pdfme 동적 표](https://pdfme.com/docs/tables)

### SlipKit의 적용 범위

SlipKit은 다음 패키지만 내부 PDF 생성 엔진으로 사용합니다.

- `@pdfme/common`
- `@pdfme/generator`
- `@pdfme/schemas`

pdfme의 React 기반 디자이너, 작성폼과 뷰어는 사용하지 않습니다.

SlipKit의 `.slip` 파일이 원본 데이터이며, PDF를 만들 때만 내부 변환 계층에서 pdfme 템플릿과 입력값을 생성합니다. pdfme의 타입과 템플릿 구조는 SlipKit의 공개 API로 노출하지 않습니다.

### 직접 사용하지 않는 기능

pdfme가 표와 페이지 분할을 지원하더라도 SlipKit의 통합 그리드는 해당 기능에 직접 의존하지 않습니다.

SlipKit이 요구하는 다음 동작은 자체 변환 계층에서 계산합니다.

- 셀별 테두리
- 셀 병합
- 여러 행으로 이루어진 반복 구간
- 빈 반복 행의 괘선
- 반복 헤더
- 열별 자동 병합
- 양식이 지정한 페이지당 항목 수
- 반복 항목 수 상한

그리드는 선, 사각형과 텍스트 요소로 분해한 뒤 pdfme에 전달합니다.

### 선택 이유

pdfme를 사용하면 PDF 바이트 생성, 폰트 임베딩과 기본 요소 렌더링을 직접 다시 구현하지 않아도 됩니다.

동시에 SlipKit 파일 형식과 변환 계층을 별도로 유지하므로 다음 기능은 프로젝트가 직접 통제할 수 있습니다.

- 양식과 전표 구조
- 파라미터와 수식
- 페이지 분할 규칙
- 저장소 어댑터
- 파일 암호화
- Web Component UI

### 확인된 주의사항

- pdfme 템플릿은 SlipKit의 공개 형식으로 저장하지 않습니다.
- 스키마 속성의 기본값을 하부 엔진에 암묵적으로 맡기지 않고 변환 계층에서 명시적으로 채웁니다.
- pdfme가 자체적으로 해석할 수 있는 표현식과 SlipKit 수식이 섞이지 않게 합니다.
- CJK 문자는 해당 글리프를 포함한 사용자 폰트가 필요합니다.
- pdfme의 표 및 페이지 분할 동작을 SlipKit 그리드의 동작으로 간주하지 않습니다.
- 의존성 버전을 올릴 때 생성된 PDF와 페이지 수를 회귀 테스트합니다.

### pdf-lib과의 관계

[pdf-lib](https://github.com/Hopding/pdf-lib)은 JavaScript 환경에서 PDF 생성과 수정을 제공하는 저수준 라이브러리입니다. 공식 저장소는 브라우저, Node.js, Deno와 React Native 지원 및 사용자 폰트 임베딩 기능을 설명합니다.

SlipKit은 원본 `pdf-lib`을 직접 렌더링 엔진으로 사용하지 않습니다. pdfme가 유지하는 `@pdfme/pdf-lib` 포크를 pdfme 의존성을 통해 간접적으로 사용합니다. 테스트에서 필요한 일부 타입과 기능을 위해 원본 `pdf-lib`이 개발 의존성으로 존재할 수 있습니다.

원본 `pdf-lib`의 릴리스 간격이 길다는 사실만으로 프로젝트가 중단됐다고 단정하지 않습니다. 다만 PDF 엔진을 직접 구성할 경우 필요한 레이아웃, 폰트와 페이지 처리 범위가 커지므로 현재는 pdfme 변환 계층을 유지합니다.

### 재검토 조건

다음 상황이 발생하면 PDF 생성 엔진을 다시 평가합니다.

- 브라우저 또는 Node.js 지원이 SlipKit의 지원 환경과 맞지 않게 된 경우
- CJK 폰트나 서브세팅에 해결하기 어려운 문제가 발생한 경우
- 현재 변환 계층으로 우회할 수 없는 PDF 오류가 반복되는 경우
- 보안 취약점이나 라이선스 변경이 발생한 경우
- 번들 크기 또는 생성 성능이 공개 기준을 충족하지 못하는 경우
- pdfme 타입이 SlipKit 공개 API에 새어 나가기 시작한 경우

## 2. Web Component와 Lit

### 요구 조건

SlipKit UI는 특정 프레임워크에 종속되지 않고 다음 환경에서 사용할 수 있어야 합니다.

- 프레임워크를 사용하지 않는 웹 애플리케이션
- React
- Vue
- 커스텀 엘리먼트를 사용할 수 있는 다른 프레임워크

### Web Component 조사 결과

커스텀 엘리먼트는 브라우저가 제공하는 표준 컴포넌트 경계입니다. 프레임워크가 달라도 같은 엘리먼트를 사용할 수 있어 임베드형 UI 라이브러리에 적합합니다.

[Vue 공식 문서](https://vuejs.org/guide/extras/web-components.html)는 Vue 애플리케이션에서 커스텀 엘리먼트를 사용하거나 Vue 컴포넌트를 커스텀 엘리먼트로 만드는 방식을 제공합니다.

[React 19 공식 발표](https://react.dev/blog/2024/12/05/react-19)는 커스텀 엘리먼트의 프로퍼티 처리를 포함한 지원을 명시합니다. SlipKit React 패키지는 이에 맞춰 React 19 이상을 지원합니다.

### Lit 조사 결과

[Lit](https://lit.dev/)은 브라우저의 커스텀 엘리먼트 위에서 반응형 프로퍼티, 템플릿 렌더링, 생명주기와 스타일 캡슐화를 제공합니다.

Lit 컴포넌트는 표준 HTML 엘리먼트이므로 외부 공개 형태가 Lit 전용 컴포넌트가 되지는 않습니다.

### SlipKit의 적용 범위

`@omdc-slipkit/elements`는 Lit으로 다음 커스텀 엘리먼트를 구현합니다.

- `<slip-designer>`
- `<slip-form>`
- `<slip-viewer>`

외부 계약은 커스텀 엘리먼트의 프로퍼티, 메서드와 이벤트입니다. Lit은 내부 구현 기술로만 사용합니다.

### React와 Vue 래퍼의 역할

React 19와 Vue가 커스텀 엘리먼트를 지원하더라도 프레임워크별 래퍼에는 다음 역할이 남습니다.

- 컴포넌트 자동 등록
- TypeScript용 프로퍼티 타입 제공
- 객체 프로퍼티 전달 방식 정리
- `slip-change`, `slip-issue` 같은 커스텀 이벤트를 프레임워크 콜백이나 emit으로 변환
- 프레임워크 사용자가 익숙한 이름과 방식으로 컴포넌트 사용

따라서 React 래퍼를 React 18 이하의 호환 계층으로 설명하지 않습니다. 현재 React 패키지는 React 19 이상을 대상으로 하며, 커스텀 이벤트와 타입을 연결하는 얇은 통합 계층입니다.

Vue에서도 호스트 빌드 설정으로 `slip-*` 태그를 커스텀 엘리먼트로 지정하면 래퍼 없이 직접 사용할 수 있습니다. 래퍼는 필수 런타임이 아니라 편의와 타입을 위한 선택 패키지입니다.

### 재검토 조건

- 브라우저 지원 범위에 커스텀 엘리먼트를 지원하지 않는 환경이 추가되는 경우
- 프레임워크 업데이트로 프로퍼티나 이벤트 전달 방식이 달라지는 경우
- 래퍼가 자체 상태와 비즈니스 로직을 갖기 시작하는 경우
- Shadow DOM 때문에 필요한 테마 또는 접근성 요구를 해결하기 어려운 경우

## 3. 스키마 검증과 JSON Schema

### 요구 조건

`.slip`은 외부에서 들어오는 JSON 파일이므로 TypeScript 타입만으로 안전성을 보장할 수 없습니다.

다음 기능이 필요합니다.

- 런타임 입력 검증
- TypeScript 타입 추론
- 양식과 전표 구분
- 오류 경로 제공
- JSON Schema 생성
- 브라우저와 Node.js 지원

### Zod 조사 결과

[Zod 공식 문서](https://zod.dev/)는 Zod 4가 TypeScript 우선 런타임 스키마 검증과 정적 타입 추론을 제공하며, JSON Schema 변환을 기본 기능으로 포함한다고 설명합니다.

SlipKit은 Zod 스키마를 런타임 검증과 TypeScript 타입의 단일 원천으로 사용하고, `z.toJSONSchema`를 이용해 Draft 2020-12 대상 JSON Schema를 생성합니다.

### 선택 이유

- 런타임 스키마와 TypeScript 타입을 함께 관리할 수 있습니다.
- 같은 스키마에서 공개용 JSON Schema를 생성할 수 있습니다.
- 브라우저와 Node.js에서 같은 검증 로직을 사용할 수 있습니다.
- 세부 오류 경로를 이용해 사용자에게 어느 값이 잘못됐는지 알릴 수 있습니다.

### 적용 시 주의사항

JSON Schema와 구조 검증만으로 모든 파일 의미를 확인할 수는 없습니다.

다음과 같은 규칙은 별도 의미 검증이나 Zod의 추가 검사가 필요합니다.

- 요소가 참조하는 파라미터의 존재 여부
- 값 소스의 상호 배타성
- 반복 구간의 범위
- 병합 셀의 겹침
- 용지와 요소 크기의 관계
- 외부 이미지 URL의 발행 제한
- 양식과 전표에만 적용되는 조건부 규칙

JSON Schema를 생성할 수 있다는 사실이 모든 Zod 변환과 사용자 정의 검사를 다른 구현에서 완전히 재현할 수 있다는 뜻은 아닙니다. 공개 스키마와 `SPEC.md`를 함께 유지합니다.

### 재검토 조건

- Zod의 번들 크기가 실제 브라우저 사용에 문제가 되는 경우
- JSON Schema 변환에서 필요한 구조를 안정적으로 표현하지 못하는 경우
- 스키마 변경 시 타입 추론 성능이 개발 작업을 방해하는 경우
- 다른 런타임 검증 도구가 마이그레이션 비용을 상쇄할 명확한 이점을 제공하는 경우

## 4. 수식 엔진

### 요구 조건

SlipKit 수식은 전체 스프레드시트가 아니라 전표의 계산 필드를 위한 기능입니다.

필요한 범위는 다음과 같습니다.

- 기본 산술
- 합계와 조건부 집계
- 문자열 처리
- 날짜와 숫자 형식
- 조건식
- 전표에서 자주 사용하는 세무 계산
- 명시적인 값 형 변환
- 임의 코드 실행 차단

셀 주소, 워크시트, 범위 재계산과 스프레드시트 호환성은 현재 요구사항이 아닙니다.

### 외부 수식 엔진 검토

[HyperFormula](https://hyperformula.handsontable.com/docs/)는 스프레드시트 계산에 필요한 다수의 함수, 셀 참조와 의존성 계산을 제공하는 전문 엔진입니다.

기능 범위는 넓지만 SlipKit에 필요한 전표 계산보다 큰 데이터 모델을 전제로 합니다. 또한 [공식 라이선스 문서](https://hyperformula.handsontable.com/docs/guide/licensing.html)에 따르면 GPLv3 또는 별도 구매하는 독점 라이선스로 제공됩니다.

현재 SlipKit의 라이선스와 배포 방식에서 HyperFormula를 그대로 포함하려면 라이선스 정책 또는 별도 계약 검토가 필요합니다. 따라서 단순히 기능 수가 많다는 이유로 포함하지 않습니다.

> [!CAUTION]
> 이 문서는 법률 자문이 아닙니다. 외부 라이브러리를 실제 배포물에 추가할 때는 해당 시점의 라이선스 원문과 프로젝트 배포 조건을 다시 확인해야 합니다.

### 자체 엔진 선택 이유

SlipKit은 제한된 문법과 함수만 지원하는 자체 파서와 평가기를 사용합니다.

이 방식은 다음 요구에 맞습니다.

- `eval` 없이 허용한 문법만 처리
- 셀 주소가 아닌 파라미터 이름 사용
- 지원 함수와 타입 규칙을 명확하게 제한
- 전표에 필요한 오류 메시지 제공
- 브라우저와 Node.js에서 같은 결과 생성
- 별도의 수식 엔진 라이선스 의존성 방지

### 비용과 주의사항

자체 수식 엔진은 다음 책임을 프로젝트가 직접 부담합니다.

- 토큰화와 파싱
- 연산자 우선순위
- 함수 인자 검사
- 날짜와 숫자 처리
- 타입 변환
- 로케일별 형식
- 오류 위치와 메시지
- 경계값과 악의적인 입력 테스트

새로운 함수를 추가할 때는 이름만 등록하지 않고 파서, 평가기, 타입 규칙, 문서와 테스트를 함께 갱신해야 합니다.

### 재검토 조건

다음 요구가 실제로 확인되면 외부 엔진을 다시 평가합니다.

- 셀 주소와 범위 참조
- 여러 계산 필드 사이의 의존성 그래프
- 변경된 값만 다시 계산하는 증분 평가
- 워크시트 또는 조회표
- 엑셀 함수와 높은 수준의 호환성
- 현재 함수 범위를 크게 넘는 업무 요구

외부 엔진을 다시 검토할 때는 기능뿐 아니라 번들 크기, 브라우저 지원, 라이선스와 SlipKit 파라미터 모델의 변환 비용을 함께 비교합니다.

## 5. 디자이너 렌더링 방식

### 후보

양식 디자이너의 편집 화면은 크게 두 방식으로 구현할 수 있습니다.

| 방식 | 장점 | 주요 부담 |
|---|---|---|
| DOM 기반 요소 배치 | 텍스트 입력, 포커스, IME와 접근성 처리에 유리 | 요소 수가 매우 많을 때 렌더링 비용 증가 |
| Canvas 기반 렌더링 | 많은 그래픽 객체와 자유 변형에 유리 | 텍스트 편집, 키보드 조작과 접근성 계층을 별도로 구현 |

### 선택

SlipKit 디자이너는 DOM 기반 절대 위치 요소를 사용합니다.

SlipKit의 주요 편집 대상은 텍스트, 필드, 그리드, 이미지와 기본 도형입니다. 자유로운 그림 제작보다 정확한 크기와 데이터 연결이 중요하며, 한글과 일본어 입력도 안정적으로 처리해야 합니다.

### 선택 이유

- 브라우저의 텍스트 입력과 IME를 사용할 수 있습니다.
- 포커스와 키보드 이벤트를 일반 DOM 규칙으로 처리할 수 있습니다.
- 요소별 편집 패널과 선택 상태를 연결하기 쉽습니다.
- Lit 컴포넌트 구조와 자연스럽게 결합됩니다.
- 일반적인 전표의 요소 수는 DOM으로 처리할 수 있는 범위입니다.

### PDF와의 관계

DOM 기반 디자이너를 사용한다는 것은 DOM을 캡처해 PDF를 만든다는 뜻이 아닙니다.

- 디자이너는 `.slip` 양식을 편집합니다.
- 미리보기와 PDF는 `core`의 변환 결과를 사용합니다.
- 최종 PDF는 pdfme를 통해 별도로 생성합니다.

화면과 PDF가 공통 좌표 규칙을 사용하더라도 폰트 측정과 렌더링 엔진의 차이로 줄바꿈이 달라질 수 있습니다. 두 결과의 일치 여부는 테스트와 실제 출력으로 계속 확인해야 합니다.

### 재검토 조건

- 자유곡선과 펜 입력이 핵심 기능이 되는 경우
- 한 페이지에 매우 많은 개별 객체를 표시해야 하는 경우
- DOM 렌더링 성능이 실제 양식에서 기준을 충족하지 못하는 경우
- 확대·축소와 회전에 현재 구조로 해결하기 어려운 요구가 추가되는 경우

Canvas를 도입하더라도 전체 디자이너를 한 번에 교체하기보다 필요한 요소나 미리보기 계층에 한정하는 방식을 먼저 검토합니다.

## 6. 파일 암호화

### 요구 조건

`.slip` 파일은 JSON이므로 평문 상태에서는 파일 내용을 직접 확인할 수 있습니다.

파일 보호 기능에는 다음 조건이 필요합니다.

- 브라우저와 Node.js에서 사용 가능
- 외부 서버 없이 암호화와 복호화
- 잘못된 키와 암호문 변경 감지
- 원시 키와 암호 문자열 지원
- 알고리즘과 키 파생 정보를 파일 봉투에 기록
- 키 관리 책임을 호스트에 유지

### Web Crypto 조사 결과

[Web Cryptography API 명세](https://www.w3.org/TR/webcrypto/)는 AES-GCM 인증 암호화와 PBKDF2 키 파생을 정의합니다.

AES-GCM은 암호화된 내용의 기밀성과 인증 태그 검증을 함께 제공합니다. PBKDF2는 암호 문자열, 솔트, 반복 횟수와 해시 함수를 사용해 키를 파생합니다.

### SlipKit의 적용

SlipKit은 다음 구성을 사용합니다.

- AES-256-GCM
- 무작위 초기화 벡터
- 문자열 암호의 PBKDF2-SHA256 키 파생
- 무작위 솔트
- 암호화 봉투에 알고리즘과 키 파생 정보 저장
- 복호화 후 일반 `.slip` 스키마 검증

정확한 바이트 구조와 복호화 절차는 [파일 형식 명세](./SPEC.md)를 따릅니다.

### 경계

암호화 기능은 다음 문제를 해결하지 않습니다.

- 사용자 인증과 권한
- 키 생성과 안전한 보관
- 사용자 사이의 키 전달
- 키 분실 복구
- 감사 기록
- 생성된 PDF의 보호
- 암호화되지 않은 메타데이터의 노출

이 책임은 호스트 애플리케이션의 보안 정책에 속합니다.

동봉된 샘플 키는 암호화 흐름을 확인하기 위한 값이며 실제 보안 키가 아닙니다.

### 재검토 조건

- Web Crypto 지원 환경이 변경되는 경우
- 보안 검토에서 알고리즘이나 파라미터 변경이 필요한 경우
- PBKDF2 반복 횟수가 현재 환경의 성능 또는 보안 기준과 맞지 않는 경우
- 키 식별자나 외부 키 관리 시스템 연동이 필요한 경우
- 암호화 봉투 버전을 추가해야 하는 경우

> [!NOTE]
> PBKDF2 반복 횟수는 영구적으로 안전한 상수가 아닙니다. 성능과 공격 비용이 변하므로 공개 전 보안 검토와 향후 버전 변경 시 다시 평가해야 합니다.

## 7. 모노레포와 작업 실행

### 현재 구성

SlipKit은 pnpm workspace로 다음 패키지와 예제를 관리합니다.

- `@omdc-slipkit/core`
- `@omdc-slipkit/elements`
- `@omdc-slipkit/react`
- `@omdc-slipkit/vue`
- Web Component, React와 Vue 데모

[pnpm 공식 문서](https://pnpm.io/)는 workspace 지원과 여러 패키지의 의존성 관리를 제공합니다.

현재 빌드, 타입 검사와 테스트는 pnpm의 재귀 실행과 필터 기능으로 처리합니다.

### 별도 작업 오케스트레이터를 사용하지 않는 이유

현재 저장소에는 Turborepo나 Nx를 사용하지 않습니다.

패키지가 네 개이고 의존 방향이 단순하므로 다음 기능만으로 현재 작업을 처리할 수 있습니다.

- workspace 패키지 연결
- 패키지별 스크립트
- `pnpm -r` 재귀 실행
- `--filter` 대상 제한
- 잠금 파일을 통한 의존성 고정

널리 사용된다는 이유만으로 작업 오케스트레이터를 추가하지 않습니다. 새 도구는 설정, 캐시 검증과 개발 규칙을 추가하므로 실제 병목이 확인된 뒤 도입합니다.

### 재검토 조건

- 패키지와 예제 수가 크게 증가하는 경우
- 전체 빌드와 테스트 시간이 개발을 방해하는 경우
- 변경된 패키지만 계산하는 작업 그래프가 필요한 경우
- CI 원격 캐시가 실질적인 이점을 제공하는 경우
- 여러 팀이 독립된 패키지를 동시에 배포하게 되는 경우

## 8. 현재 채택하지 않은 기술의 처리

기술을 채택하지 않았다는 사실이 해당 기술의 품질이 낮다는 뜻은 아닙니다.

현재 요구사항과 맞지 않거나 도입 근거가 부족한 기술은 다음 원칙으로 처리합니다.

- 구체적인 사용 사례가 생기기 전에는 의존성을 추가하지 않습니다.
- 공식 자료로 확인하지 못한 프로젝트를 대안으로 추천하지 않습니다.
- 라이선스가 현재 배포 정책과 맞지 않으면 별도 검토 없이 포함하지 않습니다.
- 현재 구조로 해결할 수 있는 문제에 새로운 프레임워크를 추가하지 않습니다.
- 성능상 이점은 실제 SlipKit 데이터와 동일한 조건에서 측정합니다.
- 기술을 교체할 때는 공개 API와 `.slip` 형식에 미치는 영향을 먼저 확인합니다.

## 9. 기술 변경 점검표

주요 의존성을 추가하거나 버전을 올릴 때 다음 항목을 확인합니다.

### 공통

- [ ] 공식 릴리스와 마이그레이션 문서를 확인했는가
- [ ] 라이선스와 배포 조건을 확인했는가
- [ ] Node.js와 지원 브라우저 범위가 맞는가
- [ ] 번들에 새 런타임 의존성이 포함되는가
- [ ] 공개 API나 `.slip` 형식에 내부 타입이 노출되는가
- [ ] 보안 공지와 알려진 취약점을 확인했는가
- [ ] 기존 테스트와 데모가 통과하는가

### PDF 관련

- [ ] 한국어와 일본어 폰트가 정상적으로 임베딩되는가
- [ ] 여러 페이지와 반복 그리드의 페이지 수가 유지되는가
- [ ] 텍스트, 이미지, 바코드와 도형이 정상 출력되는가
- [ ] 화면 미리보기와 PDF의 위치·줄바꿈 차이가 커지지 않았는가
- [ ] 생성된 PDF를 주요 브라우저와 PDF 뷰어에서 열 수 있는가

### UI 관련

- [ ] React와 Vue에서 객체 프로퍼티가 올바르게 전달되는가
- [ ] 커스텀 이벤트가 한 번만 등록되고 해제되는가
- [ ] 한글과 일본어 IME 입력이 정상 동작하는가
- [ ] Shadow DOM 스타일과 호스트 페이지가 충돌하지 않는가
- [ ] 키보드 조작과 포커스 이동이 유지되는가

### 파일 형식 관련

- [ ] Zod 런타임 스키마와 JSON Schema가 함께 갱신됐는가
- [ ] `SPEC.md`의 예시와 제약이 현재 스키마와 일치하는가
- [ ] 외부에서 만든 파일과 손상된 파일을 올바르게 거부하는가
- [ ] 공개된 이전 파일이 있다면 마이그레이션이 필요한가
- [ ] 암호화 봉투와 평문 `.slip`을 모두 읽을 수 있는가
