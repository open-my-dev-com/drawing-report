## Q-01. 내부 구현 프레임워크

Web Component로 **배포**하는 것은 확정(ADR-003)이지만, 그 내부를 무엇으로 **구현**할지는 미정.

- 후보: Lit(Web Component 네이티브, 경량), React(생태계 최대, 커스텀 엘리먼트로 감싸 배포), Svelte(컴파일 결과 경량), Preact(React 호환 + 경량)
- 판단 기준: GUI 디자이너 수준의 복잡한 UI 개발 생산성 vs 번들 크기 vs 팀 숙련도
- 구현 착수 시점에 결정하면 됨 (배포 형태에는 영향 없음)

## Q-02. 수식 함수 스타터셋 확정

방향은 확정(ADR-010: 엄선된 세트로 시작). 아래 초안을 리뷰하여 추가/제거 확정 필요.

**초안:**

| 분류 | 함수 |
|---|---|
| 집계 (표의 열 대상) | `SUM`, `AVG`, `COUNT`, `MIN`, `MAX` |
| 산술 | `+ - * /`, `ROUND`, `FLOOR`, `CEIL`, `ABS` |
| 문자열 | `CONCAT`, `LEFT`, `RIGHT`, `MID`(자르기), `REPLACE`(치환), `TRIM`, `UPPER`, `LOWER` |
| 조건 | `IF`, `AND`, `OR`, 비교연산자 (`= <> < > <= >=`) |
| 포맷 | `FORMAT_NUMBER`(천단위 콤마), `FORMAT_DATE`, `NUMBER_TO_KOREAN`(금액 한글 표기 — 전표 특화) |
| 날짜 | `TODAY`, `DATE_ADD`, `DATE_DIFF` |

- 사용자 언급 요구: 문자열 자르기·치환, 더하기, 평균 — 모두 초안에 포함됨
- 추가 검토 후보: `VLOOKUP`류(주입 데이터 참조), `SUMIF`/`COUNTIF`(조건부 집계), 부가세 특화 함수(`VAT` 등)

## Q-04. 위변조 방지 서명의 방식 상세

방향은 확정(ADR-009: 서명 기본 제공). 상세 미정:

- 단순 내용 해시(변조 "탐지"만 가능 — 재계산하면 위조 가능) vs 공개키 서명(발행자 증명까지 — 키 관리 필요)
- 키를 누가 들고 있는가: 호스트 서버 서명? 브라우저 서명? (권한 위임 원칙 ADR-004와 정합 필요)
- 서명 대상 범위: 전표 데이터만? 내장 양식 스냅샷 포함 전체?

## Q-05. GUI 디자이너 v1 기능 범위 상세

- 지원 요소 목록: 텍스트, 표, 이미지, 선/도형, 입력 필드… 어디까지?
- 표 요소의 편집 자유도 (셀 병합? 열 너비 조절? 중첩?)
- 스냅/정렬 가이드, 실행취소(undo), 요소 복사 등 편집 편의 기능 수준
- 양식 갤러리/기본 제공 템플릿 (거래명세서, 청구서 등 프리셋 몇 종을 동봉할지)

## Q-06. 저장소 어댑터 인터페이스 상세

방향은 확정(ADR-006). 상세 미정:

- 인터페이스 형태 (save/load/list/delete? 버전 이력은 어댑터 책임인가?)
- 기본 동봉 어댑터: 로컬 파일 다운로드/업로드, localStorage/IndexedDB 정도로 시작?
- 사용자 업로드 폰트(ADR-012)의 저장 위치도 이 어댑터를 경유하는가?

## Q-07. 표준 교환 포맷 명세 공개 수준

- 파일 포맷 스펙 문서를 어느 수준까지 작성·공개할지 (타 시스템이 파일을 읽고 쓰는 게 목표이므로 스펙 문서가 결국 필요 — ADR-006 ③)

- 참고: Zod 4로 스키마를 정의하면 JSON Schema 산출이 내장됨 (TECH-RESEARCH.md §5)

## Q-08. pdfme 채택 전략 (2026-08-18 리서치에서 발생 — TECH-RESEARCH.md 참조)

[pdfme](https://github.com/pdfme/pdfme)(MIT)가 우리 확정 요구의 상당 부분(JSON 템플릿, WYSIWYG 디자이너, 자동 페이지 분할 표, CJK 폰트, 브라우저/Node 생성)을 이미 구현하고 있음. 선택지:

1. **pdfme를 기반(의존성/포크)으로 삼고** 우리 고유 요구(서명·암호화, 양식 스냅샷, 저장소 어댑터, 권한 인터페이스, 수식 엔진, Web Component 포장)를 그 위에 얹는다 — 개발량 대폭 감소, 대신 pdfme의 스키마·아키텍처에 종속
2. **참조 구현으로만 활용**하고 전부 자체 개발 — 자유도 최대, 개발량 최대
3. **부분 채택**: pdfme가 유지보수하는 `@pdfme/pdf-lib` 포크 등 하위 레이어만 채택하고 상위는 자체 개발

- 판단 기준: 우리 스키마 요구(스냅샷 내장·서명 필드·asset:// 참조)를 pdfme 템플릿 포맷이 수용/확장 가능한지 실측 필요 (프로토타이핑 권장)
- 어떤 선택이든 ADR-012의 pdf-lib은 pdfme 포크 채택 (TECH-RESEARCH.md §2)
