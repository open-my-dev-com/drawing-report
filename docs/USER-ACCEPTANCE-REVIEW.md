# 유저 사용 리뷰

> [!IMPORTANT]
> 전체적인 평가는 그럴싸하게 만들어졌으나 전혀 유저의 편의성과 유저의 사용감은 일체 고려하지 않은 개발로 보여집니다.
> 내부의 수정할 내용이 너무 많아 전체적인 내용을 읽고 비슷한 내용끼리 먼저 정리해야할 듯합니다.
> 분명 이전 단계에서 자체평가를 하여 내용을 정리하였음에도 불구하고 본인 스스로의 자체평가가 너무 후한게 아닌지 우려됩니다. 유저의 관점에서 사용했을때를 고려해달라는 요청이 있었음에도 전혀 고려되지 않았습니다.
> 점수는 28/100점입니다.

> [!NOTE]
> 처리 상태는 각 항목 끝에 표시한다 — **[완료]**는 고치고 검증 게이트를 통과한 것,
> **[확인]**은 질문에 답한 것. 표시가 없으면 아직 처리 전이다.

## 버그
- 1. 행과 열 추가에서 아이콘 버튼으로 바뀌면서 +버튼과 열 라벨이 CSS상으로 붙어져버리는 버그 발생. **[완료]** — 두 칸 배치(`.prop-pair`)의 간격이 6px이라 앞 칸의 `+` 버튼이 뒤 칸 라벨과 맞닿았다. 14px로 벌리고 숫자 칸도 넓혔다
- 2. 고정이미지, 변동이미지 버튼 깨짐현상있음. => 이미지 업로드와 파라미터(현재 값이라 불리는 것) 2가지로 나누는게 더 나을것으로 보여짐. **[완료]** — 토글 버튼이 **28×24px 고정 아이콘 상자**인데 여기에 글자를 넣어 넘쳤다. 글자를 담는 토글 변형을 만들어 내용에 맞춰 늘어나게 했다
- 3. 텍스트는 백스페이스로도 잘만 지워지는데 왜 도형은 안지워질까요? (뭔가 버그가 있음, 지워질때는 지워지고 안지워질때는 안지워짐. 버그가 왜 발생하는지 모름. 다시 하니까 또 지워졌음 => 다시 해보니까 만든 시점에서는 제거가 안됨. 다른데를 클릭후에 다시 클릭하여 백스페이스해야 제거되는거 확인.) **[완료]** — 진단하신 재현 조건이 정확했다. 요소를 만드는 갈래가 끌기를 위해 `preventDefault()`를 부르는데 그러면 브라우저 기본 포커스 이동도 함께 막히고, 도구 버튼이 다시 그려지며 포커스가 컴포넌트 **밖으로** 빠져 단축키가 닿지 않았다. 캔버스를 누른 순간 호스트가 포커스를 갖게 했다
- 4. 페이지 설정에 쓰레기 뭐지요? => "썸네일·목록에 번호 대신 나온다" **[완료]** — 문장이 아닌 조각인데다 `이름` 아래·`물리명` 위에 놓여 어느 쪽 설명인지도 흐렸다. `이름을 지으면 썸네일·목록에 번호 대신 이름이 보입니다.`로 바꿨다
- 5. 샘플 데이터 편집 모달 : 입력폼 JSON전환시, 서로의 내용이 다른 이슈있음. 입력폼에서 아무 값도 입력 안했으면 적어도 "파라미터명": "" 의 형태로 전환되어야하는게 아닌가 싶음. (placeholder는 사용자로 하여금 혼동의 여지가 올 수 있으니 제거바람 => 실제로 값이 들어있는줄 알았습니다.) **[완료]** — JSON 탭이 저장된 샘플 값만 덤프해 비워 둔 파라미터가 통째로 빠졌다. 이제 **선언된 파라미터를 모두 담은 뼈대**에 지금 값을 얹는다(종류에 맞는 빈 값, 목록은 하위 필드가 든 항목 하나). 값이 든 것으로 오해되던 JSON 예시 placeholder도 지웠다
- 6. 버그는 아닐것 같은데 확인차. 그리드에서 배경색 설정하고 설정된 셀의 값을 입력하기 위해서 클릭하면 Input박스가 열리면서 배경색이 순간적으로 사라진 것으로 보이는 데, 기술적으로 이거 해결 못하는지 궁금(Input박스도 배경색을 따라가게 한다던가 하는) 안되면 뭐 어쩔수 없다고 생각함. **[완료]** — 됩니다. 입력 상자가 자기 배경색(`--sk-surface`)으로 칸을 덮고 있었다. 칸의 배경색·글자색·크기·정렬을 그대로 물려받게 했다

## 고쳐야 할 점 (화면계)

### [공통]
- 1. 세로쓰기의 버튼이 혼자 가운데 정렬이 되어있음. 스타일의 일체화가 전혀 이루어지지 않고 있음. 또한, 버튼 크기도 작아서 클릭하기 불편함. 최소한 아이콘버튼 수준의 크기 요구. (다른 버튼 계열도 마찬가지) **[완료]** — 원인은 글상자용 규칙(`flex:1; width:0`)이 **체크박스에도 걸려** 늘어난 칸 안에서 혼자 가운데로 보인 것이었다. 체크박스 크기를 고정하고 왼쪽에 세워 다른 줄과 시작 위치를 맞췄다. 누를 자리도 아이콘 버튼 크기(26px)로 통일했다(토글 24→26, 사이드바 미니 20→24)
- 2. 수식 편집 모달에서 바인딩값을 단순 뱃지로 해서 클릭해서 추가하는 것에 대해서, 이전에 말했던 바인딩 변수의 타입이 지정되어있지 않아 아무거나 막 입력해도 검사 조차 없음. 애초에 분명 이전 대화로 바인딩에 타입을 넣는다고 했었던것 같은데 이 부분이 적용되어 있지 않아 생기는 문제로 보임. **[완료]** — 지적이 맞았다. `valueType`은 스키마에 있었으나 **지정할 화면이 없어**(변동 이미지 자동 등록 경로 하나뿐) ADR-044의 엄격 타입이 실효가 없었다. ① 파라미터·하위 필드 패널에 값 종류 선택을 넣고(ADR-047), ② 수식 모달의 파라미터 칩에 종류를 함께 보이며, ③ **샘플 값이 없어도** 선언된 종류의 시험값으로 평가해 `SUM(글자값)` 같은 어긋남이 편집 중에 드러나게 했다(전에는 샘플 값이 있을 때만 검사됐다)
- 3. 고정 문구 => "직접 입력"으로 수정 **[완료]** — UI 문구 3개 언어 + SPEC·코드 주석·테스트까지 일괄(SSOT)
- 4. 바인딩 => "파라미터"로 수정 요청 **[완료]** — UI 문구 3개 언어·문서(SPEC·DECISIONS·REQUIREMENTS·가이드 3벌)·`terms.md`·코드 주석·테스트 설명까지 일괄. 코드 식별자 `binding`은 영어 규칙대로 유지
- 5. 종류 보기 => "요소 확인"으로 수정 요청 **[완료]**

### [선]
- 1. 가로/세로일때는 굵기, 기준점이 마음대로 왔다갔다 하고 있음.(선에 기준점 요소를 넣을거면 오른쪽이냐 왼쪽이냐 하나로 넣는게 나음. 위일 경우 오른쪽, 아래의 경우 왼쪽 이렇게 해도 되고 아니면 차라리 좌표 1,1 좌표 2,2 로 좌표값을 2개를 받아서 좌표 1을 기준점으로 할지 좌표 2를 기준점으로 할지정도가 더 낫지 않나.) **[완료]** — 기준점 기본값이 **방향마다 달라서** 방향을 바꾸면 값이 튀어 보였다. 선의 기준점을 **좌중앙 하나로 고정**했고, 방향을 패널에서 바꿀 수 없게 되어(아래 3번) 더는 튀지 않는다
- 2. 사선일 경우 선굵기 설정이 없음.(너비높이로 바뀜. 버그인지 고정된건지 모르겠음.) **[완료]** — 버그였다. 곧은 선에만 굵기 칸을 두어 사선으로 바꾸면 굵기를 고칠 방법이 없었다. 사선에도 굵기 칸을 보인다(사선은 두 축이 끝점을 정하므로 너비·높이는 유지)
- 3. 애초에 선의 경우 방향을 굳이 오른쪽 사이드바에서 설정할 이유를 모르겠음. 그냥 기준점위치, 길이, 선 굵기, 선 색, 형태만 있으면 되는거 아닌가? **[완료]** — 방향 선택을 패널에서 뺐다. 끝점 핸들을 끌면 그때 방향이 정해지므로 캔버스에서 이미 하는 일을 패널에 겹쳐 둔 셈이었다. 쓰이지 않게 된 문구 5종도 함께 지웠다

### [사각형]
- 1. 사각형 테두리가 없음 상태가 없음상태인건지 없음 상태인것처럼 보이는데, #000000설정으로 보임. 또한, 사각형에서 테두리 굵기 설정 + 테두리색 기본형태로 하면 테두리가 분명 없어야할텐데 미묘한 테두리같은게 생김.(원본색에서 살짝 어두운형태의) => 근데 이 어두운형태의 테두리 자체는 이쁜것 같긴 함. 그래서 그냥 없애고 싶지는 않은 느낌도 드네... 이걸 어떻게할지 고민좀. **[완료]** — 「미묘한 어두운 테두리」의 정체는 캔버스 전용 편집 보조선(`rgba(0,0,0,.15)`)이었고, PDF에는 없었다. 즉 **화면과 PDF가 어긋나 있었다**(ADR-012 위반). 캔버스가 PDF가 실제로 그릴 테두리를 그리게 고쳤다 — 사각형처럼 기본 굵기가 있는 종류는 그 기본 테두리를, **굵기가 「없음」일 때만** 보조선을 남긴다. 그래서 「없음」과 「기본값」이 화면에서 갈리고, 좋아하신 그 모습은 「없음」 상태에서 그대로 남는다

### [텍스트와 필드]
- 기본적으로 비슷한 형태고, 내용이 직접 입력이랑, 파라미터 설정, 수식 설정 이렇게 3개로 나뉘는것 같은데 분리할 필요성이 새삼 있을까... 아이콘자체는 지금처럼 분리하는게 좋긴 한데 그리드의 칸 내용이라는걸 놓고 보니 나눌 필요가 있나 싶은 느낌이 듭니다. **[완료]** — 확정하신 대로 요소 종류는 그대로 두고 **패널에서 텍스트 ↔ 필드를 바꿔 끼울 수 있게** 했다. 자리·크기·글자 스타일은 그대로 두고 담는 것만 갈아 끼우며 배지·아이콘도 따라 바뀐다

### [그리드]
- 1. 넘칠 때 자르기 => 의도 불분명한 표현의 사용. 뭐가 넘친다는건지 뭘 자른다는건지 확실하게 이해가 안됨. 이제 보니까 문자열이 길어져서 넘칠때를 의미하는것 같은데 의도 전달 가능하게 명칭 수정. **[완료]** — `글이 칸을 넘치면` / `넘는 부분 잘라내기` · `글자 줄여 넣기` (3개 언어)
- 2. 반복 구간의 명칭의 전체적인 문제가 있음 글자 크기가 길어져서 문제가 될 것 같으니, 차라리 라벨 값을 한 줄에 이어 쓰는 방식보다 2줄에 나누어서 쓰는 방식도 검토해야겠습니다.
```
반복 구간 : 구간 반복이 더 나을것 같네요.
첫 행, 끝 행 : 시작 행 종료 행
페이지당 : 구간의 기본 틀 생성 갯수
헤더 반복 : 페이지 전환시 헤더 반복

=> 추가로 최대 반복 구간 갯수 제한 기능이 없어, 무제한만 허용중인것도 고쳐야함.
```
**[일부 완료]** — 라벨 5종을 제안하신 이름으로 바꾸고(`구간 반복`·`시작 행`·`종료 행`·`구간의 기본 틀 생성 개수`·`페이지 전환 시 헤더 반복`), 길어진 라벨은 **라벨을 위·입력을 아래**로 두는 2줄 배치로 돌렸다. 반복 구간이 쓰는 값은 목록 종류 파라미터만 후보로 낸다. **최대 반복 개수 제한도 완료** — 양식이 `그릴 항목 수 상한`을 정하면 넘는 항목은 그리지 않고 페이지도 늘리지 않는다(ADR-048)
- 3. 그리드에서 특정 셀을 선택할 경우, 그리드 자체의 옵션은 감춰줘야합니다. (유저 혼동의 여지 있음) 그리드 대신 셀옵션으로 바꿔주고, 그리드 하위의 셀로 별도의 이름을 가지게 하는 편이 더 나을것 같습니다. (그리드와 셀분리, 이전의 요소와 바인딩의 분리하고도 같은 내용) **[완료]** — 칸을 고르면 그리드 옵션(행·열 수, 반복 구간, 넘침)이 감춰지고 칸 편집만 남는다. 맨 위에 그리드로 돌아가는 줄을 뒀다. `행 높이`·`열 너비`는 고른 칸의 행·열을 가리키므로 칸 쪽으로 옮겼다


## 의도와 다른 점

### 바인딩
- 바인딩과 요소를 결국 분리해내지 못함. (그 증거로 하위 바인딩입력시 여전히 요소로 자동연결이 되어버림) **[완료]** — 하위 필드를 고르면 요소가 아니라 그 필드가 오른쪽 패널에서 편집된다. 그 필드를 읽는 칸은 「쓰는 곳」으로만 보이고 자동 연결하지 않는다 (ADR-047)
- 입력필드에는 바인딩을 SELECT박스로 유저의 바인딩 실수가 발생하지 않게 유도해주는 부분이 있으나, 다른 화면에는 이러한 조치가 행해져 있지 않음.(위와 동일) **[완료]** — 그리드 칸의 값 입력이 자유 입력이었다. 선택 상자로 바꾸고 자리에 따라 후보를 가린다: 반복 구간 **안**은 그 목록의 하위 필드, **밖**은 최상위 파라미터 (ADR-047)
- 바인딩자체가 제대로 설계되어있지 않으니 하위바인딩을 만드는 방법조차 없음.(그리드를 만들어야만 만들어지는 기괴한 구조가 되어있음) 바인딩에 대해서 전체적으로 문제투성이. **[완료]** — 하위 필드가 그리드 칸에서 역산되던 구조를 끊고 정의부(`bindings[].fields`)를 단일 원천으로 만들었다. 그리드 없이 사이드바·패널에서 하위 필드를 만들고 고친다 (ADR-047)

### 왼쪽 사이드바의 하위요소
- N행 N열 -> n가 아니고, 셀 이름이 나오면 됨. (요소와 바인딩 분리를 확실히) **[완료]** — 줄에는 칸 이름만 보이고 자리(행·열)는 툴팁으로 돌렸다. 반복 구간 칸의 이름도 하위 필드의 논리명을 따른다
