# 설계 결정 로그 (ADR)

> 각 결정은 번호·결정 내용·근거·기각한 대안을 기록한다.
> 번호는 코드·문서가 참조하는 **안정 식별자**라 재사용하지 않는다. 공개 전 정리(2026-08-23)에서
> 완전히 대체돼 참조가 남지 않은 ADR(014·035)은 제거했고, 그 번호는 다시 쓰지 않는다(빈 번호).
> 이 로그와 [REQUIREMENTS.md](REQUIREMENTS.md)가 어긋나면 이 로그가 우선하며, REQUIREMENTS.md를 고친다.

## ADR-001: 전표 = 범용 양식 엔진으로 정의

- **결정**: "전표"를 특정 서식에 고정하지 않고, 양식(템플릿)을 자유롭게 정의하는 범용 양식 엔진으로 만든다. 문서형 전표(거래명세서·청구서·견적서·영수증)와 회계형 전표(차변/대변) 모두 템플릿으로 표현한다. 양식(템플릿)과 전표 데이터(기입값)는 별도 구조로 분리해 양식 1개로 전표 N장을 만든다.
- **근거**: 요구가 "자유도 보장 + 만들기 쉽게"였고, 문서형/회계형 중 하나로 한정하지 않기로 했다.
- **기각**: 문서형 전용(자유도 부족), 회계 분개 전용(레이아웃 요구 미충족).

## ADR-002: 배포 형태 = 임베드형 라이브러리 (계층형 모노레포)

- **결정**: 서버 포함 풀스택이나 독립 실행 앱이 아닌, 호스트 앱에 임베드되는 라이브러리 패키지로 만든다. 계층형 모노레포:
  - `core` — 파일 포맷 스키마·파싱·검증·마이그레이션·수식 평가·레이아웃 엔진·PDF 렌더러 (순수 TS, DOM/프레임워크 비의존)
  - `elements` — Web Component UI
  - `react` / `vue` — 얇은 래퍼 (선택 설치)
- **근거**: 권한 호스트 위임(ADR-004)·연계 방식(ADR-006)과 맞물린다. core 분리로 파일 포맷의 레퍼런스 구현이 확보되고 Node 재사용(서버 렌더러·백엔드 검증·CLI)이 가능해진다.
- **기각**: 풀스택(권한 위임과 모순), 독립 앱(임베드 요구와 모순).

## ADR-003: UI 배포 = Web Component + 프레임워크별 얇은 래퍼

- **결정**: UI를 커스텀 엘리먼트(`slip-*`)로 배포한다. React/Vue 사용자를 위해 각 프레임워크 관례로 감싼 얇은 래퍼 패키지를 별도 제공한다. 내부 구현 프레임워크는 배포 형태와 별개다(ADR-015).
- **근거**: "설치할 쪽이 뭐든 상관없이 연계되는 게 베스트". React 전용은 Vue 등에서 못 쓰므로 범용성을 1순위로 뒀다.
- **기각**: React 전용(범용성 없음), 프레임워크별 개별 포팅(유지보수 비용 배수).

## ADR-004: 권한제어 = 호스트 앱에 위임

- **결정**: 패키지는 자체 유저/인증 시스템을 갖지 않는다. 컴포넌트가 `mode`(edit/view)·권한 플래그를 속성으로 받고, 인증과 권한 판단은 호스트 앱이 책임진다.
- **근거**: 패키지툴로서 가장 가볍고, 어떤 호스트의 기존 인증 체계와도 충돌하지 않는다.
- **기각**: 자체 권한 시스템(무겁고 이중화), 파일 레벨 보호만(권한 모델로는 부족 — 파일 보호는 ADR-009로 별도).

## ADR-005: 양식 제작자 = 일반 사용자, GUI 디자이너 필수

- **결정**: 양식(템플릿)은 비개발자가 드래그앤드롭 GUI 디자이너로 직접 설계한다. GUI 디자이너가 이 프로젝트의 중심 결과물이다.
- **근거**: "일반 사용자(GUI 필수)"를 명시 선택. "만들기는 쉽게"의 대상이 개발자가 아닌 최종 사용자다.
- **파급**: 수식도 GUI에서 다뤄지므로 내장 수식 엔진(ADR-010)이 사실상 필수가 된다.

## ADR-006: 외부 연계 = 데이터 주입 + 저장소 어댑터 + 표준 파일 포맷

- **결정**: 연계 방식은 셋 — ① 호스트 데이터 주입(파라미터), ② 저장소 어댑터(저장/불러오기 인터페이스 추상화 — 로컬 파일·S3·DB·자체 서버 등), ③ 표준 교환 파일 포맷(파일 자체를 명세화). REST API 서버 제공은 범위 제외.
- **근거**: 셋을 복수 선택, REST API는 미선택. 임베드형 라이브러리(ADR-002)에 부합.

## ADR-007: 파일 포맷 = JSON 기반 자체 스키마 (ZIP 컨테이너 확장 경로 확보)

- **결정**:
  - 내용은 JSON, 구조는 자체 스키마, 전용 확장자 `.slip`(ADR-018).
  - 모든 파일에 `schemaVersion`을 내장하고, 구버전 자동 마이그레이션 계층을 core에 둔다.
  - 이미지는 `src` 필드로 통일: 외부 URL / `data:` base64 / `asset://` 내부 참조 3종(이미지 정책은 ADR-036으로 base64만 실렌더).
  - v1은 순수 JSON 단일 파일. 대용량 리소스가 필요하면 동일 JSON을 manifest로 하는 ZIP 컨테이너(docx 방식)를 추후 추가하며, `asset://` 참조가 그 확장 슬롯이다(추가 시 스키마 변경 없어야 함).
- **근거**: JS 생태계 궁합(파싱·검증·디프)이 XML 대비 우수. 복수 페이지는 포맷이 아닌 스키마 설계 문제다.
- **기각**: XML(도구 생태계 열세), 처음부터 ZIP(초기 복잡도 불필요).

## ADR-008: 양식 버저닝 = 전표 파일에 생성 시점 스냅샷 내장

- **결정**: 전표 파일은 생성 당시 양식 전체를 복사해 내장한다. 발행된 전표는 이후 양식이 수정돼도 모양이 바뀌지 않으며, 양식 저장소 없이 파일 단독으로 열람 가능하다(자기완결).
- **근거**: 전표의 증빙 성격상 "발행 당시 모습 보존"이 필수이고, 표준 교환 포맷(ADR-006)에도 부합한다.
- **기각**: templateId@version 참조(양식 저장소 없으면 열람 불가), 최신 양식 참조(발행 당시 모습 훼손).
- **트레이드오프**: 파일 용량 증가를 수용한다.

## ADR-009: 파일 보안 = 위변조 방지 서명 기본 + 암호화 옵션

- **결정**: 전표 내용의 해시/서명을 파일에 내장해 발행 후 무결성을 검증 가능하게 한다(기본 제공). 서명 상세는 ADR-019.
- **근거**: 전표는 "숨기기(암호화)"보다 "위변조 안 됨 보장(서명)"이 우선이다.
- **개정**: 암호화 옵션은 v2에서 넣지 않기로 했다(ADR-041). 서명·무결성(ADR-019)은 그대로.

## ADR-010: 계산 필드 = 내장 수식 엔진 (엄선된 함수 세트, 안전한 자체 파서)

- **결정**: 양식 필드에 엑셀 스타일 수식 문자열을 지원하는 수식 엔진을 core에 내장한다. 함수는 전부 넣지 않고 자주 쓰이는 것을 엄선한다(스타터셋은 ADR-017). 수식은 자체 파서로 해석하며 임의 코드 실행(`eval` 등)은 절대 금지.
- **근거**: 일반 사용자가 GUI로 양식을 만드는 이상(ADR-005) 합계란·치환 등 계산을 직접 정의할 수 있어야 한다.
- **기각**: 호스트가 계산해 값만 주입(일반 사용자가 계산란을 못 넣음), 전체 함수 일괄 제공(범위 통제 불가).

## ADR-011: 레이아웃 = 용지 기준 좌표계, 복수 페이지 1급, 자동 페이지 분할 필수

- **결정**: 양식은 용지 크기(A4 등) 기준 절대 좌표계로 설계한다. 페이지는 스키마의 1급 개념(`pages`)이며, 표가 페이지를 넘치면 자동으로 다음 페이지로 분할한다(헤더 반복 옵션 포함). 자동 분할은 필수 기능이다.
- **근거**: 인쇄·PDF 필수 + "자동 페이지 분할 필수"를 명시 선택.
- **개정**: 분할 **주체**는 하부 엔진이 아니라 우리 변환 계층이 직접 계산한다(ADR-037 — 분할이 필수라는 결정은 유지). 페이지별 소계 옵션은 보류(ADR-041, 반복 없는 그리드로 우회 가능).

## ADR-012: 렌더링 파이프라인 = 좌표 계산 단일화, PDF는 브라우저 직접 생성

- **결정**:
  - 파이프라인: `양식+데이터 → 변환 계층(core, 순수 TS·DOM 비의존) → PDF 엔진 → PDF`. 좌표 계산은 core에서 한 번만 하고 화면 미리보기도 같은 변환 결과를 쓴다 — **화면·인쇄·PDF 불일치가 구조적으로 불가능**하다.
  - PDF는 브라우저에서 클라이언트 직접 생성한다. 서버 왕복 없고 전표 데이터가 브라우저 밖으로 나가지 않는다. **DOM 캡처(스크린샷→이미지 PDF) 방식은 금지**(벡터 텍스트 유지).
  - 인쇄는 생성된 PDF를 인쇄하는 방식으로 통일한다.
  - 폰트는 PDF에 내장하되 사용 글자만 서브세팅한다. 언어별 기본 폰트 1종 동봉 + 호스트 공급(ADR-040/042).
  - 서버 렌더러는 추후 확장: 동일 core+PDF 렌더러를 Node 패키지로 재포장해 **호스트 인프라에서** 일괄 발행에 쓴다. **제3자 외부 서버는 어떤 경우에도 개입하지 않는다.**
- **근거**: 좌표 계산을 한 곳에 두면 벡터 텍스트·픽셀 일치·Node 재사용을 모두 얻는다. 실행 엔진은 pdfme(ADR-016).
- **기각**: DOM 캡처(래스터 품질·분할 문제), print CSS만(자동화 불가·브라우저 편차), v1부터 서버 렌더러 포함(현재 불필요).

## ADR-013: i18n = 한국어 우선, 구조만 선확보

- **결정**: UI 문구는 처음부터 리소스 파일로 분리하고, 통화·날짜 포맷 함수는 로케일 지정이 가능하게 설계해 언어 추가 시 재작업이 없게 한다. (영어·일본어 추가는 ADR-028/042.)
- **근거**: 초기 속도와 확장 가능성의 균형.

## ADR-015: Web Component 내부 구현 = Lit

- **결정**: `elements` 패키지의 내부 구현 기술로 [Lit](https://lit.dev)을 채택한다.
- **근거**: Web Component 배포(ADR-003)에 가장 자연스럽고 번들이 경량. 외부 API(커스텀 엘리먼트)에 영향 없는 내부 선택이라 유사시 교체 가능.
- **기각**: React 내부+WC 래핑(런타임 번들 증가), Svelte(생태계 대비 이점 부족).

## ADR-016: PDF 생성 엔진 = pdfme 채택 (렌더러 인터페이스 뒤로 외부 비공개)

- **결정**:
  - `@pdfme/generator`·`@pdfme/schemas`·`@pdfme/common`(MIT)을 core 내부의 **PDF 생성 실행 엔진**으로 채택한다.
  - 채택 범위는 엔진까지다. UI(디자이너/뷰어/작성폼)·파일 포맷·서명·수식·저장소 어댑터·권한 인터페이스는 전부 자체 개발한다. pdfme의 React UI(`@pdfme/ui`)는 쓰지 않는다.
  - 우리 포맷이 진실의 원천이고, pdfme 템플릿은 core가 생성 시점에 변환·조립하는 **중간 표현**이다. **pdfme 의존은 렌더러 인터페이스 뒤에 두어 공개 API에 노출하지 않으며**, 유사시 자체 렌더러로 교체 가능한 구조를 유지한다.
  - pdfme 테이블 스키마는 스타일 속성 불완전 시 조용히 깨지므로(직접 확인) 변환 계층에서 **기본값 병합을 필수**로 한다.
- **근거**: 평가에서 최고 난도 요구(A4 자동 분할·헤더 반복·한글 서브세팅·2페이지 ~260ms)를 전부 통과했다. 가장 어려운 구간을 재발명하지 않는다.
- **기각**: 전부 자체 개발(기간 대폭 증가), pdfme UI까지 전면 채택(ADR-003·015와 충돌).

## ADR-017: 수식 함수 스타터셋 확정

- **결정**: 수식 함수를 다음으로 확정한다(현재 32종 — 타입 변환 3종은 ADR-044에서 추가).
  | 분류 | 함수 |
  |---|---|
  | 집계 | `SUM`, `AVG`, `COUNT`, `MIN`, `MAX` |
  | 조건부 집계 | `SUMIF`, `COUNTIF` |
  | 산술 | `+ - * /`, `ROUND`, `FLOOR`, `CEIL`, `ABS` |
  | 문자열 | `CONCAT`, `LEFT`, `RIGHT`, `MID`, `REPLACE`, `TRIM`, `UPPER`, `LOWER` |
  | 조건 | `IF`, `AND`, `OR`, 비교연산자(`= <> < > <= >=`) |
  | 포맷 | `FORMAT_NUMBER`, `FORMAT_DATE`, `NUMBER_TO_KOREAN` |
  | 날짜 | `TODAY`, `DATE_ADD`, `DATE_DIFF` |
  | 세무 | `VAT`(세율 인자, 기본 10%) |
  | 타입 변환 | `TO_NUMBER`, `TO_STRING`, `TO_DATE` (ADR-044) |
- **근거**: 문자열 처리·집계·평균 등 언급된 요구에 더해, 전표 실무(과세/면세 구분 집계·부가세란)에서 즉시 필요한 조건부 집계·VAT를 추가했다.
- **기각**: 축소판(언급 요구 탈락), `VLOOKUP`류(넣지 않기로 확정 — ADR-039).

## ADR-018: 네이밍 = SlipKit / .slip 확장자 / slip-* 접두사

- **결정**:
  - 제품명 **SlipKit**, 파일 확장자 **`.slip`**(양식·전표 공용 — 내부 `kind`로 구분), 커스텀 엘리먼트 접두사 `slip-*`.
  - npm 스코프는 `@omdc-slipkit/*`(ADR-027로 개정 — 원래 `@slipkit/*`였다).
- **근거**: slip은 "전표"의 표준 영어 대응어(sales slip)로 의미가 정확하고 짧으며 확장자가 직관적이다.
- **기각**: VoucherKit(voucher의 상품권 의미 혼동), Jeonpyo(해외 전달 불가).

## ADR-019: 서명 상세 = SHA-256 해시 필수 + JWS(ES256) 서명 옵션

- **결정**:
  - 모든 발행 파일에 **SHA-256 내용 해시를 항상 내장**한다 — 키 없이 훼손을 탐지하는 기본 무결성 계층.
  - 호스트가 키를 제공하면 **JWS(ES256, 공개키 서명)**를 추가로 내장해 발행자를 증명한다(옵션, 통상 호스트 서버가 서명).
  - 대상 범위는 **내장 양식 스냅샷을 포함한 전표 내용 전체**다(스냅샷 위조도 막아야 함).
  - 해시·서명 계산 전제로 **JSON 정규화(canonicalization) 규칙을 스펙에 명시**한다(같은 내용이면 같은 바이트).
- **근거**: 해시만으로는 재계산 위조가 가능하고 서명 필수는 도입 장벽이 높다. 단계적 구조가 실용성과 보안을 모두 충족한다.
- **기각**: 해시만(위조 방지 불가), 서명 필수(키 없는 호스트는 발행 불가).

## ADR-020: GUI 디자이너 v1 범위 = 실사용 최소선 + 셀 병합·색 스타일

- **결정**:
  - 요소 6종으로 시작: 텍스트, 고정 그리드 표, 동적 행 표, 이미지, 선/사각형, 입력 필드. (이후 도형 4종 분리(ADR-032)·그리드 통합(ADR-037)·바코드 추가로 현재 9종.)
  - 색 스타일: 전 요소에 배경색·글자색·테두리색(+두께·형태) 지정.
  - 편집 편의: 열 너비 조절, 스냅·정렬 가이드, undo/redo, 복사/붙여넣기.
  - 기본 프리셋 2종 동봉: 거래명세서·청구서.
- **근거**: 일반 사용자 대상(ADR-005)이라 undo·스냅 없는 에디터는 체감 품질 미달이다. "실사용 최소선보다 조금 더 — 셀 병합·색 포함"을 명시 선택했다. (원래 "동적 행 표 셀 병합은 pdfme 제약으로 불가"라는 근거는 그리드 통합(ADR-037)으로 제약이 사라져 무효.)

## ADR-021: 저장소 어댑터 = CRUD + 목록·검색, 버전 이력은 선택 인터페이스

- **결정**:
  - 필수 인터페이스: `save` / `load` / `delete` / `list`(페이징·필터).
  - 버전 이력은 별도의 **선택 인터페이스** — 구현한 어댑터에서만 이력 UI가 노출된다.
  - 기본 동봉 어댑터: ① 로컬 파일 다운로드/업로드, ② IndexedDB. 구현 위치·상세는 ADR-025/045.
- **근거**: 전표 목록 화면은 사실상 모든 호스트가 필요로 하므로 `list`까지가 실용 최소선이다. 이력을 필수로 하면 어댑터 구현 장벽이 커진다.

## ADR-022: 파일 포맷 스펙 = 명세서 공개 + JSON Schema 동봉

- **결정**: `.slip` 포맷 명세서(SPEC.md)를 공개 문서로 유지하고, Zod 스키마에서 산출한 **JSON Schema를 패키지에 동봉**한다. 타 시스템은 언어 무관하게 파일을 기계 검증할 수 있다.
- **근거**: "표준 교환 파일 포맷"(ADR-006 ③)이 목표인 이상 스펙과 기계 검증 수단은 포맷의 일부다. Zod의 JSON Schema 산출로 이중 관리 비용이 없다.

## ADR-023: 브랜치 전략 = 규칙 기반 분기

- **결정**: 모든 작업은 규칙대로 브랜치를 분기해 진행한다. `main`은 보호(직접 커밋 금지, PR 병합만), 작업 브랜치는 `<type>/<scope>-<topic>` 형식, 커밋은 Conventional Commits. 규칙 본문은 [`.claude/rules/branching.md`](../.claude/rules/branching.md)에 두어 세션에 자동 적용한다(ADR-024).
- **근거**: 규칙을 세션 간 유지하기 위해 지시로 확정했다.

## ADR-024: 개발 규칙 강제 = CLAUDE.md + .claude/ 4계층 (rules·hooks·skills·settings)

- **결정**: 개발 규칙을 성격에 맞는 계층에 나눠 리포에 규정한다.
  | 계층 | 파일 | 역할 |
  |---|---|---|
  | 지침(항상 로드) | `CLAUDE.md` + `.claude/rules/branching.md` | 문서·코드 불변 규칙·검증 게이트 / 브랜치·커밋·PR·작업 시작 절차 |
  | 경로 스코프 규칙 | `.claude/rules/{core,ui-packages,docs,comments}.md` | 해당 경로 작업 시 자동 로드 |
  | 기계적 차단 | `.claude/settings.json` deny + PreToolUse 훅 `bash-guard.mjs` | main 푸시·커밋 차단, `git commit` 시 검증 게이트 자동 실행·실패 시 차단 |
  | 절차 명령 | `.claude/skills/{next-task,verify}` | `/next-task`, `/verify` |
  - `main`은 **스쿼시 머지 전용**. 미병합 브랜치 위 PR 스택 금지, 자기 PR은 한 번에 하나, 브랜치당 커밋 최소화.
- **근거**: 지침 계층은 준수를 유도하고 100% 강제는 훅·permissions가 담당한다 — 둘을 병행해야 완전하다. 훅이 못 잡는 새 위반 패턴은 `bash-guard.mjs`에 추가한다.

## ADR-025: 저장소 어댑터 구현 위치 = 인터페이스는 core, 브라우저 구현은 elements

- **결정**: 어댑터 인터페이스·타입·오류(`StorageAdapter`·`SlipStorageError`)는 core에 둔다(호스트가 자체 어댑터를 만들 때 core만 있으면 됨). 브라우저 구현 2종(`IndexedDbStorage`·`LocalFileStorage`)은 elements에 둔다. 로컬 파일 어댑터는 매체 특성상 `delete`/`list`를 `unsupported` 오류로 던진다.
- **근거**: core는 순수 TS(ADR-002)라 DOM 타입을 차단하고 있어 브라우저 API 구현을 둘 수 없다. 대부분 호스트가 elements와 함께 쓰므로 패키지를 늘리지 않고 4패키지 구조를 유지했다.
- **기각**: 새 패키지 `@omdc-slipkit/storage`(관리 패키지 증가), core에 DOM lib 추가(ADR-002 위반 — 서버 시나리오가 깨짐).

## ADR-026: 디자이너 다중 페이지 편집 = v1 포함

- **결정**: `<slip-designer>`에 다중 페이지 편집 UI를 넣는다 — 페이지 전환·추가·삭제(최소 1페이지 유지), 요소 편집은 현재 페이지 대상, 되돌리기 지원.
- **근거**: 포맷은 `pages` 배열로 다중 페이지를 1급 지원(ADR-011)하는데 디자이너가 첫 페이지만 편집하면 능력이 어긋난다.

## ADR-027: npm 패키지명에 omdc- 접두사 (`@omdc-slipkit/*`)

- **결정**: npm 패키지명을 `@slipkit/*`에서 **`@omdc-slipkit/*`**로 변경한다. 적용 범위는 **설치명(npm 패키지명)뿐**이며 제품명 SlipKit·엘리먼트 접두사 `slip-*`·확장자 `.slip`·포맷 식별자는 ADR-018 그대로다.
- **근거**: 조직 식별(omdc)을 설치명에 반영. 코드 영향이 가장 적은 범위를 선택했다.
- **기각**: 제품명까지 변경(문서 전반 수정 부담), 태그·확장자까지 변경(호환성 파괴).

## ADR-028: UI 언어에 영어 추가 (한국어 기본 유지)

- **결정**: UI 문구를 언어별 사전 구조로 개편하고 컴포넌트·래퍼·저장소 어댑터 오류에 `locale`('ko'|'en', 기본 'ko')을 둔다. 지역 붙은 로케일(`en-US`)은 언어만 보고 고르며 모르는 로케일은 한국어로 돌아간다. 새 문구는 두 사전에 함께 추가하고 `SlipStrings` 타입이 키 누락을 컴파일에서 잡는다.
- **범위 제외**: 프리셋 내용·core 오류 메시지·`NUMBER_TO_KOREAN`은 한국어 유지. 숫자 표기 로케일은 별도 축(`RenderOptions.locale`, ADR-013).
- **근거**: ADR-013이 선확보한 리소스 분리 구조 덕에 재작업 없이 사전 추가로 해결됐다.

## ADR-029: 소스 주석 표준 = TSDoc

- **결정**: 선언에 붙는 설명 주석은 **TSDoc 블록(`/** */`)**을 표준으로 한다. 공개 함수·메서드는 `@param`·`@returns`를 기본으로 채우고 오류를 던지면 `@throws`를 명시한다. 코드 중간의 구현 설명은 `//` 한 줄 주석을 유지한다. 규칙은 [`.claude/rules/comments.md`](../.claude/rules/comments.md).
- **근거**: TS 언어 서비스는 `/** */`만 문서 주석으로 인식한다 — `//`는 호버·자동완성·`.d.ts`에 안 나온다. 혼용을 표준으로 통일한다.

## ADR-030: TSDoc 형식 기계 검증 도입 (eslint + tsdoc/syntax만)

- **결정**: eslint 최소 구성을 추가하고 규칙은 `tsdoc/syntax` **하나만** 켠다. `pnpm lint`를 검증 게이트 맨 앞에 넣는다(`pnpm lint && pnpm -r typecheck && pnpm -r build && pnpm -r test`, 커밋 훅도 강제).
  - 잡는 것: 오탈자·비표준 태그, JSDoc식 타입 중괄호, `@param 이름 - 설명`의 하이픈 누락 등 문법 위반.
  - 안 잡는 것: `@param`·`@returns` 누락 — 지침·리뷰로 유지.
- **근거**: 최신 eslint-plugin-tsdoc의 규칙이 `syntax` 하나뿐임을 소스로 확인했다. 누락 검사까지 하려면 jsdoc 조합이 필요한데 구성 단순함을 우선했다. 도입 첫 실행에서 형식 위반 61건을 잡아 실효를 확인했다.
- **기각**: 미도입(사람이 계속 잡아야 함), eslint-plugin-jsdoc 조합(검사 범위는 넓으나 구성이 복잡 — 필요 시 확장).

## ADR-031: v2 범위 = 디자이너 사용 편의 중심

- **테마**: v2는 새 능력 추가보다 **디자이너를 일반 사용자가 실제로 쓸 수 있는 도구로** 다듬는 데 집중한다. v1에서 포맷·렌더러는 지원하지만 GUI가 못 따라간 구간(표 내부 편집·이미지 넣기·용지 설정 등)을 채운다.
- **기술 방향**: UI는 **Lit 유지**(ADR-015) + 자체 CSS 디자인 토큰. 기본 한글 폰트 **Pretendard**(OFL) 동봉·자동 사용(ADR-012의 "기본 한글 폰트 동봉" 이행). 서브패스 export로 안 쓰는 호스트 번들에는 안 들어간다.
  - 기각: MUI(React 전용 — Lit에 도입 불가), Tailwind(Shadow DOM 주입 빌드로 복잡도만 늘고 이점 없음).
- **범위**: 포맷 개정(0.2.0~0.5.0 — 도형 4종 분리·그리드 통합·글자 조판·페이지 번호·변동 이미지·바코드 등, ADR-032/037 이하), 표·도형·글자 GUI, 데이터·작성 흐름(수식 모달·샘플 데이터·전표 작성폼·양식 저장), 화면 점검 반영(요소·파라미터 분리 ADR-034·눈금자·격자), 고급 편집(요소 그룹화·데이터 자동 병합), 일본어(ADR-042), 총괄 리뷰. 세부 항목·순서는 [ROADMAP.md](ROADMAP.md).
- **v3**: **MCP 제공 + AI 전표 자동 생성**만 다룬다 — 편집 기능이 충분히 완성된 뒤 연동을 여는 것이 무난하다는 판단.

## ADR-032: 파일 포맷 0.2.0 상세 — 표 열 구조·자유 선·도형·글자 스타일·파라미터 정의부

> 각 항목은 PDF 변환 계층이 실제로 그리는지 직접 렌더해 확인한 결과를 따른다(ADR-012/016).

- **동적 표 열 구조**: `head: string[]` → `columns: { key, title, widthPercentage }[]` — **물리 데이터 키·표시 제목·너비를 분리**해 제목을 바꿔도 데이터·수식이 깨지지 않게 한다. (이후 그리드로 통합, ADR-037.)
- **도형을 독립 요소 타입 4종으로 분리**: `shape`를 없애고 `line`·`rect`·`ellipse`·`polygon`을 각각 요소 타입으로 둔다. 종류마다 의미 있는 스타일이 달라(선은 색·굵기·형태·방향만, 사각형은 배경·테두리·반경) 잘못된 조합이 스키마 차원에서 불가능해지고 속성 패널도 타입별 항목만 보인다.
  - **정다각형은 `sides`(변 수 3~12) 한 필드로 일반화** — 3=삼각형·5=오각형·6=육각형. 이름별 타입으로 늘리면 타입이 불어나므로 기각. 타원·정다각형은 상자에 내접.
  - **선은 `lineDirection`(horizontal/vertical/down/up)** 으로 상자 두 모서리를 잇는다. `start`/`end` 좌표 필드는 position·width·height와 정보가 중복돼 불일치 여지가 생기므로 기각.
- **사각형 모서리 반경** `radius?`(mm): 파선·점선과 동시 지정 금지(곡선 구간은 분해 렌더 불가) — 검증에서 거부.
- **테두리 형태 렌더 규칙**: `borderStyle`(solid/dashed/dotted)은 **직선(선 요소·사각형 radius 미지정·고정 그리드선)에만** 적용(변환 계층이 짧은 선분으로 분해). 곡선(타원) 테두리와 텍스트·필드·동적 표는 실선 고정 — svg의 stroke-dasharray가 무시되기 때문(직접 확인).
- **글자 스타일**: 텍스트·필드·고정 그리드 셀에 `bold`·`underline`·`strikethrough`. 밑줄·취소선은 엔진 직접 지원. **굵게는 폰트 전환**(`<이름>-Bold`가 렌더 옵션에 있으면 그 폰트로, 없으면 무시 — 동봉 Pretendard-Bold는 항상 적용). **기울임은 제외** — 한글 폰트는 이탤릭 변형이 거의 없고 흉내는 인쇄 품질을 해친다.
- **샘플 값**: 양식 본문에 `sampleValues?` — 미리보기용 시험 데이터. 발행·무결성과 무관하며 전표 생성 시 복사하지 않는다.
- **요소 그룹**: 요소 공통 `group?: string`(그룹 편집 UI는 이후).
- **파라미터 정의부**: 양식 본문에 `parameters?: { key, label? }[]` — 물리명(key)은 파일·수식·연동에, 논리명(label)은 화면 표시에. key 중복 금지. 요소가 미등록 키를 쓰는 것도 허용(등록 강제 없음).

## ADR-033: 고정 그리드 셀별 테두리 렌더 규칙

- **결정**:
  - 셀의 `borderColor`·`borderWidth`·`borderStyle`을 실제 렌더에 반영한다. 셀 값은 그 셀(병합 범위)의 둘레 변에 적용되고, 없으면 요소 값(그것도 없으면 기본 0.2mm 검정 실선)을 쓴다.
  - **공유 변 충돌**: 이웃 두 셀이 공유하는 변은 **유효 굵기가 더 큰 쪽**을 따르고, 같으면 아래·오른쪽 셀을 따른다. `borderWidth: 0`은 "그 변을 그리지 않음"이다.
  - 병합 범위 내부 경계선은 그리지 않는 기존 규칙 유지.
- **근거**: 대표 사례 — **마지막 행 왼쪽 칸 테두리를 지우고 오른쪽 한 칸만 합계 박스로** 남기는 전표 하단 표현을 표 하나로 만든다. 굵은 쪽 우선은 CSS `border-collapse`와 같은 방향이라 예측하기 쉽다.
- **기각**: 변(edge) 단위 4방향 필드(스키마·UI 복잡 — 셀 단위+충돌 규칙으로 대표 사례가 다 풀림), 먼저 선언된 셀 우선(편집 순서에 결과가 의존).

## ADR-034: 요소와 파라미터를 분리한다 — 왼쪽은 목록, 오른쪽은 편집

- **결정**:
  - **파라미터는 요소와 별개의 1급 항목**이다. 어떤 요소가 쓰든 목록에 동등하게 존재하며 요소는 "어떤 값을 쓸지" 고르기만 한다.
  - **왼쪽 사이드바는 목록·선택·추가·삭제만** 하고, **오른쪽 패널이 편집을 전담**한다. 선택 대상은 **요소 | 파라미터 | 표 열** 셋이며 아무것도 안 고르면 양식 설정이 뜬다.
  - 요소 패널의 파라미터는 등록된 목록에서 고르는 선택 상자로 하고(맨 아래 "새 값 등록"), 사이드바의 파라미터 추가(+)는 기본 이름으로 즉시 만들어 선택한다.
  - 물리명을 바꾸면 그 값을 쓰는 요소·샘플 값이 함께 따라간다. 표 파라미터는 하위 열까지 트리로 보이고, 요소 목록은 페이지별로 묶어 전부 보인다. 파라미터 패널에는 "쓰는 곳"(페이지·요소)을 둔다.
- **근거**: 사이드바 인라인 편집은 취소 수단이 없어 고치다 만 값이 바깥 클릭에 저장되고 Esc도 안 들었다(직접 확인). 편집을 한 곳으로 모으면 이 문제가 기능 추가 없이 사라진다. 선택 대상을 셋으로 넓히면 "왼쪽에서 고르고 오른쪽에서 고친다" 규칙 하나로 전부 설명된다.
- **함께 정한 화면 규칙**: 펼쳐지는 항목(색 피커·테두리 등)은 한 번에 하나만 열린다. 지정 안 한 항목은 실제 적용 중인 값(기본값·물려받는 값)을 흐리게 보인다. 표 너비는 **국소 변경**(추가는 마지막 열을 나눠 갖고 삭제는 이웃 열이 돌려받아 추가↔삭제가 정확히 원상복구).

## ADR-036: 이미지는 base64로만 담는다 — URL 참조를 쓰지 않는다 (ADR-014 대체)

- **결정**:
  - 양식에 넣는 고정 이미지는 **파일에서 골라 base64로 담는 것만** 지원한다(디자이너에 URL 입력 없음).
  - 전표 데이터로 받는 변동 이미지도 **base64만** 받는다.
  - 주소로 받아야 하는 이미지는 **호스트 서버가 중계해 base64로 바꿔 넘긴다**. 이 라이브러리는 이미지를 받아오지 않는다.
  - 이미지 크기 상한을 둔다 — `maxImageBytes`(기본 2MB)를 호스트가 조인다.
  - **발행 파일은 외부 URL 의존 없이 단독 완결**이어야 한다(ADR-008 스냅샷 원칙과 동일) — 발행 검증은 스냅샷·변동 이미지 값에 외부 URL이 없는지 확인한다.
- **근거**:
  - **URL은 어차피 PDF로 나오지 않는다.** `resolveImageSrc`는 `data:`·`asset://`만 풀고 http(s)는 오류다 — core가 순수 TS라 네트워크를 안 쓰기 때문(ADR-002)이며 바뀔 성질이 아니다. 원래 하이브리드 안(작성 중 URL 허용 → 발행 시 내장)은 "발행 시 내장" 코드가 만들어진 적이 없어 실제로 동작한 적 없는 결정이었다.
  - 받아오는 쪽을 만들면 CORS·인증·실패 처리가 전부 호스트 환경에 달린 문제라 라이브러리가 떠안기에 부적절하다. 호스트 서버는 이미 그 맥락을 갖고 있다.
  - 바이너리는 선택지가 아니다 — 전표 `values`가 `Record<string, JsonValue>`라 JSON에 안 담긴다. base64는 원본보다 ~33% 커져 상한이 없으면 전표 파일이 감당 못 한다.
- **기각**: 붙여넣은 주소를 디자이너가 그 자리에서 받아 변환(CORS로 자주 실패, 원인을 못 손씀), 주소를 그대로 저장(미리보기·PDF가 깨진 채).
- **영향**: 스키마는 바꾸지 않는다(다른 시스템이 만든 파일을 못 읽게 될 이유가 없음) — 다만 외부 URL은 **PDF로 렌더할 수 없음**을 SPEC에 명시한다.

## ADR-037: 그리드를 하나로 합치고 반복 구간을 둔다 — 표 조판을 우리 것으로

- **결정**:
  - 요소 `grid`를 신설한다 — **고정 그리드와 동적 표를 하나로 합친 그리드**이며, 그리드 안의 **행 범위 하나를 반복 구간**으로 지정해 데이터 배열만큼 복제한다.
  - 행 높이·열 너비는 **mm 절대값**. 요소의 `width`·`height`는 그 합이다.
  - 한 페이지에 담는 반복 항목 수(`perPage`)를 양식이 정한다. 넘치면 다음 페이지로 잇고, 적으면 **남는 칸을 빈 줄(괘선 포함)로 그린다**. 이어지는 페이지에 헤더를 다시 그릴지 `repeatHeader`로 정한다.
  - 칸보다 긴 글은 **낱말 단위로 줄바꿈**하고, 칸 높이를 넘는 부분은 `overflow`로 고른다: `clip`(기본) 또는 `shrink`(글자 크기 축소).
  - 셀은 `content`·`parameter`·`formula`를 가질 수 있고, 반복 구간 안에서는 항목의 필드를 이름 그대로 읽는다.
  - PDF 변환은 반복 구간을 펼쳐 **선·사각형·글자로 분해**한다 — 하부 엔진의 표 기능을 안 쓰므로 **페이지 분할도 우리가 계산**한다.
- **근거**:
  - **하부 엔진의 표는 열별 제어가 사실상 없다** — 열 단위로 받는 것이 너비·정렬 둘뿐이고 그 정렬조차 헤더·본문에 동시에 걸려 "헤더만 가운데"가 안 된다. 2단 헤더(칸 합치기)도 구조적으로 불가능(엔진 소스 확인).
  - **엔진의 페이지 분할은 확장할 수 없다** — 분할 여부가 스키마 `type` 이름에 박혀 있다(같은 표를 새 타입으로 바꾸자 80행이 2쪽→1쪽으로 잘림). 타입을 유지한 채 그리기만 가로채도 행 높이를 바꾸는 변화(열별 글자 크기·셀 병합·쪽 소계)는 엔진 분할 계산과 어긋난다.
  - 고정 그리드는 **이미 우리가 선·사각형·글자로 분해해 그리고 있다**(셀별 스타일·병합·셀별 테두리 ADR-033 포함). 반복만 얹으면 막혀 있던 것이 한꺼번에 열린다.
  - 행 높이를 고정하면 **페이지 분할이 계산이 아니라 분배**가 된다 — 자리가 고정된 전표 양식에 더 맞다. 반복 구간을 여러 행으로 잡으면 한 항목이 여러 행짜리 블록(등록번호·상호 / 성명·주소)이 되어 실제 전표에서 자주 쓰는 모양이 표현된다.
- **기각**:
  - 엔진 표의 타입 이름 유지+그리기만 교체(분할은 공짜로 남지만 병합·중첩·소계가 계속 불가), 엔진 기여·포크(반영 시점이 통제 밖, 포크는 유지보수 부담), 행 높이를 내용에 따라 늘리기(페이지 분할이 다시 계산 문제 — 전표는 줄 수가 정해진 양식이 많아 잃는 것이 작다), 행 높이 비율(%)(반복으로 행 수가 달라지면 기준을 잃음).
- **마이그레이션**: 고정 그리드는 반복 없는 그리드로, 동적 표는 헤더 1행 + 반복 1행 그리드로 옮긴다. 비율(%) 트랙은 상자 기준 mm로 환산하고 마지막 트랙이 반올림 오차를 흡수한다. **반복 구간 칸의 `parameter`는 전표 값 키가 아니라 항목 필드**라 값 목록에서 최상위로 올리지 않고 그리드 하위 줄로만 보인다.

## ADR-038: 데이터 자동 병합 — 이어지는 같은 값을 세로로 합친다

- **결정**:
  - 그리드 열에 `autoMerge`를 둔다. 켜면 그 열의 **반복 구간 칸이 앞 벌과 값이 같을 때 세로로 합쳐진다.**
  - 제어는 **열별**(`columns[i].autoMerge`)이고 기본 꺼짐. 반복 구간 밖(헤더·꼬리)은 영향 없다.
  - 규칙 셋: ① 앞 벌 같은 열과 값이 같으면 병합을 늘린다, ② **페이지가 바뀌면 끊고 값을 다시 쓴다**, ③ **빈 값은 합치지 않는다.**
  - 그 열의 반복 구간 칸이 **구간 전체 높이를 차지할 때만** 켤 수 있다(아니면 스키마 거부).
- **근거**:
  - **실제 수요는 표 중첩이 아니라 묶어 보이기였다** — 한 열의 값이 이어지는 목록(상품별 주문자 등)을 묶는 것이지 칸 안에 다른 표를 넣는 것이 아니다.
  - **그리드의 성질을 지킨다** — 항목 수도 행 높이도 안 바꾸므로 페이지 분할이 여전히 "분배"다(ADR-037). 반복 펼치는 루프에서 앞 벌과 값을 견줘 세로 병합만 늘린다.
  - **페이지 경계에서 값을 다시 쓰는 것이 핵심** — 호스트가 이어지는 값을 비워 넣어도 페이지가 갈리면 새 페이지 첫 줄이 어느 묶음인지 알 수 없다. 그리는 쪽이 묶음을 알아야 고칠 수 있다.
  - **열별이 맞는 단위** — 통째로 켜면 수량 열의 `2`와 `2`가 우연히 같다고 합쳐져 전표가 틀린다. 합칠 열은 사람이 지정한다.
- **기각**: 표 중첩(항목 높이 가변 → 페이지 분할이 다시 계산, 실제 수요 미확인), 묶음 소계 행(같은 이유 — 반복 없는 그리드로 우회), 호스트가 값 비워 넣기(페이지 경계에서 묶음 이름 사라짐), 칸별 제어(결과는 열별과 같고 설정 자리만 늘어남).

## ADR-039: VLOOKUP류 수식 함수를 넣지 않는다

- **결정**: 범위 검색(VLOOKUP류) 함수를 넣지 않는다. 실제로 막히는 양식이 나오면 그때 다시 판단하되, 그때 필요한 것이 이 함수가 아닐 수 있다.
- **근거**:
  - **상정한 쓰임이 없었다** — ADR-017에서 사유 없이 미뤄진 뒤 세 번 이월됐다. 어느 전표 어느 자리에서 필요한지가 한 번도 적히지 않았다.
  - **전표는 이미 확정된 데이터를 그린다** — 조회표가 올 곳 셋이 전부 막힌다: ① 전표 데이터는 반복 구간이 이미 한 줄씩 훑고, ② 조회표를 넘길 수 있다면 그 값을 항목에 직접 넣으면 되며(결합은 DB 쪽 일), ③ 양식에 조회표를 담을 자리가 포맷에 없다.
  - **함수 하나가 아니라 값 모델 확장이다** — `FormulaValue`에 표(2차원·레코드) 개념이 없어 넣으려면 파서·평가기·오류·도움말이 전부 따라온다.
  - 구간별 요율 같은 규칙은 지금도 `IF` 중첩으로 되고, 전표 구간은 보통 2~3단이라 감당된다.
- **기각**: 그대로 두고 나중에 판단(근거 없이 남은 항목은 착수 판단을 매번 흐림), 양식에 상수표 자리부터 만들기(별도 설계 건, 수요 미확인).

## ADR-040: 폰트·용지 자원을 호스트 인터페이스로 공급받는다

- **결정**:
  - 렌더 폰트를 **읽기 전용 공급 인터페이스**로 받는다: `SlipFontProvider { getFonts(): Font[] | Promise<Font[]> }`. 뷰어·작성폼·디자이너 **세 컴포넌트 공용**이며 기존 `fonts` 배열 속성을 대체한다.
  - 디자이너는 그 위에 용지 설정을 더한다: `SlipDesignerSettings extends SlipFontProvider { getPaperSizes?(); savePaperSize?(size) }`. 용지 목록 공급은 읽기, 사용자가 입력한 용지 보관은 쓰기다.
  - **폰트 업로드(디자이너에서 파일 추가)는 넣지 않는다** — 업로드한 폰트도 보관 위치가 호스트 몫이라(ADR-021과 같은 이유) `getFonts` 공급만 둔다.
- **근거**:
  - **공급은 pull이라 인터페이스가 맞다** — 서버 폴더 등에서 비동기로 받아 와야 하므로 Promise 메서드가 이벤트보다 자연스럽다. 용지는 사용자가 입력한 것을 되돌려 보관하므로 `savePaperSize`(쓰기)를 둔다.
  - **저장 위치는 라이브러리가 정할 수 없다** — core는 I/O가 없고(ADR-002) 저장 매체는 호스트마다 다르다(ADR-003). 공급 인터페이스로 두면 위치 결정이 호스트로 넘어간다.
  - **용지 목록은 포맷과 무관** — 실제 크기는 늘 `.slip`의 `paper`에 담겨 효력을 갖고, 인터페이스는 고르개 후보·기억만 담당한다(포맷 불변).
- **기각**: 이벤트+속성(밀어내기만 되고 "돌려받는" 경우를 못 담음), `.slip` 저장소 어댑터에 폰트·용지 합치기(관심사가 섞이고 기존 구현 2종이 안 쓰는 메서드를 떠안음), 디자이너 폰트 업로드+내부 저장(보관 위치를 라이브러리가 못 정함).

## ADR-041: v2 3단계 축소 — 파일 암호화 제외, 페이지 소계·프리셋 확충 보류

- **결정**: ① 파일 암호화(ADR-009 옵션): **넣지 않는다**(위변조 방지 서명은 그대로). ② 페이지마다 소계(ADR-011 미이행분): **보류**. ③ 동봉 프리셋 확충: **보류**.
- **근거**: 세 항목 모두 "있으면 좋다" 수준이고 어느 전표 어느 자리에서 꼭 필요한지가 적히지 않았다(ADR-039와 같은 기준). 암호화는 열쇠 관리·봉투 구조·호환 문제를 떠안는데 임베드형 라이브러리에서는 호스트가 자기 전송 계층에서 처리하는 편이 낫다. 소계는 반복 없는 그리드로 우회된다(ADR-037). 프리셋은 `presets` 주입으로 호스트가 자기 양식을 넣을 수 있어 동봉 확충의 값이 작다.

## ADR-042: 일본어(ja) 대응 — 기본 일본어 폰트 동봉 + 대자 함수 미도입

- **결정**:
  - **UI 언어에 일본어(`ja`)를 더한다** — `SlipLocale`을 `'ko'|'en'|'ja'`로 넓히고 `ja` 사전을 채운다.
  - **기본 일본어 폰트 1종을 동봉한다** — Noto Sans JP **Regular** 한 두께. `locale="ja"`이고 `getFonts`가 없으면 자동으로 쓴다. 서브패스(`@omdc-slipkit/elements/fonts/noto-sans-jp`)로 동적 import해 일본어를 안 쓰는 번들에는 안 들어간다. **더 넓은 글자·굵기는 `getFonts`(ADR-040)로 공급.**
  - **금액을 한자 숫자로 적는 함수는 넣지 않는다**(대자·상용 한자 모두) — `NUMBER_TO_KOREAN`은 한글 전용 그대로. 수요가 확인되면 ADR-017을 개정한다.
  - 수식 포맷 로케일은 BCP-47이라 `ja-JP`가 코드 변경 없이 된다. 동봉 프리셋 내용은 한국어 고정(일본어 양식은 `presets`로).
  - **문서는 한국어·영어·일본어 3벌**이 된다(가이드 5종 + 리포 README). 한 벌을 고칠 때 나머지도 함께 고친다.
- **근거**:
  - **바로 쓸 수 있어야 기본값이다** — Pretendard는 가나·한자 글리프가 없어 일본어가 두부(□)로 나온다. 언어만 바꿔도 렌더되려면 그 언어 글자를 담은 기본 폰트가 있어야 한다.
  - **동봉과 공급의 분담** — 전부 동봉하면 용량이 크고 전부 공급에 맡기면 기본 상태가 깨진다. "기본 Regular 하나 동봉 + 나머지는 `getFonts`"가 둘을 만족한다.
  - **가변 폰트 인스턴싱본은 임베드가 깨진다** — @pdfme/pdf-lib의 CID 임베더가 못 받았다. Google Fonts의 **정적** TTF를 서브셋했더니 렌더가 통과했다(직접 확인, 재생성은 `scripts/generate-noto-sans-jp.mjs`).
  - **대자는 수요가 불확실**해 "자리가 비어 보인다고 채우지 않는다"(CLAUDE.md)에 따라 뺀다 — 넣더라도 순증분이다.
- **기각**: 일본어 폰트 미동봉·전적 `getFonts`(기본 상태에서 일본어 깨짐), 모든 두께·전 글자 동봉(용량 과다), 가변 폰트 그대로 동봉(임베더 비호환).

## ADR-043: 뷰어가 발행 전표 무결성을 로드 시 검증한다 (fail-closed)

- **결정**:
  - `<slip-viewer>`는 **발행(issued) 전표를 로드할 때 `verifyIntegrity`를 호출**한다 — 해시를 재계산하고, 공개키(`verificationKey`)가 주어지면 서명까지 확인한다.
  - 검증에 실패하면 **PDF를 그리지 않고 오류를 표시**한다(fail-closed).
  - 뷰어·react·vue에 **`verificationKey`(공개키 JWK) 속성**을 더한다. 서명이 있는데 키가 없으면 검증 실패로 처리한다.
- **근거**: `verifyIntegrity`가 export만 되고 로드 경로에 **연결돼 있지 않아** 위조된 issued 전표(값을 고치고 아무 64-hex 해시를 넣은 것)가 그대로 그려졌다. 해시 재계산은 키 없이도 순진한 변조를 잡고, 서명 검증은 공개키가 있어야 진위까지 보증한다. 검증 실패 문서를 화면에 그리는 것은 위험하므로 fail-closed다.
- **영향**: 작성폼(`<slip-form>`)은 이번 범위에 넣지 않았다(편집 흐름이라 로드 검증의 값이 뷰어보다 작다). core `verifyIntegrity` API는 그대로.
- **기각**: 검증 실패 시 경고만 띄우고 PDF는 그리기(변조 문서를 진본처럼 보일 위험).

## ADR-044: 수식 엄격 타입 + 타입 변환 함수(TO_NUMBER·TO_STRING·TO_DATE)

- **문제**: 산술(`+ - * /`·`SUM` 등)은 숫자 문자열을 자동으로 수로 바꾸는데 `=`·`<>`는 엄격 비교라, `A > 3`은 되고 `A = 3`은 타입이 다르면 어긋나 헷갈렸다. 자동 변환은 실패할 수 있는 변환(글자→숫자)을 조용히 넘겨 오류를 늦게 드러냈다.
- **결정**:
  - **숫자를 요구하는 자리는 숫자만 받는다** — 산술·`SUM`·`AVG`·`ROUND`·`VAT` 등에서 문자열 자동 변환을 없앤다. 빈 값(`null`)은 0으로 본다(미입력=0). 비어있지 않은 비숫자 문자열은 오류.
  - **글자를 요구하는 자리는 숫자·논리를 자동 글자화**한다(손실 없는 변환만 자동) — `CONCAT`·`LEFT` 등은 그대로. *위험한 변환(글자→숫자)만 명시, 안전한 변환(숫자→글자)은 자동*이 규칙이다.
  - **타입 변환 3종 추가**: `TO_NUMBER`(글자·논리→수, 빈 값=0), `TO_STRING`(수·논리→글자), `TO_DATE`(날짜 검증→`YYYY-MM-DD`). 29→32종.
  - **`number` 파라미터의 빈 값은 받는 시점에 0으로 정규화** — core `normalizeNumericParameters`를 두고 렌더 진입점과 작성폼이 함께 써(SSOT) 미리보기·PDF·뷰어가 같은 값을 본다. 최상위 파라미터만 다룬다.
- **근거**: 규칙이 하나(숫자 자리엔 숫자)면 배우기 쉽고 자동 변환 분기가 없어져 코드가 준다. 실패할 수 있는 변환만 `TO_NUMBER`로 드러내 오류를 이른 자리에서 잡는다. 빈칸을 0으로 다루는 것은 회계 양식 관례에 맞다. (저장된 전표가 없는 시점이라 마이그레이션 없이 동작을 바꾼다.)
- **범위**: 편집 시점 정적 타입 검사·그리드 열 종류는 이번에 넣지 않는다 — 엄격 런타임은 정적 검사의 부분집합이라 재작업 없이 위에 얹을 수 있다.
- **기각**: 모든 자리 자동 변환(실패 변환을 조용히 넘김), 지금의 불일치 유지, 숫자→글자도 명시 요구(흔한 "숫자+단위"가 성가심).

## ADR-045: IndexedDB 저장소 — 본문 Blob 분리 + 화면 스냅샷 페이징

- **문제**: `list()`가 `getAll()`로 **본문(base64 이미지 포함)까지 통째로** 메모리에 올렸다(목록엔 제목만 필요). "커서"가 오프셋 숫자라 페이지 사이 저장·삭제 시 목록이 밀려 **항목이 중복·누락**됐다.
- **결정**:
  - **본문을 `Blob`으로 저장**한다(메타 `id·kind·title·updatedAt`은 같은 레코드의 형제 필드). IndexedDB는 Blob을 **느긋한 핸들**로 돌려주므로 `list()`가 메타만 읽으면 본문 바이트가 메모리에 안 올라온다. 열 때만 그 레코드의 Blob을 읽는다.
  - **한 레코드에 메타+본문을 함께** 둔다(별도 store로 안 쪼갬) — "목록에 뜨는 것은 반드시 열린다"는 불변식이 유지되고 orphan이 구조적으로 안 생긴다.
  - **목록 모달은 열 때 전체 메타를 한 번 받아 스냅샷으로 쥐고** 검색·번호 페이지 이동을 메모리로 한다 — 페이지 사이 저장·삭제가 있어도 창이 안 흔들려 중복·누락이 사라진다("더 보기"를 1234 번호 페이지로).
  - **열 때 본문이 손상돼 파싱에 실패하면** 크래시 대신 오류를 표시한다(파일은 목록에 남아 지울 수 있음).
  - **마이그레이션**: DB v1→v2, 옛 문자열 본문을 `onupgradeneeded`에서 Blob으로. `load()`는 옛 문자열도 받아들인다.
- **근거**: Blob 분리는 목록을 가볍게 하면서도 한 레코드라 무결성을 지킨다. 스냅샷 페이징은 오프셋 재조회의 중복·누락을 없애고, 메타가 가벼워 전량을 한 번 받아도 부담이 없으며 1234 임의 점프가 된다.
- **범위**: 다른 저장 환경(서버·오브젝트 스토리지)은 "목록=메타"를 더 쉽게 지원한다 — 인터페이스가 `list`(메타)·`load`(본문)로 감싸므로 이 결정은 IndexedDB 구현에 한정된다.
- **기각**: 메타/본문 두 store 분리(orphan·"목록엔 있는데 안 열림"이라는 새 실패 모드), keyset 커서 페이징(안정적이나 1234 임의 점프 불가), `.slip`을 zip 컨테이너로(포맷·서명·사람이 읽는 JSON까지 흔들려 범위 과다).

## ADR-046: 공개 전 스키마 버전 재정리 — 개발 단계 버전을 첫 버전 0.1.0으로 합침

- **문제**: 개발 단계에서 포맷을 여러 번 고치며 `schemaVersion`이 `0.1.1`→…→`0.5.0`까지 올라갔으나, 이 버전들은 **어디에도 공개된 적이 없고**(npm 미배포, 저장된 전표 0건) 마이그레이션 계층은 쓸 일 없는 개발 이력만 담았다. 첫 공개가 `0.5.0`이면 겪은 사용자가 없는데 번호만 부풀어 오해를 준다.
- **결정**:
  - 지금까지 만든 스키마(내용 그대로)를 **첫 버전 `0.1.0`**으로 다시 이름 붙인다(롤백이 아니라 라벨 변경).
  - **마이그레이션 계층을 비운다**(`BUILT_IN_MIGRATIONS = []`) — 공개된 옛 버전이 없어 변환 대상이 없다. JSON Schema는 `0.1.0` 하나만 남긴다. 마이그레이션 기계(`migrateSlipDocument`)는 미래를 위해 그대로.
  - **공개(안정 릴리스) 버전은 `1.0.0`부터**. npm 패키지 버전은 `schemaVersion`과 별개라 손대지 않는다.
- **근거**: 저장된 전표가 0건이고 공개된 적이 없어 마이그레이션을 유지할 값이 없다. 번호를 부풀리지 않고 `0.1.0`에서 시작해 `1.0.0` 안정 릴리스로 가는 통상 흐름을 따른다.
- **문서 처리**: 규범 문서(SPEC·코드·JSON Schema·가이드)는 `0.1.0`으로 맞춘다. 이 로그의 옛 ADR(031/032/037 등)에 남은 `0.2.0`~`0.5.0` 표기는 **개발 반복을 가리키는 기록**일 뿐 릴리스 버전이 아니다.
- **기각**: `0.5.0` 그대로 공개(겪은 사람 없는 이력을 짊어짐), 첫 공개를 `1.0.0`으로(아직 안정 보장 단계가 아님).

## ADR-047: 파라미터 정의부가 하위 필드까지 담는다 — 그리드 종속을 끊는다

- **문제**: 사용자 인수 검토에서 "파라미터와 요소를 결국 분리해내지 못했다"는 지적이 나왔고, 코드로 확인한
  결과 셋이 사실이었다.
  - **하위 필드를 만들 방법이 없었다.** 목록(반복 구간)의 항목 필드는 정의부에 자리가 없어 **그리드
    반복 구간 칸에서 역산**됐다 — 그리드를 먼저 만들어야만 하위 필드가 생기는 구조였다.
  - **값 종류를 지정할 화면이 없었다.** `valueType`은 스키마에 있었으나 변동 이미지를 만들 때
    `'image'`로 자동 등록되는 경로 하나뿐이라, 사용자가 `number`·`date`를 고를 방법이 없었다.
    ADR-044가 런타임 엄격 타입을 넣었지만 **종류를 정할 자리가 없어** 실효가 없었다.
  - **값 고르는 자리가 제각각이었다.** 필드 요소만 선택 상자로 유도하고 그리드 칸은 자유 입력이라
    오타가 그대로 들어갔다.
- **결정**:
  - **정의부(`parameters`)가 하위 필드의 단일 원천**이 된다 — `{ key, label?, valueType?, fields? }`.
    `fields`는 `valueType: 'list'`에서만 두며 항목 하나가 가진 값을 `{ key, label?, valueType? }`로
    선언한다. **그리드 없이도** 사이드바·패널에서 만들고 고칠 수 있다.
  - **하위 필드는 다시 하위를 갖지 않는다** — 반복 구간이 읽는 것은 평평한 객체 배열뿐이다(ADR-038).
  - **값 종류를 패널에서 고른다** — 최상위는 6종, 하위 필드는 목록을 뺀 5종(칸 하나에 목록을 담을 수 없다).
    종류를 목록이 아닌 것으로 바꾸면 하위 필드를 함께 정리해 스키마가 거부하는 조합을 남기지 않는다.
  - **값을 고르는 자리는 전부 선택 상자**로 한다. 그리드 칸은 자리에 따라 후보가 갈린다 — 반복 구간
    **안**은 그 구간이 쓰는 목록의 `fields`, **밖**은 최상위 파라미터(목록 제외). 목록에 없는 값을
    고를 수 없으니 오타가 구조적으로 안 생긴다.
  - **하위 필드를 고르면 요소가 아니라 그 필드가 편집된다** — 그 필드를 읽는 칸이 있으면 「쓰는 곳」으로
    보이되 **자동 연결하지 않는다**(ADR-034의 요소·파라미터 분리를 하위 필드까지 관철).
  - **반복 구간이 쓰는 값은 목록으로 등록**한다 — 그래야 하위 필드를 선언할 수 있다.
- **호환**: `fields`는 선택 필드이며, 정의부에 없는데 칸이 쓰고 있는 필드는 목록에 "정의부에 없음"으로
  **그대로 보인다** — 옛 파일이 값을 잃지 않는다.
- **버전**: 선택 필드 추가라 **0.1.0을 유지**한다. 0.1.0은 아직 공개된 적이 없어(ADR-046) 버전 번호가
  호환성 의미를 갖지 않으며, 여기서 올리면 ADR-046이 없앤 "겪은 사람 없는 버전 이력"이 되살아난다.
  첫 공개 전까지의 순증분 변경은 0.1.0 안에서 흡수하고, 공개 시점에 1.0.0으로 확정한다.
- **기각한 대안**: ⓐ 하위 필드를 그리드 칸에서 계속 역산 — 그리드를 만들어야만 값이 생기고, 칸을 지우면
  값 정의도 사라진다 · ⓑ 하위 필드에 다시 하위를 허용(중첩 목록) — 반복 구간이 평평한 배열만 읽으므로
  (ADR-038) 그릴 수 없는 구조를 파일에 담게 된다 · ⓒ 그리드 칸 값 입력을 자유 입력으로 두고 검사만 추가 —
  오타를 사후에 알려 주는 것보다 고를 수 없게 하는 편이 낫다.

## ADR-048: 화면이 정하는 범위 — 바코드 종류 공급, 반복 항목 수 상한

- **문제**: 사용자 인수 검토에서 나온 둘 다 "라이브러리가 전부 열어 두고 호스트가 줄일 수단이 없다"는
  같은 모양이었다.
  - **바코드 종류 12종이 항상 전부** 보였다. 하부 엔진이 그릴 수 있는 것을 그대로 연 뒤 화면 노출
    범위를 정하지 않고 넘어가, 대부분의 호스트에 필요 없는 선택지가 늘어서 있었다.
  - **반복 구간이 그릴 항목 수에 상한이 없었다.** 전표가 준 항목 수만큼 페이지가 늘어나므로,
    양식이 "이 표는 최대 30줄"이라고 정할 방법이 없었다.
- **결정**:
  - **바코드 종류는 호스트가 좁힌다** — `SlipDesignerSettings.getBarcodeKinds?()`. 폰트·용지와 같은
    공급 인터페이스이며(ADR-040), 주지 않거나 빈 배열이면 12종을 모두 보인다. 이미 파일에 든 종류는
    목록에 없어도 고르개에 남긴다(열었다가 값을 잃지 않게).
  - **반복 항목 수 상한은 양식이 정한다** — `repeat.maxItems`(선택). 넘는 항목은 그리지 않고 페이지도
    늘리지 않는다. `perPage` 이상이어야 하며 상한은 100,000이다. 정하지 않으면 지금처럼 항목 수만큼
    페이지가 늘어난다.
- **근거**:
  - **고르개의 범위는 호스트 사정이다.** 어떤 바코드를 쓰는지는 설치한 곳마다 다르고, 라이브러리가
    정할 수 없다 — 폰트·용지에서 이미 같은 결론에 이르렀다(ADR-040).
  - **상한은 양식의 성질이다.** 자리가 정해진 전표 양식에서 "표가 몇 줄까지"는 데이터가 아니라 양식이
    아는 값이다. 전표 데이터가 많다고 페이지가 무한히 늘면 인쇄물이 의도와 달라진다.
  - 둘 다 **선택**이라 정하지 않으면 지금 동작 그대로다 — 기존 파일·호스트가 영향을 받지 않는다.
- **버전**: 선택 필드 추가라 **0.1.0을 유지**한다(ADR-047과 같은 이유 — 첫 공개 전이라 버전 번호가
  호환성 의미를 갖지 않는다).
- **기각한 대안**: ⓐ 바코드 종류를 코드에서 줄이기 — 어느 호스트에 무엇이 필요한지 라이브러리가 모른다 ·
  ⓑ 상한을 전역 상수로 — 양식마다 줄 수가 다르므로 양식이 정하는 것이 맞다 · ⓒ 상한을 넘으면 오류 —
  전표 데이터가 많다고 발행이 막히면 곤란하다. 그리지 않고 넘기는 편이 낫다.

## ADR-049: 필드의 값 소스도 배타로 — 파라미터와 수식 중 하나

- **문제**: 필드는 `parameter`가 필수이고 `formula`가 선택이라 **둘을 함께 둘 수 있었다.** 그런데 렌더는
  수식이 있으면 수식만 쓰고 파라미터는 무시한다. 화면에는 둘이 나란히 있어 파라미터가 표시에 쓰이는
  것처럼 보였고, 실제로는 아무 일도 하지 않았다. 그리드 셀·바코드는 이미 `content·parameter·formula`
  **하나만** 갖도록 검사하는데 필드만 예외였다.
- **결정**:
  - 필드의 값 소스를 **`parameter` XOR `formula`**로 한다 — 그리드 셀·바코드와 같은 규칙. 둘 다 있거나
    둘 다 없으면 파일을 거부한다.
  - 디자이너는 그리드 셀과 같은 **값 소스 고르개**를 둔다(파라미터 | 수식). 소스를 바꾸면 반대쪽 값은
    지운다.
  - **수식만 쓰는 필드는 전표 값의 키가 아니다** — 작성폼은 입력을 내지 않고 계산 결과만 보여준다
    (줄 식별자는 요소 id, 이름은 요소 이름).
  - 빈 수식(`''`)은 **빈 글로 그린다** — 소스를 수식으로 막 바꿔 아직 아무것도 안 쓴 상태에서
    파싱 오류로 미리보기가 깨지지 않게 한다.
- **근거**: 같은 자리에 같은 규칙을 쓴다. 무엇이 쓰이는지 화면만 보고 알 수 있어야 하며, 안내 문구를
  덧붙여 설명할 일이 아니라 **애초에 둘을 함께 둘 수 없게** 하는 것이 맞다.
- **영향**: 동봉 프리셋의 합계 필드가 수식만 갖도록 바뀐다(파라미터 `totalAmount`는 정의부에 남아
  작성폼에서 따로 채울 수 있다). 선택 필드를 필수에서 선택으로 바꾸는 것이라 기존 파일은 그대로 읽히되,
  둘을 함께 가진 파일은 거부된다 — 공개 전이라 그런 파일은 없다.
- **기각한 대안**: ⓐ 화면에 "수식이 우선입니다" 안내 붙이기 — 구조가 헷갈리는 것을 설명으로 덮는 것이라
  근본 해결이 아니다 · ⓑ 수식을 파라미터의 가공식으로 두고 둘 다 유지 — 그러면 파라미터 값이 실제로
  쓰여야 하는데 렌더가 그러지 않으며, 그리드 셀 규칙과도 어긋난다.

## ADR-050: 선은 길이·각도로 편집한다 (저장 형식은 그대로)

- **문제**: 선의 편집 화면이 방향에 따라 달라졌다 — 곧은 선은 `길이`, 사선은 `너비·높이`. 같은 요소인데
  방향을 바꾸면 셀 구성이 통째로 바뀌어 값이 튀는 것처럼 보였고, 어느 값을 고쳐야 하는지도 매번 달랐다.
- **결정**: 선은 방향과 무관하게 **`길이`·`각도`·`선 굵기`** 셋으로 편집한다. 각도는 0°가 오른쪽,
  90°가 아래(화면 좌표계 시계 방향)다. 0·90·180·270°에 ±0.5° 이내면 곧은 선으로 맞춘다.
- **저장 형식은 바꾸지 않는다** — 파일에는 지금처럼 상자(`width`·`height`) + `lineDirection`으로
  담기고(ADR-032), 화면이 그 사이를 오간다. 캔버스의 끝점 핸들 조작도 그대로다.
- **근거**: 사람이 선을 다룰 때 떠올리는 것은 "어디서 시작해 얼마나 어느 쪽으로"이지 상자가 아니다.
  화면 표현과 저장 형식을 분리하면 포맷을 흔들지 않고 조작만 일관되게 만들 수 있다.
- **기각한 대안**: ⓐ 좌표 2개(시작·끝)로 저장 형식까지 바꾸기 — 요소 공통 `position`·`width`·`height`와
  정보가 중복돼 불일치 여지가 생긴다(ADR-032에서 이미 기각) · ⓑ 방향별로 셀을 다르게 두기(지금까지의
  방식) — 같은 요소인데 화면이 바뀌어 헷갈린다.

## ADR-051: 포맷 키·코드 식별자도 `parameter`으로 통일 (옛 `binding`)

- **문제**: 용어를 `바인딩`→`파라미터`로 바꿀 때(ADR-047, USER-ACCEPTANCE-REVIEW) UI 문구·문서만
  바꾸고 `.slip` 포맷 키와 코드 식별자는 `binding`으로 남겨 뒀다. 화면·문서는 "파라미터", 파일·코드는
  "binding"으로 갈라져, 파일을 열어 보거나 코드를 읽을 때 같은 것을 두 이름으로 부르게 됐다.
- **결정**: 포맷 키와 코드 식별자도 `parameter`으로 맞춘다.
  - **포맷 키**: 양식 본문의 `bindings[]` → `parameters[]`, 요소·셀·반복 구간의 값 키 `binding` →
    `parameter` (텍스트를 제외한 필드·이미지·바코드·그리드 셀·`repeat`).
  - **코드 식별자**: `BindingDef`→`ParameterDef`, `BindingField`→`ParameterField`,
    `BindingValueType`→`ParameterValueType`, `normalizeNumericBindings`→`normalizeNumericParameters`,
    `SLIP_LIMITS.maxBindings`→`maxParameters` 등.
- **버전은 0.1.0 그대로** (ADR-046) — 공개된 파일도 저장된 전표도 없어 마이그레이션 부담이 없다.
  옛 키를 받아 주는 계층은 두지 않는다. SPEC·JSON Schema·타입·테스트를 함께 고쳤다.
- **근거**: 코드 식별자는 영어를 쓰되(CLAUDE.md 「언어」) 특정 영어 단어를 강제하지는 않는다 —
  `binding`→`parameter`는 영어→영어 정리라 규칙과 무관하고, 화면·문서와 이름이 하나로 모인다.
  공개 전이 이 정리를 부담 없이 할 수 있는 마지막 시점이다.
- **기각한 대안**: ⓐ 포맷 키만 두고 코드만 바꾸기 — 파일을 열면 여전히 `binding`이 보여 갈라짐이
  남는다 · ⓑ 그대로 두기 — 공개 뒤에는 배포된 파일 때문에 바꾸기 어려워진다.
