## 문서 원칙

ADR 번호는 코드와 다른 문서에서 참조할 수 있는 안정적인 식별자입니다.

- 채택한 결정은 삭제하지 않습니다.
- 결정이 바뀌면 기존 기록을 남기고 새 ADR에서 대체합니다.
- 사용하지 않게 된 번호도 다른 결정에 다시 사용하지 않습니다.
- 구현 세부사항보다 결정 당시의 문제, 선택한 방향과 이유를 기록합니다.

> [!IMPORTANT]
> `DECISIONS.md`는 결정의 이유와 변경 이력을 설명하는 문서입니다.
>
> 실제 요구사항, 공개 API, 파일 형식은 각각 `REQUIREMENTS.md`, API 문서와 `SPEC.md`를 기준으로 확인해야 합니다. 문서끼리 어긋나는 경우 어느 한 문서를 조용히 우선하지 않고, 관련 문서를 함께 고쳐 일관성을 회복해야 합니다.

## ADR-001: 전표를 범용 양식 엔진으로 정의한다

**상태:** 채택

### 맥락

SlipKit은 거래명세서, 청구서, 견적서와 같은 문서형 전표뿐 아니라 차변과 대변을 다루는 회계형 전표도 표현해야 합니다. 특정 서식이나 업무에 구조를 고정하면 다른 전표를 지원할 때마다 별도 기능이 필요합니다.

### 결정

전표를 특정 업무 서식이 아닌 범용 양식 엔진으로 정의합니다.

양식과 전표 데이터는 분리하며, 하나의 양식으로 여러 전표를 작성할 수 있게 합니다.

### 근거

자유로운 레이아웃과 쉬운 작성 경험을 함께 제공하려면 업무별 전용 구조보다 양식과 데이터가 분리된 범용 구조가 적합합니다.

### 기각한 대안

- 문서형 전표에 한정: 회계형 전표를 표현하기 어렵습니다.
- 회계 분개에 한정: 자유로운 인쇄 레이아웃 요구를 충족하지 못합니다.

## ADR-002: 임베드형 라이브러리와 계층형 모노레포를 사용한다

**상태:** 채택

### 맥락

SlipKit은 자체 서버나 사용자 계정을 가진 독립 서비스보다, 기존 업무 시스템에 포함해 사용하는 도구여야 합니다. 동시에 파일 검증과 렌더링 같은 핵심 기능은 브라우저 UI와 분리할 필요가 있습니다.

### 결정

SlipKit을 호스트 애플리케이션에 포함하는 임베드형 라이브러리로 제공합니다.

패키지는 다음 계층으로 분리합니다.

- `core`: 스키마, 파싱, 검증, 마이그레이션, 수식, 레이아웃과 PDF 렌더링
- `elements`: Web Component 기반 UI
- `react`: React용 얇은 래퍼
- `vue`: Vue용 얇은 래퍼

`core`는 DOM과 UI 프레임워크에 의존하지 않는 TypeScript 코드로 유지합니다.

### 근거

핵심 로직을 UI에서 분리하면 브라우저뿐 아니라 Node.js 기반 검증, 렌더링과 자동화에서도 재사용할 수 있습니다.

### 기각한 대안

- 서버를 포함한 풀스택 제품: 호스트의 인증·저장 구조와 중복됩니다.
- 독립 실행 애플리케이션: 기존 시스템에 포함한다는 목표와 맞지 않습니다.

## ADR-003: Web Component와 프레임워크별 얇은 래퍼를 제공한다

**상태:** 채택

### 맥락

호스트 애플리케이션은 React, Vue 또는 다른 프레임워크를 사용할 수 있습니다. 특정 프레임워크 전용 UI만 제공하면 사용할 수 있는 환경이 제한됩니다.

### 결정

UI는 `slip-*` 커스텀 엘리먼트로 제공합니다.

React와 Vue 패키지는 Web Component를 각 프레임워크의 사용 방식에 맞게 연결하는 얇은 래퍼로 유지합니다.

### 근거

Web Component는 프레임워크와 독립적으로 배포할 수 있으며, 래퍼를 이용하면 각 프레임워크 사용자도 익숙한 방식으로 사용할 수 있습니다.

### 기각한 대안

- React 전용 구현: 다른 프레임워크에서 직접 사용할 수 없습니다.
- 프레임워크별 독립 구현: 기능과 버그 수정이 여러 구현으로 분산됩니다.

## ADR-004: 인증과 권한은 호스트가 제어한다

**상태:** 채택

### 맥락

SlipKit은 여러 애플리케이션에 포함되는 라이브러리입니다. 사용자와 역할, 접근 정책은 호스트마다 다르므로 라이브러리가 공통 권한 모델을 정의하기 어렵습니다.

### 결정

SlipKit은 자체 사용자, 로그인과 권한 시스템을 제공하지 않습니다.

호스트 애플리케이션이 사용자의 권한을 판단하고, 허용된 화면과 컴포넌트만 노출합니다. SlipKit 컴포넌트의 표시 여부를 보안 경계로 사용하지 않습니다.

### 근거

호스트가 이미 가진 인증·권한 체계와 중복되지 않으며, 라이브러리가 특정 보안 모델을 강요하지 않습니다.

### 기각한 대안

- SlipKit 자체 권한 시스템: 호스트의 인증 구조와 충돌하거나 이중 관리가 발생합니다.
- 컴포넌트 속성만으로 권한 제어: UI 상태는 신뢰할 수 있는 보안 경계가 아닙니다.

## ADR-005: 비개발자를 위한 GUI 디자이너를 핵심 기능으로 제공한다

**상태:** 채택

### 맥락

SlipKit의 양식 제작자는 개발자가 아닐 수 있습니다. JSON을 직접 작성하거나 코드로 레이아웃을 구성해야 한다면 범용 양식 엔진의 활용 범위가 크게 줄어듭니다.

### 결정

비개발자가 드래그 앤 드롭으로 양식을 설계할 수 있는 GUI 디자이너를 핵심 기능으로 제공합니다.

### 근거

“자유롭게 만들 수 있으면서 만들기는 쉬워야 한다”는 목표를 충족하려면 양식 제작을 코드에서 분리해야 합니다.

### 영향

일반 사용자가 계산식을 구성할 수 있도록 안전한 내장 수식 엔진이 필요합니다.

## ADR-006: 데이터 주입, 저장소 어댑터와 표준 파일 형식으로 연계한다

**상태:** 채택

### 맥락

호스트는 업무 데이터를 양식에 넣고, 양식과 전표를 자체 저장소에 보관하며, 필요하면 파일로 교환해야 합니다.

### 결정

외부 연계 방식을 다음 세 가지로 제공합니다.

1. 호스트 데이터 주입
2. 저장소 어댑터
3. 공개된 `.slip` 파일 형식

SlipKit 자체 REST API 서버는 제공하지 않습니다.

### 근거

임베드형 라이브러리는 호스트의 데이터와 저장 인프라를 사용해야 합니다. 서버 구현까지 포함하면 호스트의 기존 구조와 중복됩니다.

## ADR-007: JSON 기반 자체 파일 형식을 사용한다

**상태:** 개정

**관련 결정:** ADR-036, ADR-046, ADR-051

### 맥락

양식과 전표는 사람이 조사할 수 있고, 다양한 환경에서 파싱·검증할 수 있는 교환 형식이 필요합니다.

### 결정

`.slip` 파일은 JSON 기반 자체 스키마를 사용합니다.

모든 파일에 `schemaVersion`을 포함하며, 향후 공개 버전 간 변경이 발생하면 `core`의 마이그레이션 계층에서 처리합니다.

현재 형식은 단일 JSON 문서입니다. 대용량 리소스가 필요해질 경우 JSON을 매니페스트로 사용하는 컨테이너 형식을 별도로 검토할 수 있습니다.

### 근거

JSON은 JavaScript와 TypeScript 생태계에서 파싱, 검증과 변경 비교가 쉽고 다른 언어에서도 널리 지원됩니다.

### 기각한 대안

- XML: 현재 기술 생태계에서 얻는 이점보다 관리 비용이 큽니다.
- 처음부터 ZIP 컨테이너 사용: 아직 필요하지 않은 복잡성을 추가합니다.

## ADR-008: 전표에 생성 당시의 양식 스냅샷을 포함한다

**상태:** 채택

### 맥락

전표를 만든 뒤 원본 양식이 수정되면 과거 전표의 모습까지 바뀌어서는 안 됩니다. 또한 전표 파일이 양식 저장소 없이도 열려야 합니다.

### 결정

전표 파일의 `templateSnapshot`에 전표를 만들 당시의 양식 본문을 깊은 복사로 포함합니다.

양식의 `sampleValues`가 양식 본문의 일부로 스냅샷에 남을 수 있지만, 전표 렌더링에는 전표 최상위 `values`만 사용합니다.

### 근거

발행 당시의 모양을 보존하고 전표 파일을 자기완결적으로 유지할 수 있습니다.

### 기각한 대안

- 양식 ID와 버전만 저장: 양식 저장소를 사용할 수 없으면 전표를 열 수 없습니다.
- 항상 최신 양식 사용: 과거 전표의 모양이 달라질 수 있습니다.

### 영향

전표 파일의 크기가 커질 수 있지만, 재현 가능성을 위해 이를 수용합니다.

## ADR-009: 파일 무결성과 암호화를 함께 제공한다

**상태:** 대체

**대체 결정:** ADR-053, ADR-054

### 맥락

초기 설계에서는 발행된 전표의 변경을 탐지하고, 필요하면 내용을 숨기는 기능을 파일 보안의 기본 방향으로 검토했습니다.

### 당시 결정

전표 내용에 해시 또는 서명을 포함하고 암호화는 선택 기능으로 제공하기로 했습니다.

### 변경

실제 사용 흐름에서는 전표 `.slip`보다 생성된 PDF를 보관하므로 `.slip` 무결성 계층은 제거했습니다. 자세한 내용은 ADR-053을 따릅니다.

파일 내용을 숨기는 암호화는 별도의 실제 사용 가치가 있어 ADR-054에서 다시 채택했습니다.

## ADR-010: 안전한 자체 수식 엔진을 제공한다

**상태:** 개정

**관련 결정:** ADR-017, ADR-039, ADR-044

### 맥락

양식 제작자는 합계, 조건, 문자열 조합과 날짜 계산을 양식 안에서 정의할 수 있어야 합니다. 호스트가 모든 계산 결과를 미리 만들어야 한다면 GUI 디자이너의 활용성이 떨어집니다.

### 결정

엑셀과 유사한 수식 문자열을 처리하는 자체 파서와 평가기를 `core`에 제공합니다.

임의 코드 실행을 허용하는 `eval`과 동적 함수 생성은 사용하지 않습니다.

### 근거

제한된 문법과 함수만 허용하면 일반 사용자가 계산을 정의할 수 있으면서도 임의 코드 실행을 차단할 수 있습니다.

### 기각한 대안

- 계산 결과만 호스트에서 주입: 일반 사용자가 양식의 계산 규칙을 정의할 수 없습니다.
- JavaScript 표현식 실행: 보안과 동작 예측 가능성을 보장하기 어렵습니다.

## ADR-011: 용지 좌표계와 다중 페이지를 1급 개념으로 사용한다

**상태:** 개정

**관련 결정:** ADR-037, ADR-041

### 맥락

SlipKit은 화면 문서가 아니라 인쇄와 PDF 생성을 전제로 하는 양식을 다룹니다. 요소 위치와 페이지 분할 결과를 예측할 수 있어야 합니다.

### 결정

레이아웃은 밀리미터 단위의 용지 좌표계를 사용합니다.

페이지는 스키마의 1급 개념으로 두며, 양식은 여러 페이지를 가질 수 있습니다. 반복 데이터의 페이지 분할은 SlipKit의 변환 계층에서 계산합니다.

### 근거

용지 기준 좌표는 인쇄 결과를 명확하게 정의합니다. 페이지 분할을 직접 계산하면 하부 PDF 엔진의 표 기능에 의존하지 않고 동일한 결과를 재현할 수 있습니다.

### 변경

페이지별 소계는 필수 기능에서 제외하고 보류했습니다. 자세한 내용은 ADR-041을 따릅니다.

## ADR-012: 화면과 PDF가 같은 레이아웃 변환 결과를 사용한다

**상태:** 개정

**관련 결정:** ADR-016, ADR-037, ADR-040, ADR-042, ADR-056

### 맥락

화면 미리보기와 PDF가 서로 다른 좌표 계산을 사용하면 위치, 줄바꿈과 페이지 분할이 달라질 수 있습니다.

### 결정

양식과 데이터를 `core`의 공통 변환 계층에서 렌더링 가능한 구조로 변환합니다. 화면 미리보기와 PDF 생성은 가능한 한 같은 좌표 계산과 변환 규칙을 사용합니다.

PDF는 브라우저에서 직접 생성하고, 텍스트를 유지하는 벡터 기반 결과를 사용합니다. DOM 화면을 캡처해 이미지 PDF로 만드는 방식은 사용하지 않습니다.

### 근거

공통 변환 계층은 화면과 PDF 사이의 차이를 줄이고, 브라우저와 Node.js 환경에서 같은 핵심 로직을 재사용할 수 있게 합니다.

> [!NOTE]
> 공통 변환 계층은 화면과 PDF의 일관성을 높이지만, 브라우저 렌더링과 PDF 엔진의 차이까지 자동으로 제거한다는 의미는 아닙니다. 두 출력은 테스트로 계속 검증해야 합니다.

### 기각한 대안

- DOM 캡처: 텍스트가 이미지가 되고 인쇄 품질과 접근성이 떨어집니다.
- Print CSS만 사용: 브라우저에 따라 결과가 달라지고 자동 생성에 제약이 있습니다.
- 처음부터 별도 서버 렌더러 제공: 현재 제품 범위를 넘어섭니다.

### 근거

## ADR-016: PDF 생성 엔진으로 pdfme를 사용한다

**상태:** 채택

### 맥락

PDF 생성에는 좌표 기반 배치, 폰트 임베딩과 다중 페이지 처리가 필요합니다. 이를 모두 처음부터 구현하면 프로젝트의 핵심인 양식 편집 경험에 집중하기 어렵습니다.

### 결정

`@pdfme/generator`, `@pdfme/schemas`와 `@pdfme/common`을 내부 PDF 생성 엔진으로 사용합니다.

SlipKit의 파일 형식과 공개 API에는 pdfme 구조를 노출하지 않습니다. SlipKit의 변환 계층이 필요할 때 pdfme용 중간 표현을 생성합니다.

pdfme의 React UI는 사용하지 않습니다.

### 근거

PDF 생성의 어려운 부분을 검증된 엔진에 맡기면서도, 파일 형식과 UI를 SlipKit이 독립적으로 관리할 수 있습니다.

### 영향

pdfme 의존성은 렌더러 경계 안에 두어 향후 다른 엔진으로 교체할 수 있게 유지합니다.

## ADR-017: 수식 함수의 기본 범위를 제한한다

**상태:** 개정

**관련 결정:** ADR-039, ADR-044

### 맥락

엑셀의 모든 함수를 구현하는 것은 범위가 지나치게 크지만, 전표에서 자주 사용하는 계산과 문자열 처리는 기본으로 필요합니다.

### 결정

다음 범주의 함수를 제공합니다.

| 범주 | 함수 |
|---|---|
| 집계 | `SUM`, `AVG`, `COUNT`, `MIN`, `MAX` |
| 조건부 집계 | `SUMIF`, `COUNTIF` |
| 산술 | `ROUND`, `FLOOR`, `CEIL`, `ABS`와 기본 산술 연산자 |
| 문자열 | `CONCAT`, `LEFT`, `RIGHT`, `MID`, `REPLACE`, `TRIM`, `UPPER`, `LOWER` |
| 조건 | `IF`, `AND`, `OR`와 비교 연산자 |
| 형식 | `FORMAT_NUMBER`, `FORMAT_DATE`, `NUMBER_TO_KOREAN` |
| 날짜 | `TODAY`, `DATE_ADD`, `DATE_DIFF` |
| 세무 | `VAT` |
| 형 변환 | `TO_NUMBER`, `TO_STRING`, `TO_DATE` |

### 근거

전표에서 반복적으로 사용하는 계산을 우선 제공하고, 구체적인 사용 사례가 없는 함수는 추가하지 않습니다.

### 변경

- VLOOKUP 계열 함수는 ADR-039에 따라 제공하지 않습니다.
- 명시적인 형 변환 함수와 엄격한 타입 규칙은 ADR-044에서 추가했습니다.

## ADR-020: GUI 디자이너의 초기 기능 범위를 실사용 최소선으로 정한다

### 맥락

GUI 디자이너는 단순히 요소를 배치하는 것만으로는 실제 전표를 만들기 어렵습니다. 편집 과정에 필요한 기본 도구와 표 작성 기능이 함께 필요합니다.

- 기본 프리셋

## ADR-021: 저장소 어댑터는 CRUD와 목록 조회를 제공한다

**상태:** 개정

**관련 결정:** ADR-025, ADR-045, ADR-055

### 맥락

호스트는 양식과 전표를 자체 저장소에 보관할 수 있어야 합니다. 목록 화면을 만들기 위해서는 단순 저장과 불러오기뿐 아니라 검색과 페이징도 필요합니다.

### 결정

필수 저장소 인터페이스는 다음 작업을 제공합니다.

- 저장
- 불러오기
- 삭제
- 목록 조회와 필터링

버전 이력은 선택 인터페이스로 분리합니다.

기본 구현으로 로컬 파일과 IndexedDB 저장소를 제공합니다.

### 근거

목록 조회까지 포함해야 실제 애플리케이션에서 사용할 수 있습니다. 반면 버전 이력을 필수로 만들면 저장소 구현 부담이 지나치게 커집니다.

## ADR-022: 파일 형식 명세와 JSON Schema를 공개한다

**상태:** 채택

### 맥락

`.slip`을 표준 교환 형식으로 사용하려면 SlipKit 패키지를 사용하지 않는 시스템도 파일 구조를 이해하고 검증할 수 있어야 합니다.

### 결정

JSON Schema는 런타임 스키마와 동일한 정의에서 생성해 이중 관리를 피합니다.

### 근거

사람이 읽는 명세와 기계가 읽는 스키마를 함께 제공해야 언어와 구현에 독립적인 교환 형식으로 사용할 수 있습니다.

## ADR-023: 규칙 기반 브랜치 전략을 사용한다

**상태:** 채택

### 맥락

여러 기능과 문서를 병렬로 수정하는 과정에서 기준 브랜치가 불명확하거나 작업이 섞이면 검토와 추적이 어려워집니다.

### 결정

- `main`에는 직접 커밋하지 않습니다.
- 작업은 목적별 브랜치에서 진행하고 Pull Request로 병합합니다.
- 브랜치 이름은 작업 종류와 범위를 나타냅니다.
- 커밋 메시지는 Conventional Commits 형식을 따릅니다.
- 구체적인 작업 규칙은 저장소의 개발 규칙 문서에서 관리합니다.

### 근거

일관된 분기와 병합 규칙은 변경 범위를 명확하게 하고 검토와 되돌리기를 쉽게 만듭니다.

## ADR-024: 개발 규칙을 저장소 안에서 관리하고 검증한다

**상태:** 채택

### 맥락

대화나 작업자 기억에만 의존하는 규칙은 세션이 바뀌면 쉽게 누락됩니다. 중요한 규칙은 저장소 안에 남기고 가능한 범위에서 자동 검증해야 합니다.

### 결정

개발 규칙을 다음 계층으로 관리합니다.

- 항상 적용되는 저장소 지침
- 경로별 코드와 문서 작성 규칙
- 위험한 Git 작업을 차단하는 훅과 권한 설정
- 반복 작업을 수행하는 검증 절차

### 근거

문서 지침은 판단 기준을 제공하고, 훅과 자동 검증은 실수로 규칙을 어기는 것을 줄입니다.

> [!NOTE]
> 개발 도구의 구체적인 파일 구성은 변경될 수 있습니다. 이 ADR의 핵심은 특정 도구가 아니라 규칙을 저장소에 남기고 자동 검증 가능한 부분을 기계적으로 검사한다는 원칙입니다.

## ADR-025: 저장소 인터페이스는 `core`, 브라우저 구현은 `elements`에 둔다

**상태:** 채택

### 맥락

호스트가 자체 저장소 어댑터를 구현할 때 UI 패키지에 의존할 필요는 없습니다. 반면 IndexedDB와 파일 다운로드는 브라우저 API에 의존합니다.

### 결정

저장소 인터페이스, 타입과 공통 오류는 `core`에 둡니다.

IndexedDB와 로컬 파일 저장소 구현은 `elements`에 둡니다.

로컬 파일 저장소에서 지원할 수 없는 삭제와 목록 작업은 명시적인 미지원 오류를 반환합니다.

### 근거

`core`의 DOM 비의존성을 유지하면서도 브라우저 환경에 필요한 기본 저장소를 제공할 수 있습니다.

## ADR-026: 디자이너에서 여러 페이지를 편집할 수 있게 한다

**상태:** 채택

다중 페이지가 파일 형식의 1급 개념인 만큼 GUI에서도 동일하게 다룰 수 있어야 합니다.

## ADR-028: 영어 UI를 제공한다

**상태:** 개정

**관련 결정:** ADR-042

### 맥락

UI가 한국어에만 고정되면 해외 호스트 애플리케이션에서 사용하기 어렵습니다.

영어 UI 사전을 추가하고 컴포넌트와 래퍼가 `locale`을 받을 수 있게 합니다.

알 수 없는 로케일은 기본 로케일로 처리하며, 새 문구를 추가할 때 지원 언어의 사전을 함께 갱신합니다.

### 근거

초기에 마련한 다국어 구조를 실제 지원 언어로 확장하고, 번역 키 누락을 타입과 테스트에서 확인할 수 있게 합니다.

### 변경

일본어는 ADR-042에서 추가했습니다.

## ADR-032: 공개 전 파일 형식에 도형과 표현 속성을 확장한다

초기 스키마는 실제 전표를 표현하기 위한 도형, 글자 스타일과 파라미터 정의가 충분하지 않았습니다.

## ADR-033: 인접한 그리드 셀의 테두리 충돌 규칙을 정의한다

**상태:** 채택

### 맥락

인접 셀이 같은 경계에 서로 다른 테두리를 지정하면 어느 값을 그릴지 명확한 규칙이 필요합니다.

### 결정

- 셀의 테두리 설정이 있으면 요소 기본값보다 우선합니다.
- 공유 경계에서는 유효한 굵기가 더 큰 테두리를 사용합니다.
- 굵기가 같으면 아래쪽 또는 오른쪽 셀의 설정을 사용합니다.
- 테두리 굵기 `0`은 해당 경계를 그리지 않는다는 뜻입니다.
- 병합된 셀 내부의 경계는 그리지 않습니다.

### 근거

결과가 선언 순서에 따라 달라지지 않고, 사용자가 굵은 테두리로 구역을 강조할 수 있습니다.

## ADR-034: 요소와 파라미터를 분리하고 편집 위치를 통일한다

**상태:** 개정

**관련 결정:** ADR-047, ADR-051

### 맥락

파라미터를 요소 안에서만 관리하면 여러 요소가 같은 값을 사용하는 관계를 이해하기 어렵습니다. 사이드바에서 목록과 편집을 동시에 처리하면 수정 도중 값이 의도치 않게 적용될 수 있습니다.

### 결정

파라미터를 요소와 독립된 1급 항목으로 관리합니다.

- 왼쪽 영역은 목록, 선택, 추가와 삭제를 담당합니다.
- 오른쪽 영역은 선택한 항목의 편집을 담당합니다.
- 요소는 등록된 파라미터를 선택해 사용합니다.
- 파라미터에서는 해당 값을 사용하는 요소와 위치를 확인할 수 있게 합니다.
- 아무것도 선택하지 않았을 때는 양식 설정을 표시합니다.

### 근거

선택과 편집의 역할을 나누면 화면 동작을 예측하기 쉬우며, 요소와 데이터 정의의 관계도 명확해집니다.

### 변경

목록 파라미터의 하위 필드는 ADR-047에서 파라미터 정의부로 이동했고, 용어는 ADR-051에서 `parameter`로 통일했습니다.

## ADR-035: 공개 전 다음 파일 형식 범위를 예고한다

**상태:** 대체

**대체 결정:** ADR-037, ADR-038, ADR-039와 이후 구현

### 맥락

당시 다음 개발 단계에서 동적 표, 파라미터 타입, 글자 표현과 페이지 기능을 확장하는 계획을 미리 기록했습니다.

### 당시 계획

- 동적 표 렌더링 개선
- 파라미터 값 종류
- 글자와 문단 속성 확장
- 페이지 번호와 이름
- 그리드 셀의 파라미터와 수식
- 표 중첩과 조회 수식 검토

### 변경

이 항목은 최종 결정이 아닌 공개 전 계획이었습니다.

- 동적 표는 ADR-037의 통합 그리드와 반복 구간으로 대체했습니다.
- 묶음 표현은 ADR-038의 자동 병합으로 정리했습니다.
- VLOOKUP 계열 함수는 ADR-039에서 도입하지 않기로 했습니다.
- 나머지 기능은 이후 공개 전 구현 과정에 반영했습니다.

따라서 현재 설계 기준으로 사용하지 않고 역사적 기록으로만 남깁니다.

## ADR-036: 이미지 입력과 렌더링에서는 내장 데이터를 사용한다

**상태:** 채택

**대체한 결정:** ADR-014

### 맥락

외부 URL 이미지는 CORS, 인증, 네트워크 실패와 콘텐츠 변경 가능성이 있습니다. `core`는 네트워크 요청을 수행하지 않으므로 외부 URL을 그대로 PDF에 렌더링할 수도 없습니다.

### 결정

- 디자이너는 파일에서 선택한 이미지를 base64 데이터로 저장합니다.
- 전표의 변동 이미지 값도 렌더링 가능한 내장 데이터로 전달합니다.
- URL 이미지를 사용해야 하는 호스트는 직접 이미지를 가져와 base64로 변환한 뒤 SlipKit에 전달합니다.
- 호스트가 이미지 크기 상한을 설정할 수 있게 합니다.
- 발행할 전표는 외부 URL에 의존하지 않는 자기완결적인 상태여야 합니다.

### 근거

이미지 네트워크 요청은 호스트의 인증과 보안 정책을 알아야 처리할 수 있습니다. 라이브러리는 렌더링 가능한 데이터만 받아 일관된 결과를 생성하는 편이 안전합니다.

> [!NOTE]
> 파일 스키마가 호환성을 위해 URL 형태를 읽을 수 있더라도, SlipKit이 해당 URL을 네트워크에서 가져오거나 PDF로 렌더링한다는 의미는 아닙니다.

### 기각한 대안

- 디자이너가 URL 이미지를 직접 가져오기: CORS와 인증 실패를 라이브러리가 해결할 수 없습니다.
- URL을 그대로 발행 파일에 저장: 파일이 외부 서버의 상태에 의존하게 됩니다.

## ADR-037: 고정 표와 동적 표를 하나의 그리드로 통합한다

**상태:** 채택

### 맥락

하부 PDF 엔진의 표 기능만으로는 셀별 스타일, 병합, 복잡한 헤더와 예측 가능한 페이지 분할을 구현하기 어렵습니다. 고정 표와 동적 표를 별도 요소로 유지하면 기능과 편집 방식이 중복됩니다.

### 결정

하나의 `grid` 요소로 고정 그리드와 반복 데이터를 모두 표현합니다.

- 그리드 안에서 하나의 연속된 행 범위를 반복 구간으로 지정할 수 있습니다.
- 행 높이와 열 너비는 밀리미터 단위의 절대값입니다.
- 한 페이지에 표시할 반복 항목 수는 `perPage`로 정합니다.
- 항목이 부족하면 남은 반복 영역을 빈 행으로 그릴 수 있습니다.
- 다음 페이지에서 헤더 반복 여부를 정할 수 있습니다.
- 긴 글은 줄바꿈하고 `clip` 또는 `shrink` 방식으로 넘침을 처리합니다.
- 반복 구간은 `core`에서 선, 사각형과 텍스트로 펼쳐 렌더링합니다.
- 페이지 분할도 SlipKit 변환 계층이 직접 계산합니다.

### 근거

그리드를 기본 요소로 직접 펼치면 셀별 스타일과 병합 규칙을 유지하면서 페이지 분할 결과를 예측할 수 있습니다.

### 기각한 대안

- 하부 엔진의 표 기능을 그대로 사용: 셀별 제어와 확장에 한계가 있습니다.
- 내용에 따라 행 높이를 자동 증가: 페이지 분할이 다시 복잡한 조판 문제가 됩니다.
- 표 종류를 계속 분리: 같은 기능과 UI를 중복 구현해야 합니다.

## ADR-038: 반복 데이터의 연속된 같은 값을 자동 병합할 수 있게 한다

**상태:** 채택

### 맥락

실제 전표에서는 같은 거래처나 품목에 속한 연속 행을 한 덩어리로 보이게 해야 할 수 있습니다. 이를 위해 중첩 표 전체를 도입하는 것은 지나치게 복잡합니다.

### 결정

그리드 열에 선택적인 `autoMerge` 설정을 제공합니다.

- 반복 구간에서 같은 열의 연속된 표시 값이 같으면 세로로 병합합니다.
- 빈 값은 병합하지 않습니다.
- 페이지가 바뀌면 병합을 끝내고 새 페이지에 값을 다시 표시합니다.
- 반복 구간 전체 높이를 차지하는 셀에만 적용할 수 있습니다.
- 열별로 명시적으로 설정하며 기본값은 비활성화입니다.

### 근거

항목 수와 행 높이를 바꾸지 않고 필요한 묶음 표현을 제공할 수 있어 ADR-037의 단순한 페이지 분할 구조를 유지합니다.

### 기각한 대안

- 중첩 표: 가변 높이와 페이지 분할 문제가 다시 발생합니다.
- 같은 값이면 모든 열 자동 병합: 수량처럼 우연히 같은 값까지 잘못 병합할 수 있습니다.
- 호스트가 반복 값을 비워서 전달: 페이지가 바뀌면 묶음의 값을 알 수 없습니다.

## ADR-039: VLOOKUP 계열 함수를 제공하지 않는다

**상태:** 채택

### 맥락

VLOOKUP과 유사한 조회 함수를 추가하려면 수식 엔진에 표 또는 조회 데이터 모델이 필요합니다. 하지만 실제 전표에서 해당 기능이 필요한 구체적인 사용 사례가 확인되지 않았습니다.

### 결정

현재 수식 엔진에는 범위 조회 함수를 추가하지 않습니다.

실제 양식에서 해결할 수 없는 사례가 확인되면 필요한 데이터 구조와 함께 다시 검토합니다.

### 근거

전표는 일반적으로 호스트가 조회와 결합을 끝낸 데이터를 전달합니다. 근거 없는 조회 함수 하나를 추가하면 파서, 평가기, 오류 처리와 UI까지 확장해야 합니다.

### 기각한 대안

- 예상 수요만으로 VLOOKUP 추가: 지원할 조회 데이터 모델이 정의되지 않았습니다.
- 양식에 상수 조회표부터 추가: 실제 요구가 없는 상태에서 파일 형식을 복잡하게 만듭니다.

## ADR-040: 폰트와 용지 후보는 호스트 공급 인터페이스로 받는다

**상태:** 개정

**관련 결정:** ADR-042, ADR-048, ADR-056

### 맥락

호스트마다 사용할 수 있는 폰트와 용지가 다르며, 서버나 자체 저장소에서 비동기로 불러와야 할 수 있습니다.

### 결정

폰트는 `getFonts` 공급 인터페이스로 받습니다.

디자이너 설정에서는 용지 후보를 가져오고 사용자가 만든 용지를 저장할 수 있는 인터페이스를 추가로 제공합니다.

SlipKit이 폰트 업로드와 영구 저장 위치를 직접 관리하지는 않습니다.

### 근거

자원의 저장 위치와 사용 권한은 호스트가 가장 잘 알고 있습니다. 공급 인터페이스는 SlipKit이 특정 저장소를 가정하지 않게 합니다.

### 변경

`core`에서의 폰트와 공통 설정 사용 방식은 ADR-056의 `createSlipKit`으로 통합했습니다.

## ADR-041: 일부 기능을 보류하고 범위를 축소한다

파일 암호화, 페이지별 소계와 동봉 프리셋 확장은 당시 구체적인 사용 사례에 비해 설계와 구현 비용이 컸습니다.

페이지별 소계와 추가 기본 프리셋은 계속 보류하며, 필요성이 확인되면 별도 결정으로 다시 검토합니다.

## ADR-042: 일본어 UI와 기본 일본어 폰트를 제공한다

**상태:** 채택

### 맥락

일본어 UI만 추가하고 일본어 글리프가 없는 기본 폰트를 사용하면 화면이나 PDF에서 문자가 깨질 수 있습니다.

### 결정

- `ja` 로케일과 일본어 UI 사전을 제공합니다.
- 일본어를 표시할 수 있는 Noto Sans JP Regular를 기본 폰트로 제공합니다.
- 일본어를 사용하지 않는 번들에 불필요하게 포함되지 않도록 별도 진입점에서 불러옵니다.
- 추가 글자와 굵기는 호스트가 `getFonts`로 공급합니다.
- 일본어 금액 한자 표기 함수는 현재 제공하지 않습니다.
- 공개 문서는 한국어, 영어와 일본어판을 함께 관리합니다.

### 근거

로케일을 바꾸는 것만으로 기본적인 일본어 문서가 렌더링되어야 합니다. 모든 폰트를 번들에 포함하는 대신 기본 한 종류와 호스트 공급 방식을 조합합니다.

### 기각한 대안

- 일본어 폰트를 전부 호스트에 맡기기: 기본 설정에서 일본어가 깨질 수 있습니다.
- 여러 굵기와 전체 글리프를 모두 동봉: 번들 크기가 지나치게 증가합니다.
- 수요 확인 없이 일본어 숫자 함수를 추가: 수식 범위만 불필요하게 넓어집니다.

암호화된 파일의 복호화 실패는 ADR-054의 인증 암호화 규칙에 따라 별도로 처리합니다.

## ADR-044: 수식에서 엄격한 타입과 명시적 형 변환을 사용한다

**상태:** 채택

### 맥락

산술 연산은 숫자 문자열을 자동 변환하지만 비교 연산은 타입을 구분하면 같은 값이 상황에 따라 다르게 처리됩니다. 자동 변환 실패가 늦게 드러나는 문제도 있습니다.

### 결정

- 숫자가 필요한 연산에는 숫자 값만 허용합니다.
- 비어 있는 값은 숫자 문맥에서 `0`으로 처리합니다.
- 숫자가 아닌 문자열은 산술 연산에서 오류로 처리합니다.
- 문자열이 필요한 곳에서는 숫자와 논리값을 문자열로 표현할 수 있습니다.
- 위험한 변환은 `TO_NUMBER`, `TO_STRING`, `TO_DATE`로 명시합니다.
- 최상위 `number` 파라미터의 빈 값은 전표 조립과 렌더링 진입점에서 `0`으로 정규화합니다.

### 근거

숫자 자리는 숫자만 받는다는 일관된 규칙이 자동 변환보다 이해하기 쉽고 오류를 빠르게 발견할 수 있습니다.

## ADR-045: IndexedDB 본문은 Blob으로 저장하고 목록은 메타데이터로 처리한다

**상태:** 개정

**관련 결정:** ADR-055

### 맥락

목록을 불러올 때 base64 이미지를 포함한 전체 본문을 메모리에 올리면 데이터가 커질수록 비효율적입니다. 오프셋 기반 재조회는 목록이 변경될 때 중복과 누락을 만들 수 있습니다.

### 결정

- IndexedDB의 한 레코드에 메타데이터와 본문을 함께 저장합니다.
- 본문은 Blob으로 저장하고, 목록 조회에서는 메타데이터만 사용합니다.
- 본문은 사용자가 실제 항목을 열 때 읽습니다.
- 목록 화면은 열 때 받은 메타데이터 스냅샷을 기준으로 검색과 페이지 이동을 처리합니다.
- 손상된 본문을 열지 못해도 목록에서 해당 항목을 확인하고 삭제할 수 있게 합니다.
- 이전 문자열 본문은 데이터베이스 마이그레이션에서 Blob으로 변환합니다.

### 근거

메타데이터와 본문을 같은 레코드에 두면 고아 데이터 없이 목록 조회 비용을 줄일 수 있습니다. 화면 스냅샷을 사용하면 목록이 열려 있는 동안 항목 위치가 흔들리지 않습니다.

## ADR-046: 공개 전 스키마 버전을 `0.1.0`으로 정리한다

**상태:** 채택

### 맥락

공개 전 개발 과정에서 스키마 버전이 여러 번 증가했지만 해당 버전으로 배포되거나 보관된 파일은 없었습니다. 첫 공개부터 높은 버전 번호를 사용하면 실제 호환성 이력이 있었던 것처럼 보일 수 있습니다.

### 결정

- 공개 전까지 개발한 현재 스키마를 `0.1.0`으로 다시 표시합니다.
- 공개되지 않은 개발 단계 사이의 마이그레이션은 제거합니다.
- 미래 버전을 위한 마이그레이션 구조는 유지합니다.
- npm 패키지 버전과 파일의 `schemaVersion`은 별개로 관리합니다.

### 근거

사용자가 경험하지 않은 개발 이력을 호환성 버전으로 유지할 필요가 없습니다.

> [!NOTE]
> 과거 ADR에 남아 있는 `0.2.0`부터 `0.5.0`까지의 표현은 공개된 파일 버전이 아니라 당시 개발 단계를 가리키는 기록입니다.

## ADR-047: 파라미터 정의부에서 목록의 하위 필드까지 관리한다

**상태:** 채택

### 맥락

목록 항목의 필드를 그리드 셀에서 역산하면 그리드를 먼저 만들어야만 데이터 구조를 정의할 수 있습니다. 파라미터가 요소와 분리된 1급 항목이라는 원칙에도 맞지 않습니다.

### 결정

- `parameters`가 최상위 값과 목록의 하위 필드를 정의하는 단일 원천이 됩니다.
- 목록 파라미터는 `fields`로 항목의 필드를 정의합니다.
- 하위 필드는 다시 하위 목록을 가질 수 없습니다.
- 파라미터와 하위 필드의 값 종류를 디자이너에서 선택할 수 있게 합니다.
- 그리드 셀은 해당 위치에서 사용할 수 있는 파라미터 또는 하위 필드 중 하나를 선택합니다.
- 반복 구간 안에서는 연결된 목록 파라미터의 필드만 선택할 수 있습니다.
- 반복 구간 밖에서는 최상위 파라미터를 선택합니다.

### 근거

데이터 정의를 그리드와 분리하면 양식의 입력 구조를 먼저 설계할 수 있고, 자유 입력으로 인한 파라미터 이름 오타도 줄일 수 있습니다.

### 호환성

정의부에 없는 기존 필드를 즉시 삭제하지 않고 확인 가능한 상태로 유지해 사용자가 정리할 수 있게 합니다.

## ADR-048: 바코드 후보는 호스트가, 반복 항목 상한은 양식이 정한다

**상태:** 채택

### 맥락

모든 바코드 종류를 항상 표시하면 호스트에 필요 없는 선택지가 많아집니다. 반복 항목 수에 상한이 없으면 예상보다 많은 페이지가 생성될 수도 있습니다.

### 결정

- 호스트는 디자이너 설정의 공급 인터페이스로 표시할 바코드 종류를 제한할 수 있습니다.
- 공급하지 않거나 빈 목록을 반환하면 지원하는 전체 바코드 종류를 표시합니다.
- 기존 파일에 저장된 바코드 종류는 현재 후보 목록에 없더라도 값을 보존합니다.
- 양식은 반복 구간의 선택적 `maxItems`로 렌더링할 최대 항목 수를 정할 수 있습니다.
- 상한을 넘는 항목은 렌더링하지 않습니다.
- 상한을 지정하지 않으면 전달된 항목 수만큼 처리합니다.

### 근거

바코드 후보는 설치 환경의 정책이고, 반복 영역의 크기는 양식의 성질입니다. 각각을 가장 잘 아는 주체가 설정하게 합니다.

## ADR-049: 필드의 값 소스는 파라미터와 수식 중 하나만 사용한다

**상태:** 채택

### 맥락

필드가 파라미터와 수식을 동시에 가지면 렌더러는 수식만 사용하면서도 UI에는 두 값이 모두 유효한 것처럼 보일 수 있습니다.

### 결정

필드의 값 소스는 다음 중 정확히 하나여야 합니다.

- 파라미터
- 수식

두 값을 동시에 지정하거나 둘 다 지정하지 않은 파일은 유효하지 않습니다.

디자이너에서 값 소스를 변경하면 사용하지 않는 반대쪽 설정을 제거합니다. 빈 수식은 편집 중인 상태로 보고 빈 글자로 렌더링합니다.

### 근거

실제 렌더링에 사용되는 값이 무엇인지 구조와 UI에서 명확하게 알 수 있어야 합니다. 안내 문구로 우선순위를 설명하는 것보다 애초에 모호한 조합을 허용하지 않는 편이 안전합니다.

## ADR-050: 선은 길이와 각도로 편집하고 기존 형식으로 저장한다

**상태:** 채택

### 맥락

수평·수직선과 사선이 서로 다른 크기 입력 방식을 사용하면 방향을 바꿀 때 편집 화면이 달라지고 조작을 예측하기 어렵습니다.

### 결정

디자이너에서 선은 다음 값으로 편집합니다.

- 길이
- 각도
- 선 굵기

각도는 화면 좌표계를 기준으로 시계 방향으로 증가합니다. 주요 직각에 가까운 각도는 해당 각도에 맞춥니다.

파일에는 기존처럼 요소의 위치, 너비, 높이와 `lineDirection`을 저장합니다.

### 근거

사용자는 선을 길이와 방향으로 이해하는 반면, 공통 요소 구조는 경계 상자로 저장하는 편이 일관됩니다. 편집 표현과 저장 형식을 분리하면 스키마를 변경하지 않고 조작 경험을 개선할 수 있습니다.

## ADR-051: `binding` 용어를 `parameter`로 통일한다

**상태:** 채택

### 맥락

UI와 문서는 파라미터라는 표현을 사용하지만 파일과 코드에는 `binding`이 남아 있었습니다. 같은 개념을 두 이름으로 부르면 문서와 구현을 함께 이해하기 어렵습니다.

### 결정

파일 형식, 타입, 함수와 코드 식별자에서 `binding`을 `parameter`로 변경합니다.

주요 변경은 다음과 같습니다.

- `bindings` → `parameters`
- `binding` → `parameter`
- `BindingDef` → `ParameterDef`
- 관련 타입, 함수와 제한 이름도 같은 기준으로 변경

공개 전 변경이므로 이전 이름을 위한 별도 마이그레이션은 제공하지 않습니다.

### 근거

화면, 문서, 파일과 코드에서 같은 개념을 같은 이름으로 표현할 수 있습니다.

## ADR-052: 전표 조립 함수 `buildVoucher`를 공개한다

**상태:** 개정

**관련 결정:** ADR-053

### 맥락

UI 없이 `core`만 사용하는 호스트는 양식 스냅샷, 값 정규화와 발행 상태를 직접 조립해야 했습니다. 작성폼과 호스트 구현이 서로 다른 전표를 만들 가능성이 있습니다.

### 결정

`buildVoucher(template, values)`를 `core` 공개 API로 제공합니다.

이 함수는 다음 작업을 수행합니다.

- 양식 스냅샷 깊은 복사
- 전표 값 깊은 복사
- 숫자 파라미터 정규화
- 발행 전 상태인 `issued: false` 전표 생성

작성폼도 같은 함수를 사용합니다.

### 근거

전표 조립 규칙을 한곳에 두면 스냅샷 누락, 입력 객체 참조 공유와 값 정규화 누락을 방지할 수 있습니다.

### 변경

무결성 계층이 제거됨에 따라 발행은 암호학적 서명 작업이 아니라 `issued` 상태를 확정하는 별도 단계입니다.

## ADR-053: 파일 무결성 해시와 서명을 제거한다

**상태:** 채택

**대체한 결정:** ADR-009의 무결성 부분, ADR-019, ADR-043

### 맥락

무결성 기능은 발행된 전표 `.slip` 파일을 보관하고 나중에 다시 열어 검증하는 흐름을 전제로 했습니다.

실제 사용 흐름에서는 양식과 데이터를 이용해 PDF를 생성하고 해당 PDF를 보관하며, 전표 `.slip` 파일은 남기지 않는 경우가 많습니다. 키 없는 해시는 파일을 수정한 사람이 다시 계산할 수 있으므로 발행자나 진위를 보장하지도 못합니다.

### 결정

다음 무결성 기능을 제거합니다.

- SHA-256 내용 해시
- JWS 서명과 검증
- JSON 정규화
- 전표의 `integrity` 필드
- 작성폼의 서명 키
- 뷰어의 검증 키와 로드 시 무결성 검사

`issued`는 암호학적 신뢰 표시가 아니라 발행 후 입력을 잠그는 논리적 상태로 유지합니다.

### 근거

실제 보관하지 않는 파일에 복잡한 무결성 계층을 유지할 가치가 부족합니다. 파일의 출처나 법적 진위가 필요하다면 보관 대상에 맞는 별도의 서명 체계를 설계해야 합니다.

### 향후 검토

시스템 간 `.slip` 전표 교환과 장기 보관 요구가 실제로 확인되면 별도의 결정으로 다시 검토할 수 있습니다.

## ADR-054: 선택적인 AES-256-GCM 파일 암호화를 제공한다

**상태:** 채택

**개정한 결정:** ADR-041

### 맥락

`.slip`은 JSON이므로 평문 파일을 열면 양식과 전표 내용을 확인할 수 있습니다. 전송 구간 암호화만으로는 다운로드하거나 저장한 파일 자체를 보호할 수 없습니다.

### 결정

`core`에서 선택적인 파일 암호화와 복호화를 제공합니다.

- 암호화 알고리즘은 AES-256-GCM을 사용합니다.
- 32바이트 원시 키 또는 암호 문자열을 사용할 수 있습니다.
- 암호 문자열은 PBKDF2-SHA256으로 키를 파생합니다.
- 암호화된 파일은 평문 `.slip`과 구분되는 봉투 구조를 사용합니다.
- 복호화한 결과는 일반 `.slip` 파일과 같은 방식으로 파싱하고 검증합니다.
- 키의 생성, 전달, 보관과 권한 관리는 호스트가 책임집니다.

정확한 봉투 구조와 검증 절차는 [파일 형식 명세](./SPEC.md)를 따릅니다.

### 근거

암호화는 파일 자체를 저장하거나 전달할 때 내용을 숨기는 실제 사용 가치가 있습니다. AES-GCM은 기밀성과 함께 잘못된 키 및 암호문 변경도 검출합니다.

### 기각한 대안

- 파일 보호를 전송 구간에만 맡기기: 저장된 파일은 평문으로 남습니다.
- 처음부터 암호화 ZIP 컨테이너 사용: 현재 요구에 비해 구조가 무겁습니다.
- 내장 공용 키 사용: 소스에 포함된 키는 실제 보안 수단이 될 수 없습니다.

## ADR-055: 저장소 어댑터에서 암호화를 자동 적용할 수 있게 한다

**상태:** 채택

### 맥락

암호화가 `core` 함수로만 제공되면 호스트가 모든 저장과 불러오기 경로에 직접 연결해야 합니다.

### 결정

기본 저장소 어댑터가 선택적인 암호화 설정을 받을 수 있게 합니다.

- 암호화를 활성화하면 저장 시 본문을 암호화합니다.
- 불러올 때 암호화 봉투를 자동으로 감지하고 복호화를 시도합니다.
- 평문 파일은 기존과 동일하게 읽습니다.
- 현재 키와 이전 키 목록을 받아 키 교체 기간의 파일을 읽을 수 있게 합니다.
- 저장할 때는 항상 현재 키를 사용합니다.
- 이전 키로 연 파일을 다시 저장하면 현재 키로 암호화합니다.
- IndexedDB에서는 목록 조회에 필요한 메타데이터를 평문으로 두고 본문만 암호화합니다.
- 로컬 파일 저장소에서는 파일 전체가 암호화 봉투가 됩니다.

키를 제공하지 않은 데모 환경에서는 샘플 키를 사용할 수 있지만, 해당 키는 실제 보안 수단으로 사용하지 않습니다.

### 근거

암호화 대상과 시점은 저장 정책에 속하므로 저장소 어댑터가 자연스러운 적용 위치입니다. 키 교체를 지원하면 기존 파일을 한 번에 다시 암호화하지 않고 점진적으로 이전할 수 있습니다.

> [!WARNING]
> 소스 코드에 포함된 샘플 키는 누구나 확인할 수 있습니다. 실제 환경에서는 반드시 호스트가 관리하는 별도의 키를 제공해야 합니다.
>
> IndexedDB 메타데이터는 목록 표시를 위해 평문으로 남으므로 제목과 갱신 시각 등은 암호화되지 않을 수 있습니다.

## ADR-056: 설정을 가진 `createSlipKit` 인스턴스를 표준 진입점으로 제공한다

**상태:** 채택

### 맥락

폰트, 로케일과 암호화 키처럼 여러 작업에서 공통으로 사용하는 설정을 함수마다 전달하면 호출부가 반복되고 설정 누락 가능성이 커집니다.

### 결정

`createSlipKit(config)` 팩토리를 제공하고, 공통 설정을 가진 인스턴스를 반환합니다.

설정에는 다음 항목이 포함될 수 있습니다.

- 폰트 공급 함수
- 로케일
- 현재 암호화 키
- 이전 암호화 키 목록

인스턴스는 렌더링, 전표 조립, 수식 평가, 암호화와 복호화 작업을 제공합니다.

파일마다 달라질 수 있는 값은 메서드 인자로 덮어쓸 수 있습니다.

파싱, 검증과 같은 기존 순수 함수도 계속 개별적으로 공개합니다. `createSlipKit`은 순수 함수를 대체하는 필수 파사드가 아니라 공통 설정을 반복하지 않기 위한 표준 편의 진입점입니다.

### 근거

공통 설정을 한곳에서 관리하면 함수 시그니처가 안정되고 폰트나 암호화 키를 호출마다 빠뜨리는 실수를 줄일 수 있습니다.

### 기각한 대안

- 모든 기능을 하나의 거대한 클래스에만 제공: 설정이 필요 없는 파싱과 검증까지 인스턴스에 종속됩니다.
- 모든 함수에 설정을 반복 전달: 호출부가 복잡해지고 설정이 늘 때 공개 API가 계속 변경됩니다.

## ADR-057: 서버 지원은 ESM 전용을 유지하고 exports 보정으로 제공한다

**상태:** 채택

### 맥락

서버에서 core를 사용하는 실제 사용 사례는 전표 PDF의 서버 측 생성과 보관입니다. 서버가 전표를 검증하고 렌더링까지 수행하는 구조를 전제로 하며, 클라이언트가 만든 PDF를 업로드받아 원본처럼 보관하는 방식은 저장된 PDF가 검증된 전표 데이터의 렌더 결과임을 서버가 보증할 수 없어 제외합니다.

조사에서 다음을 확인했습니다.

- 현재 `exports`에는 `types`·`import` 조건만 있어, CommonJS로 출력되는 프로젝트(일반적인 NestJS 구성 포함)에서 패키지 이름 `require`가 exports 해석 단계에서 실패합니다.
- 같은 ESM 산출물을 `require` 조건으로 노출하면 Node의 `require(esm)` 기능으로 동기 로드가 가능합니다. 빌드된 core의 의존 그래프(pdfme·fontkit·Zod 포함)에 top-level `await`가 없음을 확인했습니다.
- `require(esm)`은 Node 22.12부터 기본 활성이고 22.13부터는 플래그 없이 경고가 없습니다. Node 20은 2026-04-30에 유지보수가 종료됐고, Node 22는 2027-04까지 지원되는 Maintenance LTS입니다.
- 동봉 폰트 하위 경로 모듈은 DOM 없이 동작해 서버에서도 쓸 수 있으나, 같은 exports 보정이 필요합니다.

### 결정

1. ESM 전용 배포를 유지하고 CommonJS 병행 배포(이중 빌드)는 하지 않습니다.
2. 다음 경로의 `exports`에 같은 ESM 산출물을 가리키는 `require` 조건을 추가합니다.
   - `@omdc-slipkit/core` (루트 진입점)
   - `@omdc-slipkit/elements/fonts/pretendard`
   - `@omdc-slipkit/elements/fonts/noto-sans-jp`
   Web Component가 들어 있는 `elements` 루트 진입점은 서버 지원 대상이 아니므로 추가하지 않습니다.
3. `engines.node`를 `>=22.13`으로 명시합니다 — 경고 없이 `require(esm)`을 쓸 수 있는 가장 낮은 지원 LTS 계열입니다.
4. core 하위 진입점 분리는 하지 않습니다. 현재 서버 사용 사례는 PDF 생성까지 포함해 어차피 렌더 의존성을 사용하므로, 검증 전용 소비 같은 실제 요구가 확인되면 다시 검토합니다.
5. 서버 프레임워크 전용 패키지는 만들지 않고, 서버(NestJS) 통합은 가이드 문서로 안내합니다.
6. 설치 상태에서 패키지 이름으로 `require`하는 스모크 테스트를 두어, 의존성이 top-level `await`를 도입하는 등의 회귀를 잡습니다.

### 근거

- 정한 Node 지원 범위(22.13 이상)에는 모두 `require(esm)`이 있으므로, exports 보정만으로 ESM 전용 배포를 유지하면서 CommonJS 소비를 지원할 수 있습니다.
- 하위 진입점과 전용 패키지는 실제 요구 없이 공개 API 계약과 유지 비용을 늘립니다.

### 기각한 대안

- **CommonJS 병행 배포(이중 빌드)**: CommonJS 산출물을 별도로 요구하는 도구나 소비 환경까지 지원할 수 있지만, 정한 Node 지원 범위에서는 런타임 호환성 이점이 없고 같은 클래스가 두 벌 실리는 문제(dual package hazard)와 빌드·테스트 비용이 추가됩니다.
- **core 하위 진입점 5개 분리**: 로딩 범위와 공개 API 설계를 위한 별개의 선택이며 서버 호환성의 필수 조건이 아닙니다. 부분 로딩 요구가 확인되면 다시 검토합니다.
- **`@omdc-slipkit/nestjs` 전용 패키지**: 배포 형식 문제를 해결하지 못하고(전용 패키지도 core를 불러옵니다), 담을 내용이 프로바이더 등록 수준으로 얇으며, 문서와 프레임워크 추적 유지비가 듭니다.

## ADR-058: 브랜치 형식을 훅으로 집행하고 예외는 허용 목록으로 제어한다

**상태:** 채택

### 맥락

브랜치 형식 규칙(`<type>/<scope>-<topic>`, ADR-024)은 문서로만 존재해 규칙에 맞지 않는 브랜치에서의 작업을 막을 수단이 없었습니다. 한편 원격 실행 환경처럼 브랜치 이름을 강제하는 경우가 있어, 규칙에 맞지 않는 브랜치도 통제된 방식으로는 쓸 수 있어야 합니다.

### 결정

1. PreToolUse 훅(`bash-guard.mjs`)이 커밋·푸시 시 현재 브랜치의 형식을 검사해 어긋나면 차단합니다. 형식 검사는 검증 게이트보다 먼저 실행합니다.
2. 규칙에 맞지 않아도 허용할 브랜치는 `.claude/hooks/branch-guard.json`의 `allowBranches` 패턴 목록(`*` 와일드카드)으로 관리합니다. 이 목록은 리포에 커밋되어 변경이 검토 대상이 됩니다.
3. 허용 목록에는 사용자 확인을 받은 브랜치만 추가합니다.
4. 자동화 도구 이름을 딴 브랜치(`claude*`·`codex*` 등)는 같은 파일의 `denyBranches` 거부 목록으로 항상 차단합니다. 거부 목록은 허용 목록보다 우선하며, 허용 목록으로도 열 수 없습니다.

### 근거

- 규칙의 집행 지점이 훅 하나로 모이고, 예외도 같은 자리에서 명시적으로 관리됩니다.
- 환경 변수 같은 일회성 우회와 달리, 커밋되는 설정 파일은 예외의 근거가 이력으로 남습니다.

### 기각한 대안

- **환경 변수로 검사 끄기**: 켜고 끈 기록이 남지 않고, 끈 채로 잊기 쉽습니다.
- **경고만 하고 통과**: 규칙이 다시 문서 수준으로 약해집니다. 예외가 필요하면 허용 목록에 명시하는 쪽이 명확합니다.

## ADR-059: 소스 주석에는 동작과 제약만 적는다

**상태:** 채택

### 맥락

주석 규칙은 근거 설계 결정을 주석 본문에 `ADR-xxx`로 표기하도록 했고, 실제 코드에는 결정 번호·작업 항목 번호·개발 경위가 널리 쌓였습니다. 이런 참조는 코드를 읽는 사람을 문서로 오가게 하고, 결정이 개정되면 낡은 참조로 남으며, 주석이 현재 동작보다 이력을 설명하는 데 치우치게 했습니다.

### 결정

1. 소스 주석은 코드의 현재 동작과, 코드만으로 드러나지 않는 제약·이유만 설명합니다.
2. 설계 결정 번호(`ADR-xxx`), 작업 항목 번호(`G-xx`·`F-xx`·`D-xx`·`Q-xx`), 개발 경위와 이전 동작은 소스 주석에 적지 않습니다. 결정의 배경은 이 문서에서 찾습니다.
3. TSDoc 형식과 태그·자동 검사 규칙(ADR-029, ADR-030)은 그대로 유지합니다.

이 결정은 소스 코드 주석에만 적용됩니다. 규칙 문서와 일반 문서에서는 지금처럼 ADR 번호를 표기합니다.

### 근거

ADR-029는 주석을 구현 방식보다 사용자가 알아야 할 동작, 제약과 오류 조건 중심으로 작성하도록 정의했습니다. 결정 번호와 경위 표기는 이 목적에 들어맞지 않으며, 근거와 이력은 이 문서가 담당합니다.

### 기각한 대안

- **주석에 ADR 번호 표기 유지**: 결정이 개정될 때마다 주석이 낡은 참조로 남고, 표기 여부도 일관되게 유지되지 않았습니다.

## ADR-060: 사용자 대면 메시지의 기본 언어를 영어로 하고 로케일로 전환한다

**상태:** 채택 (ADR-013의 기본 한국어 원칙을 개정)

**관련 결정:** ADR-013, ADR-028, ADR-042, ADR-056

### 맥락

UI 문구는 언어별 리소스로 분리되어 있었지만(ADR-013, ADR-028, ADR-042), core의 사용자 대면 오류 메시지(파싱·검증·수식·렌더링·암호화)는 한국어로 고정되어 있었습니다. UI의 기본 언어와 `FORMAT_NUMBER` 등 형식 함수의 기본 로케일도 한국어(`ko-KR`)였습니다. 공개를 앞두고, 로케일을 설정하지 않은 국제 사용자가 기본 상태에서 읽을 수 있는 메시지가 필요했습니다.

### 결정

1. 사용자 대면 메시지의 기본 언어는 **영어**입니다. BCP 47 로케일의 언어 부분이 `ko`·`ja`면 한국어·일본어로, 그 밖이거나 생략하면 영어로 표시합니다.
2. core는 로케일을 인자·설정으로 받아 메시지 언어를 정합니다. `parseSlipFile`·`validateSlipFile`·`encryptSlipFile`·`decryptSlipFile`의 `locale` 옵션, 렌더링·수식의 `locale`, `createSlipKit`의 `config.locale`은 동일한 로케일 설정을 사용합니다.
3. `FORMAT_NUMBER` 등 형식 함수의 기본 로케일을 `ko-KR`에서 `en-US`로 바꿉니다.
4. elements UI의 기본 언어를 한국어에서 영어로 바꾸고, 지원하지 않는 로케일의 대체 언어도 한국어에서 영어로 바꿉니다. 수식 도움말도 같습니다.
5. 동봉 프리셋은 `getPresets(locale)`로 해당 언어의 제목·라벨·문구로 **생성**합니다. 이미 만들어진 양식의 문구는 이후 로케일 변경과 무관하게 유지됩니다(자동 번역 금지, ADR-028 유지).
6. 리포의 개발 언어 규칙(문서·커밋 메시지 한국어)은 그대로 둡니다. 사용자 대면 메시지 언어와 개발 문서 언어는 별개의 결정입니다.

### 근거

- 라이브러리를 처음 설치한 사용자는 로케일을 지정하지 않을 수 있습니다. 영어를 기본값으로 사용하면 세 지원 언어 외의 사용자도 오류 메시지를 이해할 수 있습니다.
- 메시지 언어와 숫자·날짜 형식이 동일한 `locale` 값을 사용하므로 호스트는 하나의 설정만 관리하면 됩니다.
- 동기 실행 경로인 수식 파싱·평가와 `.slip` 검증은 진입점에서 선택한 메시지 사전을 실행이 끝날 때까지 유지합니다. 암호화·렌더링과 같은 비동기 경로는 로케일을 인자로 전달합니다.

### 기각한 대안

- **한국어 기본 유지**: 국제 공개 시 기본 상태의 메시지를 대부분의 사용자가 읽을 수 없습니다.
- **오류 코드만 제공하고 번역은 호스트 책임**: 임베드형 패키지의 통합 부담을 지나치게 키우고, 세 언어 사전이 이미 있는 UI 문구 구조와도 어긋납니다.

## ADR-061: AI 연동은 로컬 MCP 서버 패키지로 제공한다

**상태:** 채택

**관련 결정:** ADR-002, ADR-010, ADR-021, ADR-025, ADR-054, ADR-057, ADR-060

### 맥락

로드맵의 MCP·AI 연동 항목은 AI가 다룰 수 있는 대상, 도구의 입력과 출력, 사용자 확인 없이 허용할 작업의 범위와 데이터 보호 방식을 먼저 정하도록 요구합니다. MCP 도구의 정의와 응답은 AI의 컨텍스트에 그대로 들어가므로, 큰 파일과 이미지를 다루는 방식이 토큰 비용을 좌우합니다. LLM이 배열 인덱스 기반 편집(RFC 6902 JSON Patch)에서 인덱스 계산을 자주 틀린다는 측정 결과가 있고, 문서 편집 계열 MCP 서버들은 요약 우선 읽기와 안정 식별자 지목 수정으로 수렴해 있습니다.

### 결정

- 새 패키지 `@omdc-slipkit/mcp`를 추가합니다. stdio 전송의 로컬 MCP 서버이며, 파일 처리 기능은 `@omdc-slipkit/core`의 공개 API만 사용합니다. 커스텀 폰트를 설정하지 않으면 `@omdc-slipkit/elements`의 동봉 폰트를 사용합니다.
- 파일 접근은 서버 시작 시 지정한 작업 디렉터리 안의 경로로 제한합니다. 이 접근은 `StorageAdapter` 구현인 `FileSystemStorage`로 공개해, Node 백엔드를 가진 호스트가 같은 규칙으로 재사용할 수 있게 합니다.
- 서버는 `slipkit-mcp.json`에서 작업 디렉터리, 로케일, 커스텀 폰트와 암호화 키 환경변수 이름을 읽습니다. CLI 인자와 환경변수는 설정 파일보다 우선하며, 설정 파일의 상대 경로는 해당 파일 위치를 기준으로 해석합니다.
- 커스텀 폰트는 TTF·OTF 파일 경로와 렌더러에서 참조할 이름으로 등록합니다. 목록을 생략하면 로케일에 맞는 동봉 폰트를 사용합니다.
- 도구는 7종입니다: `slip_list`, `slip_read`, `slip_save`, `slip_edit`, `slip_build_voucher`, `slip_render_pdf`, `slip_schema`.
- 읽기는 요약이 기본이고, 요소·페이지를 지목해 필요한 부분만 전문을 반환합니다. base64 데이터는 어떤 응답에도 싣지 않고 크기 표시로 치환합니다. 이미지는 파일 경로를 받아 서버가 직접 읽어 에셋으로 넣습니다.
- 새 파일은 전문(JSON) 저장으로 만들고, 기존 파일은 요소 id·파라미터 key·페이지 번호를 지목하는 부분 수정 연산으로 고칩니다. 연산 묶음은 원자적으로 적용하며, 적용 결과가 전체 검증을 통과하지 못하면 아무것도 저장하지 않습니다.
- 발행 도구는 두지 않고, 발행된 전표의 수정 요청은 거부합니다. 발행은 호스트 애플리케이션에서 사람이 수행합니다.
- 암호화 키 값은 환경변수로만 받습니다. 기본 이름은 `SLIPKIT_MCP_KEY`와 `SLIPKIT_MCP_PREVIOUS_KEYS`이며, 설정 파일에서 다른 환경변수 이름을 지정할 수 있습니다. 키가 있으면 암호화 파일을 읽고 쓰며, 키 없이 암호화 파일을 읽으면 설정 방법을 안내하는 오류를 반환합니다.
- 도구 이름·설명·응답과 구조 안내(`slip_schema`)는 AI가 읽는 자료라 영어로 고정합니다. 저장소 어댑터의 오류 문구는 로케일 사전(영어 기본, 한국어·일본어)을 따릅니다 (ADR-060).

### 근거

- 배열 인덱스 대신 id를 지목하면 연산 순서와 무관하게 적용되고, LLM의 인덱스 계산 오류를 원천적으로 피합니다.
- 기존 파일을 전문으로 다시 받으면 AI가 손대지 않은 요소를 조용히 빠뜨릴 수 있고, 그런 파일도 스키마상 유효해 검증으로 걸러지지 않습니다. 부분 수정은 사고 범위를 지목한 대상 안으로 가둡니다.
- base64 제외와 요약 우선 읽기는 클라이언트의 도구 응답 상한을 넘지 않기 위한 조치이며, 이미지 하나가 상한을 넘길 수 있습니다.
- 저장 시 전체 검증과 정확한 오류 반환은 별도 검증 도구 없이도 AI가 스스로 고쳐 재시도하는 흐름을 만듭니다.

### 기각한 대안

- **요소 종류별 세분 도구**: 도구 정의가 연결 시점부터 항상 컨텍스트에 올라가 상시 토큰 비용이 커지고, 서버가 디자이너의 편집 로직을 중복 구현하게 됩니다.
- **RFC 6902 JSON Patch 도구**: 배열 인덱스 계산 오류와 포인터 이스케이프 규칙이 알려진 실패 지점입니다.
- **코드 실행 도구**: 임의 코드 실행 금지 원칙(ADR-010)과 충돌합니다.

## ADR-062: 조건부 서식은 조건식과 색상 재정의 규칙으로 구성한다

**상태:** 채택

**관련 결정:** ADR-010, ADR-012, ADR-037, ADR-044

### 맥락

금액의 부호, 기한 초과 여부나 업무 상태에 따라 글자색과 배경색을 바꿔야 하는 양식이 있습니다. 현재 서식은 요소와 그리드 셀에 고정되어 있어, 양식 제작자가 양수는 파란색, 음수는 빨간색처럼 값에 따른 표시 규칙을 정의할 수 없습니다.

조건부 서식이 특정 UI나 PDF 변환 단계에만 구현되면 같은 전표가 표시 위치에 따라 다르게 보입니다. 임의 JavaScript나 호스트 콜백을 조건으로 사용하면 `.slip` 파일만으로 결과를 재현할 수도 없습니다.

### 결정

- 조건부 서식 규칙은 조건식과 색상 재정의 항목으로 구성하고 양식에 저장합니다.
- 조건식은 기존 수식 파서와 평가기를 사용하며 논리값을 결과로 반환해야 합니다. 반복 그리드 안에서는 해당 행의 목록 항목을 기존 수식과 같은 방식으로 참조합니다.
- 첫 구현 범위는 텍스트 요소, 입력 필드 요소와 그리드 셀의 `fontColor`, `backgroundColor`, `borderColor`로 제한합니다. 위치, 크기, 표시 여부와 내용은 조건부 서식으로 바꾸지 않습니다.
- 기본 서식을 먼저 적용한 뒤, 조건이 참인 규칙을 선언된 순서대로 합성합니다. 같은 속성을 여러 규칙이 바꾸면 뒤에 선언된 규칙의 값을 사용합니다.
- 조건부 서식 평가는 `core`의 공통 렌더링 경로에서 수행합니다. 디자이너의 캔버스와 샘플 미리보기, 작성 폼, 뷰어와 PDF는 같은 평가 결과를 사용합니다.
- 실제 JSON 필드명, 규칙별 식별자, 규칙 수 상한과 스키마 버전 변경 방식은 구현을 시작할 때 파일 형식 설계와 함께 확정하고 `SPEC.md`와 JSON Schema에 함께 반영합니다. 그전까지 조건부 서식은 현재 파일 형식에 포함하지 않습니다.

### 근거

- 기존 수식 엔진을 사용하면 파라미터 접근, 타입 규칙과 임의 코드 실행 금지 원칙을 그대로 적용할 수 있습니다.
- 색상만 재정의하면 값에 따른 강조 요구를 충족하면서 줄바꿈, 요소 배치와 페이지 분할에 미치는 영향을 제한할 수 있습니다.
- 여러 규칙을 순서대로 합성하면 양수·음수·기한 초과처럼 서로 다른 조건을 독립적으로 작성할 수 있고, 규칙이 겹칠 때의 결과도 명확합니다.
- 규칙을 양식에 저장하고 공통 렌더링 경로에서 평가해야 실행 환경과 무관하게 같은 결과를 재현할 수 있습니다.

### 영향

- 파일 스키마와 타입, 마이그레이션, 수식 평가 컨텍스트, 렌더 변환과 디자이너 편집 UI를 함께 변경해야 합니다.
- 반복 그리드에서는 행별 평가가 추가되므로 규칙 수와 데이터 크기에 따른 성능 검증이 필요합니다.
- MCP가 양식을 읽고 수정할 수 있도록 스키마 안내와 부분 수정 연산에도 조건부 서식 구조를 반영해야 합니다.

### 기각한 대안

- **수식이 색상 문자열이나 서식 객체를 반환**: 수식의 값 계산과 표시 규칙이 섞이고 반환 타입이 복잡해집니다.
- **임의 JavaScript 또는 호스트 콜백 사용**: 실행 환경마다 결과가 달라지고 임의 코드 실행 금지 원칙과 충돌합니다.
- **먼저 일치한 규칙 하나만 적용**: 글자색과 배경색처럼 서로 다른 속성을 별도 조건으로 조합하기 어렵습니다.
- **조건에 따라 크기, 위치나 표시 여부까지 변경**: 레이아웃과 페이지 분할을 다시 계산해야 하므로 색상 강조라는 첫 요구보다 변경 범위가 지나치게 커집니다.

## ADR-063: 조건부 서식에 글자 강조를 추가한다

**상태:** 채택

**관련 결정:** ADR-062

### 맥락

색만으로는 흑백 인쇄 양식에서 조건에 따른 강조를 표현하기 어렵습니다. 굵게, 기울임, 밑줄과 취소선은 요소의 위치와 크기를 바꾸지 않아 색과 같은 방식으로 덮어쓸 수 있습니다.

### 결정

- 조건부 서식 규칙에 `bold`, `italic`, `underline`, `strikethrough`를 추가합니다. ADR-062의 색 3종 제한을 색과 글자 강조로 확장합니다.
- 규칙은 색과 강조를 합쳐 하나 이상 지정해야 합니다.
- `true`는 강조를 적용하고 `false`는 기본 서식의 강조를 끕니다. 생략하면 기본 서식을 유지합니다.
- 굵게와 기울임은 변형 폰트 규칙(SPEC §9.3)을 그대로 따르며, 해당 변형 폰트가 없으면 적용하지 않습니다.
- 글자 크기, 글꼴, 위치, 크기와 표시 여부는 여전히 조건부 서식으로 바꾸지 않습니다.

### 근거

- 강조 4종은 요소 상자 안의 글자 표현만 바꾸므로 다른 요소의 배치와 페이지 분할에 영향을 주지 않습니다.
- 기존 서식 속성과 같은 이름·의미를 사용해 규칙 구조와 편집 UI를 그대로 확장할 수 있습니다.

### 영향

- 파일 스키마, 공통 평가 결과, 렌더 변환, 디자이너 캔버스·규칙 편집과 MCP 안내에 강조 4종을 함께 반영합니다.
- 디자이너의 규칙 편집은 강조 4종을 기본 유지(미지정)·적용(`true`)·해제(`false`) 3단계로 편집합니다.
- 캔버스는 기존 규칙대로 기울임을 표시하지 않으며, 동봉 폰트에는 Italic 변형이 없어 기울임은 호스트가 변형 폰트를 공급할 때 PDF에 적용됩니다.

### 기각한 대안

- **글자 크기까지 변경**: 상자 안 줄바꿈, 셀 축소(shrink)와 세로쓰기 배치가 글자 크기 측정에 걸려 있어 화면과 PDF가 어긋날 위험이 큽니다. 필요성이 확인되면 별도로 결정합니다.
