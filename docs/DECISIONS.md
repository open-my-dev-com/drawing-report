# 설계 결정 로그 (ADR)

> 각 결정은 번호·상태·날짜·결정 내용·근거·기각된 대안을 기록한다.
> 결정을 뒤집을 때는 삭제하지 않고 상태를 `Superseded by ADR-xxx`로 바꾼 뒤 새 ADR을 추가한다.

## ADR-001: 전표 = 범용 양식 엔진으로 정의

- 상태: 확정 (2026-08-18)
- **결정**: "전표"를 특정 서식에 고정하지 않고, 양식(템플릿)을 자유롭게 정의하는 범용 양식 엔진으로 만든다. 문서형 전표(거래명세서·청구서·견적서·영수증)와 회계형 전표(차변/대변) 모두 템플릿으로 표현한다. 양식(템플릿)과 전표 데이터(기입값)는 별도 구조로 분리한다.
- **근거**: 사용자 요구가 "자유도 보장 + 만들기 쉽게"였고, 문서형/회계형 중 하나로 한정하지 않기로 선택함. 템플릿-데이터 분리는 양식 1개로 전표 N장을 만들기 위한 전제.
- **기각된 대안**: 문서형 전용(자유도 부족), 회계 분개 전용(레이아웃 요구 미충족).

## ADR-002: 배포 형태 = 임베드형 라이브러리 (계층형 모노레포)

- 상태: 확정 (2026-08-18)
- **결정**: 서버 포함 풀스택이나 독립 실행 앱이 아닌, 호스트 앱에 임베드되는 라이브러리 패키지로 만든다. 구조는 계층형 모노레포:
  - `core` — 파일 포맷 스키마·파싱·검증·마이그레이션·수식 평가·레이아웃 엔진·PDF 렌더러 (순수 TS, DOM/프레임워크 비의존)
  - `elements` — Web Component UI
  - `react` / `vue` — 얇은 래퍼 (선택 설치)
- **근거**: 권한 호스트 위임(ADR-004) + 연계 방식(ADR-006) 선택과 맞물린다. core 분리로 파일 포맷의 레퍼런스 구현이 확보되고, Node 재사용(서버 렌더러, 백엔드 검증, CLI)이 가능해짐.
- **기각된 대안**: 풀스택(권한 위임 결정과 모순), 독립 앱(임베드 요구와 모순).

## ADR-003: UI 배포 = Web Component + 프레임워크별 얇은 래퍼

- 상태: 확정 (2026-08-18)
- **결정**: UI를 커스텀 엘리먼트(`<voucher-designer>`, `<voucher-viewer>` 등)로 배포한다. React/Vue 사용자를 위해 각 프레임워크 관례로 감싼 얇은 래퍼 패키지를 별도 제공한다. 내부 구현 프레임워크는 미정(OPEN Q-01) — 배포 형태와 내부 구현은 별개다.
- **근거**: 사용자 요구 "설치할 쪽이 뭐든 상관없이 연계되는 게 베스트". React 전용으로 만들면 Vue 등에서 사용 불가함을 확인하고 범용성을 1순위로 선택.
- **기각된 대안**: React 전용(범용성 없음), 프레임워크별 개별 포팅(유지보수 비용 배수 증가).

## ADR-004: 권한제어 = 호스트 앱에 위임

- 상태: 확정 (2026-08-18)
- **결정**: 패키지는 자체 유저/인증 시스템을 갖지 않는다. 컴포넌트가 `mode`(edit/view)·권한 플래그를 속성으로 받고, 인증과 권한 판단은 설치한 호스트 앱이 책임진다.
- **근거**: 패키지툴로서 가장 가볍고 표준적인 방식. 어떤 호스트의 기존 인증 체계와도 충돌하지 않음.
- **기각된 대안**: 자체 권한 시스템(무겁고 호스트와 이중화), 파일 레벨 보호만(권한 모델로는 부족 — 단 파일 보호는 ADR-009로 별도 채택).

## ADR-005: 양식 제작자 = 일반 사용자, GUI 디자이너 필수

- 상태: 확정 (2026-08-18)
- **결정**: 양식(템플릿)은 비개발자가 드래그앤드롭 GUI 디자이너로 직접 설계한다. GUI 디자이너가 이 프로젝트의 중심 결과물이다.
- **근거**: 사용자가 "일반 사용자 (GUI 필수)"를 명시적으로 선택. "만들기는 쉽게"의 대상이 개발자가 아닌 최종 사용자임이 확정됨.
- **파급 효과**: 수식도 GUI에서 다뤄져야 하므로 내장 수식 엔진(ADR-010)이 사실상 필수가 됨. 개발 비용의 중심이 디자이너 UI에 놓임.

## ADR-006: 외부 연계 = 데이터 주입 + 저장소 어댑터 + 표준 파일 포맷

- 상태: 확정 (2026-08-18)
- **결정**: 연계 방식은 3가지 — ① 호스트 앱 데이터 주입(바인딩), ② 저장소 어댑터(저장/불러오기 인터페이스 추상화 — 로컬 파일·S3·DB·자체 서버 등), ③ 표준 교환 파일 포맷(파일 자체를 명세화). REST API 서버 제공은 범위 제외.
- **근거**: 사용자가 3가지를 복수 선택, REST API는 미선택. 임베드형 라이브러리(ADR-002) 결정에 부합.

## ADR-007: 파일 포맷 = JSON 기반 자체 스키마 (ZIP 컨테이너 확장 경로 확보)

- 상태: 확정 (2026-08-18)
- **결정**:
  - 내용은 JSON, 구조는 자체 정의 스키마, 전용 확장자 사용(명칭은 OPEN Q-03).
  - 모든 파일에 `schemaVersion`을 내장하고, 구버전 파일 자동 마이그레이션 계층을 core에 처음부터 만든다.
  - 이미지는 `src` 필드로 통일: 외부 URL / `data:` base64 내장 / `asset://` 내부 리소스 참조의 3종을 동일하게 취급.
  - v1은 순수 JSON 단일 파일. 대용량 리소스가 필요해지면 동일 JSON을 manifest로 하는 ZIP 컨테이너(docx 방식)를 추후 추가한다. `asset://` 참조 구조가 이 확장의 장치이며, 컨테이너 추가 시 스키마 변경이 없어야 한다.
- **근거**: 이미지 "링크 표시"는 JSON에 부담이 없고, 내장은 base64로 시작 가능. 복수 페이지는 포맷이 아닌 스키마 설계 문제. JS 생태계 궁합(파싱·검증·디프)이 XML 대비 우수. 사용자 질문("이미지 링크·복수 페이지에도 JSON이 강세인가")에 대한 검토를 거쳐 확정.
- **기각된 대안**: XML(도구 생태계 열세), 처음부터 ZIP(초기 복잡도 불필요).

## ADR-008: 양식 버저닝 = 전표 파일에 생성 시점 스냅샷 내장

- 상태: 확정 (2026-08-18)
- **결정**: 전표 파일은 생성 당시 양식 전체를 복사해 내장한다. 발행된 전표는 이후 양식이 수정되어도 절대 모양이 바뀌지 않으며, 양식 저장소 없이 파일 단독으로 열람 가능하다(자기완결).
- **근거**: 전표의 회계·증빙 성격상 "발행 당시 모습 보존"이 필수. 표준 교환 파일 포맷(ADR-006)에도 부합 — 파일 하나로 완결되므로 타 시스템이 참조 해소 없이 읽을 수 있음.
- **기각된 대안**: templateId@version 참조(양식 저장소 없으면 열람 불가), 최신 양식 참조(발행 당시 모습 훼손 — 전표 용도에 위험).
- **트레이드오프 인지**: 파일 용량 증가. 스냅샷 내장을 택한 대가로 수용.

## ADR-009: 파일 보안 = 위변조 방지 서명 기본 + 암호화 옵션

- 상태: 확정 (2026-08-18)
- **결정**:
  - 전표 내용의 해시/서명을 파일에 내장하여 발행 후 무결성을 검증 가능하게 한다(기본 제공).
  - 파일 내용 암호화를 옵션으로 제공한다. 키 관리는 호스트 책임. 암호화 파일은 표준 교환성이 제한됨을 명세에 명시한다.
  - 서명 방식 상세(해시 vs 공개키 서명, 키 관리 흐름)는 OPEN Q-04.
- **근거**: 전표는 "숨기기(암호화)"보다 "위변조 안 됐음 보장(서명)"이 우선이라는 검토에 사용자 동의, 둘 다 선택하되 서명이 기본.

## ADR-010: 계산 필드 = 내장 수식 엔진 (엄선된 함수 세트, 안전한 자체 파서)

- 상태: 확정 (2026-08-18)
- **결정**: 양식 필드에 엑셀 스타일 수식 문자열을 지원하는 수식 엔진을 core에 내장한다. 함수는 전부 넣지 않고 자주 쓰이는 것을 엄선한 세트로 시작한다(집계/산술/문자열/조건/포맷/날짜 — 스타터셋 확정은 OPEN Q-02). 수식은 자체 파서로 해석하며 임의 코드 실행(`eval` 등)은 절대 금지.
- **근거**: 일반 사용자가 GUI로 양식을 만드는 이상(ADR-005) 합계란·치환 등의 계산을 사용자가 직접 정의할 수 있어야 함. 사용자가 "자주 쓰는 수식을 추리고 싶다(문자열 자르기·치환, 더하기, 평균 등)"고 방향을 명시.
- **기각된 대안**: 호스트가 계산해 값만 주입(일반 사용자가 양식에 계산란을 못 넣음), 전체 함수 일괄 제공(범위 통제 불가).

## ADR-011: 레이아웃 = 용지 기준 좌표계, 복수 페이지 1급, 자동 페이지 분할 필수

- 상태: 확정 (2026-08-18)
- **결정**: 양식은 용지 크기(A4 등) 기준의 절대 좌표계로 설계한다. 페이지는 스키마의 1급 개념(`pages`)이며, 표(품목 리스트)가 페이지를 넘치면 자동으로 다음 페이지로 분할한다(헤더 반복·페이지별 소계 옵션 포함). 자동 분할은 v1 필수 기능이다.
- **근거**: 인쇄·PDF 필수 선택 + 사용자가 "자동 페이지 분할 필수"를 명시적으로 선택. 레이아웃 엔진 난이도가 최상급이 됨을 인지하고 결정.

## ADR-012: 렌더링 파이프라인 = 렌더 트리 기반, PDF는 브라우저 직접 생성

- 상태: 확정 (2026-08-18) — 일부 조정: 레이아웃·PDF 생성의 실행자는 ADR-016(pdfme 엔진)으로 확정. 파이프라인 원칙(좌표 계산 단일화, 브라우저 직접 생성, DOM 캡처 금지, 폰트 서브세팅, 서버 렌더러 = 호스트 인프라)은 그대로 유효.
- **결정**:
  - 파이프라인: `양식+데이터 → 레이아웃 엔진(core, 순수 TS·DOM 비의존) → 렌더 트리(용지 좌표 기반 그리기 명령) → 화면 렌더러 / PDF 렌더러`. 좌표 계산은 core에서 한 번만 — 화면·인쇄·PDF 불일치가 구조적으로 불가능.
  - PDF는 브라우저에서 클라이언트 직접 생성(pdf-lib 계열). 서버 왕복 없고 전표 데이터가 브라우저 밖으로 나가지 않는다. DOM 캡처(스크린샷→이미지 PDF) 방식은 금지.
  - 인쇄는 생성된 PDF를 인쇄하는 방식으로 통일.
  - 폰트는 PDF에 내장하되 한글 폰트는 사용 글자만 서브세팅. 기본 한글 폰트 1종 동봉 + **사용자 폰트 업로드/등록 지원**(사용자 확정 요구).
  - 서버 렌더러는 추후 확장: 동일 core+PDF 렌더러를 Node 패키지(`render-node` 등)로 재포장해 호스트 인프라에서 일괄 발행 자동화에 사용. headless 브라우저 불필요. **제3자 외부 서버는 어떤 경우에도 개입하지 않는다.**
- **근거**: 자동 페이지 분할(ADR-011) 때문에 정교한 레이아웃 계산이 어차피 필요 → 렌더 트리 방식의 추가 비용이 상대적으로 작고, 벡터 텍스트·픽셀 일치·Node 재사용을 모두 얻음. "서버 렌더러 = 호스트 인프라에서 실행"임을 사용자에게 확인받고 확정.
- **기각된 대안**: DOM 캡처(래스터 품질·분할 문제), print CSS만(자동화 불가·브라우저 편차), v1부터 서버 렌더러 포함(현재 필요 없음, 추후 재포장으로 충분).

## ADR-013: i18n = 한국어 우선, 구조만 선확보

- 상태: 확정 (2026-08-18) — **영어 UI 추가는 ADR-028** (v1 언어를 한국어·영어 2종으로 확장, 기본은 한국어 유지)
- **결정**: v1의 UI 언어는 한국어. 단 UI 문구는 처음부터 리소스 파일로 분리하고, 통화·날짜 포맷 함수는 로케일 지정이 가능하게 설계해 추후 언어 추가 시 재작업이 없게 한다.
- **근거**: 초기 속도와 확장 가능성의 균형. 사용자 선택.

## ADR-014: 이미지(asset) 처리 = 하이브리드 (작성 중 URL 허용, 발행 시 내장)

- 상태: 확정 (2026-08-18)
- **결정**: 전표 작성·편집 중에는 외부 URL 이미지 참조를 허용하되, **전표를 발행(확정)하는 시점에 이미지를 base64로 파일에 내장**한다. 파일 포맷은 순수 JSON 단일 파일을 유지하며, ZIP 컨테이너는 추후 확장 슬롯으로만 예약(ADR-007에 부합).
- **근거**: 발행된 전표는 파일 단독 완결이어야 함(ADR-008 스냅샷 원칙과 동일한 논리 — 외부 URL은 언제든 죽거나 바뀔 수 있어 증빙 성격과 모순). 반면 작성 중에는 호스트 앱 CDN의 이미지(로고 등)를 가볍게 참조하는 것이 실용적.
- **기각된 대안**: 항상 내장(양식 파일이 항상 무겁고 CDN 활용 불가), 처음부터 ZIP(초기 복잡도).

## ADR-015: Web Component 내부 구현 = Lit

## ADR-016: PDF 생성 엔진 = pdfme 채택 (렌더러 인터페이스 뒤로 외부 비공개)

- 상태: 확정 (2026-08-18) — OPEN Q-08 해결, 평가 근거: docs/Q08-PDFME-EVAL.md
- **결정**:
  - `@pdfme/generator`·`@pdfme/schemas`·`@pdfme/common`(MIT)을 core 내부의 **PDF 생성·페이지 분할 실행 엔진**으로 채택한다.
  - 채택 범위는 엔진까지만이다. UI(디자이너/뷰어/작성폼), 전표 파일 포맷, 서명, 수식, 저장소 어댑터, 권한 인터페이스는 전부 자체 개발한다. pdfme의 React 기반 `@pdfme/ui`는 사용하지 않는다(ADR-003/015 유지).
  - 우리 전표 파일 포맷이 진실의 원천이며, pdfme 템플릿은 core가 내부에서 **생성 시점에 변환·조립하는 중간 표현**이다. pdfme 의존은 core의 렌더러 인터페이스 뒤에 두어 외부에 공개하지 않으며, 유사시 자체 렌더러로 교체 가능한 구조를 유지한다.
  - pdfme 테이블 스키마는 스타일 속성 불완전 시 조용히 깨지므로(직접 확인), 변환 계층에서 **기본값 병합을 필수**로 한다.
- **근거**: 평가(Q08-PDFME-EVAL.md)에서 최고 난도 요구 전부 통과 — A4 자동 페이지 분할(ADR-011), 분할 시 헤더 반복, 한글 렌더링·폰트 서브세팅(10.4MB→20KB, ADR-012), 템플릿 루트 확장 필드 수용, 샌드박스 표현식 평가, 2페이지 생성 ~260ms.
- **기각된 대안**: 전부 자체 개발(가장 어려운 구간을 재발명, 기간 대폭 증가), pdfme UI까지 전면 채택(ADR-003·015와 충돌).
- **영향**: ADR-012의 파이프라인 원칙(좌표 계산 단일화, 브라우저 직접 생성, DOM 캡처 금지)은 유지하되, "렌더 트리 직접 구현" 부분은 pdfme가 실행자가 되는 것으로 조정. ADR-012의 pdf-lib 계열 = pdfme 유지보수 포크로 자연 충족.

## ADR-019: 서명 상세 = SHA-256 해시 필수 + JWS(ES256) 서명 옵션

- 상태: 확정 (2026-08-18) — OPEN Q-04 해결
- **결정**:
  - 모든 발행(확정) 파일에 **SHA-256 내용 해시를 항상 내장**한다. 키 없이 훼손·변조를 탐지할 수 있는 기본 무결성 계층이다.
  - 호스트가 키를 제공하면 **JWS(ES256, 공개키 서명)**를 추가로 내장하여 "누가 발행했는지"까지 증명한다(옵션). 서명 주체·키 관리는 호스트 책임(ADR-004 권한 위임 원칙에 부합 — 통상 호스트 서버가 서명).
  - 해시·서명의 대상 범위는 **내장 양식 스냅샷을 포함한 전표 내용 전체**다(스냅샷 위조로 발행 당시 모습을 바꾸는 것도 막아야 하므로).
  - 해시·서명 계산의 전제로 **JSON 정규화(canonicalization) 규칙을 스펙에 명시**한다(같은 내용이면 항상 같은 바이트가 되도록 — 키 정렬 등).
- **근거**: 해시만으로는 재계산 위조가 가능하고, 서명 필수는 도입 장벽이 높음. 단계적 구조가 ADR-009의 "서명 기본 + 실용성"을 모두 충족. 사용자 선택.
- **기각된 대안**: 해시만(위조 방지 불가), 서명 필수(키 없는 호스트는 발행 불가).

## ADR-020: GUI 디자이너 v1 범위 = 실사용 최소선 + 셀 병합·색 스타일

- 상태: 확정 (2026-08-18) — OPEN Q-05 해결
- **결정**:
  - 요소 6종: 텍스트, **고정 그리드 표**(행 수 고정 틀 — 공급자 정보란 등), **동적 행 표**(품목 리스트 — 자동 페이지 분할 대상), 이미지, 선/사각형, 입력 필드.
  - **셀 병합: 고정 그리드 표에서 지원**(변환 계층이 선·텍스트로 분해해 렌더하므로 pdfme 제약 없음). 동적 행 표의 셀 병합은 v2(pdfme 자동 분할 표에 병합 개념이 없음).
  - **색 스타일 지원**: 전 요소에 배경색·글자색·테두리색(+두께·스타일) 지정 가능.
  - 편집 편의: 열 너비 조절, 스냅·정렬 가이드, undo/redo, 복사/붙여넣기.
  - 기본 프리셋 2종 동봉: 거래명세서, 청구서.
  - v2로 미루는 것: 동적 행 표 셀 병합, 요소 그룹화, 레이어 패널, 표 중첩, 프리셋 확충.
- **근거**: 일반 사용자 대상(ADR-005)이라 undo·스냅 없는 에디터는 체감 품질 미달. 사용자가 "실사용 최소선보다 조금 더 — 셀 병합·색 포함"을 명시 선택. 전표 양식의 병합 수요는 고정 그리드(머리부 틀)에 집중되므로 표를 2종으로 분리해 병합을 v1에 안전하게 포함.

## ADR-021: 저장소 어댑터 = CRUD + 목록·검색, 버전 이력은 선택 인터페이스

## ADR-022: 파일 포맷 스펙 = 명세서 공개 + JSON Schema 동봉

## ADR-023: 브랜치 전략 = 규칙 기반 분기

- 상태: 확정 (2026-08-18)
- **결정**: 이후 모든 작업은 브랜치 규칙 문서에 정의한 규칙대로 브랜치를 분기해 진행한다. 요지: `main`은 보호(직접 커밋 금지, PR 병합만), 작업 브랜치는 `<type>/<scope>-<topic>` 형식(`feat|fix|docs|proto|chore` × 패키지 스코프), 커밋은 Conventional Commits.
- **근거**: 사용자 지시 — "다음 작업은 브랜치 분기 후, 생성 브랜치는 규칙을 정해놓고 규칙대로 분기할 것".
- **이관 (2026-08-18)**: 규칙 본문은 처음 `docs/BRANCHING.md`에 있었으나, 세션 자동 적용을 위해 [`.claude/rules/branching.md`](../.claude/rules/branching.md)로 통합·이동하고 원본 파일은 제거했다 (ADR-024). 기록: 부트스트랩(요구사항 Q&A·ADR-001~023·pdfme 평가)은 `claude/package-voucher-tool-dorcwu` 브랜치에서 진행되었고, main 병합 시점부터 규칙이 전면 적용되었다.

## ADR-024: 개발 규칙 강제 = CLAUDE.md + .claude/ 4계층 (rules·hooks·skills·settings)

- 상태: 확정 (2026-08-18)
- **결정**: Claude Code 공식 문서를 리서치해, 개발 규칙을 성격에 맞는 계층에 나눠 리포에 규정한다.
  | 계층 | 파일 | 역할 |
  |---|---|---|
  | 지침(항상 로드) | `CLAUDE.md` + `.claude/rules/branching.md` | 문서·코드 불변 규칙·검증 게이트 / 브랜치·커밋·PR·작업 시작 절차. `@docs/ROADMAP.md` 임포트 |
  | 경로 스코프 규칙 | `.claude/rules/{core,ui-packages,docs}.md` | 해당 경로 파일을 다룰 때만 자동 로드되는 상세 규칙 (`paths` frontmatter) |
  | 기계적 차단 | `.claude/settings.json` `permissions.deny` + PreToolUse 훅 `.claude/hooks/bash-guard.mjs` | main 푸시·커밋 차단(지침 무관 강제), `git commit` 시 검증 게이트(typecheck·build·test) 자동 실행·실패 시 커밋 차단 |
  | 절차 명령 | `.claude/skills/{next-task,verify}/SKILL.md` | `/next-task`(로드맵 다음 작업을 규칙대로 시작), `/verify`(검증 게이트 실행·보고) |
  - **병합 방식 확정**: `main`은 스쿼시 머지 전용. **미병합 브랜치 위 PR 스택 금지**, 자기 PR은 한 번에 하나만 진행, 브랜치당 커밋 최소화(가급적 1커밋).
  - 원격 Claude 세션이 `claude/*` 등 임의 브랜치명을 지정해도 실제 작업·푸시·PR은 브랜치 규칙 형식(`<type>/<scope>-<topic>`) 브랜치로 한다.
- **근거**: 사용자 지시(2026-08-18) — 규칙이 세션 간 유지되지 않아 위반 사례 발생(세션 지정 `claude/*` 브랜치 사용, 미병합 브랜치 위 PR 스택 → 스쿼시 머지 시 충돌). 공식 문서 리서치: CLAUDE.md·rules는 매 세션/해당 파일 작업 시 자동 로드되는 지침 계층(구체·간결할수록 준수율 최고)이고, 100% 강제는 hooks(종료 코드 2 = 차단)·permissions 계층 담당 — 지침과 강제를 병행해야 완전하다.
- **한계 인지**: 지침 계층(CLAUDE.md·rules)은 준수를 유도할 뿐 하드 강제가 아니다. 하드 강제는 훅이 담당하며, 훅이 커버하지 못하는 새 위반 패턴이 발견되면 `bash-guard.mjs`에 추가한다.

## ADR-025: 저장소 어댑터 구현 위치 = 인터페이스는 core, 브라우저 구현은 elements

- 상태: 확정 (2026-08-19) — OPEN Q-09 해결
- **결정**:
  - 어댑터 인터페이스·타입·오류(`StorageAdapter`, `SlipStorageError` 등)는 `@slipkit/core`에 둔다. 호스트가 자체 어댑터(S3·DB 등)를 구현할 때는 core만 있으면 된다.
  - 기본 동봉 브라우저 구현 2종 — ① IndexedDB(`IndexedDbStorage`), ② 로컬 파일 다운로드/업로드(`LocalFileStorage`) — 는 `@slipkit/elements`에 둔다.
  - 로컬 파일 어댑터는 매체 특성상 `delete`/`list`를 지원할 수 없으므로 호출 시 `unsupported` 코드의 `SlipStorageError`를 던진다. 호스트 UI는 이 코드를 보고 해당 기능을 숨길 수 있다.
- **근거**: core는 순수 TS(ADR-002)로 tsconfig에서 DOM 타입을 차단하고 있어 브라우저 API(IndexedDB, 파일 다운로드/업로드 DOM 조작) 구현을 둘 수 없다. 대부분의 호스트가 뷰어·디자이너(elements)와 함께 쓸 것이므로 패키지를 늘리지 않고 현행 4패키지 구조를 유지하는 쪽을 사용자가 선택했다 (2026-08-19).
- **기각된 대안**: ① 새 패키지 `@slipkit/storage`(분리는 깔끔하나 관리할 패키지가 하나 늘어남), ② core에 DOM lib 추가(ADR-002 위반 — 서버 사용 시나리오가 깨짐).

## ADR-029: 소스 주석 표준 = TSDoc

- 상태: 확정 (2026-08-19)
- **결정**: 선언(공개 API, 클래스 멤버, 인터페이스·타입 필드, 상수 등)에 붙는 설명 주석은
  **TSDoc 블록(`/** ... */`)**을 표준으로 한다. 공개(export) 함수·메서드는 `@param`
  (매개변수마다)·`@returns`를 기본으로 채우고, 오류를 던지면 `@throws`로 조건을 명시한다
  (void·무인자면 해당 태그 생략). `@remarks`·`@defaultValue`·`@example` 등 나머지 태그는
  덧붙일 정보가 있을 때 쓴다. 코드 중간의 구현 설명은 `//` 한 줄
  주석을 유지한다(TSDoc은 선언 설명 전용). 주석 본문은 한국어. 규칙은
  [`.claude/rules/comments.md`](../.claude/rules/comments.md)로 세션에 자동 적용한다.
- **근거**: TypeScript 언어 서비스는 `/** */` 블록만 문서 주석으로 인식한다 — 같은 내용이라도
  `//`로 쓰면 에디터 호버·자동완성·산출 `.d.ts`에 노출되지 않는다. 기존 코드가 이미 두 형식을
  혼용하고 있어(TSDoc 블록 약 150개, 선언 위 `//` 주석 혼재) 표준을 정해 통일한다.
- **보류**: eslint-plugin-tsdoc 기계 검증 도입은 리포에 처음으로 lint 도구를 넣는 검증 게이트
  구성 변경이라 별도 쟁점(Q-11)으로 분리했다.

## ADR-030: TSDoc 형식 기계 검증 도입 (eslint + tsdoc/syntax만)

- 상태: 확정 (2026-08-19) — OPEN Q-11 해결
- **결정**: 리포 루트에 eslint 최소 구성을 추가하고 규칙은 `tsdoc/syntax`(eslint-plugin-tsdoc)
  **하나만** 켠다. `pnpm lint`를 검증 게이트 맨 앞 단계로 추가한다
  (`pnpm lint && pnpm -r typecheck && pnpm -r build && pnpm -r test`) — 커밋 훅(bash-guard)도
  같은 명령을 강제한다.
  - 잡는 것: 오탈자·비표준 태그, JSDoc식 타입 중괄호(`@param {string}`), `@param 이름 - 설명`의
    하이픈 누락, 이스케이프 안 된 `<`·`>` 등 TSDoc 문법 위반.
  - 안 잡는 것: `@param`·`@returns` 누락, 매개변수 이름 불일치 — 지침
    ([`.claude/rules/comments.md`](../.claude/rules/comments.md))과 리뷰로 유지한다.
- **근거**: 최신 eslint-plugin-tsdoc(0.5.2, 2026-02)까지 규칙이 `syntax` 하나뿐임을 패키지
  소스로 직접 확인했다. 누락 검사까지 하려면 eslint-plugin-jsdoc 조합이 필요한데, 사용자가
  구성 단순함을 우선해 tsdoc 플러그인만 넣는 쪽을 선택했다 (2026-08-19). 도입 직후 첫 실행에서
  형식 위반 61건(하이픈 누락 등)을 잡아 수정했다 — 형식 검사만으로도 실효가 있음을 확인.
- **기각된 대안**: ① 도입하지 않음(지침만) — 형식 오탈자를 사람이 계속 잡아야 함,
  ② eslint-plugin-jsdoc 조합(누락까지 강제) — 검사 범위는 넓지만 JSDoc 방언 옵션 조정 등
  구성이 복잡해짐. 필요해지면 규칙 추가로 확장 가능.

## ADR-031: v2 범위 확정 — 디자이너 사용 편의 중심

- 상태: 확정 (2026-08-19) — 사용자가 직접 화면을 점검하며 요구를 제시하고, 세부 확정은 위임함
- **테마**: v2는 새 능력 추가보다 **"디자이너를 일반 사용자가 실제로 쓸 수 있는 도구로"** 다듬는
  데 집중한다. v1에서 파일 포맷·렌더러는 지원하지만 GUI가 따라가지 못한 구간(표 내부 편집,
  이미지 넣기, 용지 설정 등)을 채우는 것이 중심이다.

### 기술 방향

- **UI 기술은 Lit 유지**(ADR-015), 스타일은 **자체 CSS + 디자인 토큰**(색·간격·글꼴 변수) 정리로
  현대화한다.
  - 기각: MUI(React 전용 — Lit 구조에 도입 불가), Tailwind(Shadow DOM에 생성 CSS를 주입하는
    빌드 구성이 필요해 복잡도가 늘고, 컴포넌트 라이브러리라 유틸 클래스 공유 이점이 없음).
- **기본 한글 폰트 동봉 = Pretendard**(OFL 라이선스) Regular·Bold 2종. 뷰어·디자이너가 폰트
  미지정 시 자동 사용해 미리보기 한글 깨짐을 없앤다 — **ADR-012의 "기본 한글 폰트 1종 동봉"
  미이행분의 이행**이다. elements의 서브패스 export로 동봉해 쓰지 않는 호스트의 번들에는
  들어가지 않게 한다.

### 파일 포맷 개정 (스키마 0.2.0 — 1회로 묶어 마이그레이션 1번)

- **동적 표 열 구조**: `head: string[]`(제목이 곧 데이터 키) → 열 객체 배열(**데이터 키·표시
  제목·너비 분리**). 제목을 바꿔도 데이터·수식이 깨지지 않게 한다. 기존 문서는 키=제목으로
  자동 마이그레이션.
- **선**: 시작점·끝점 좌표 방식 도입(사선 가능). 도형 종류에 **타원·삼각형** 추가.
- **글자 스타일**: 굵게·밑줄·취소선 필드 추가. 밑줄·취소선은 PDF 엔진 직접 지원, 굵게는 폰트
  변형(동봉 Bold) 사용. **기울임은 제외** — 한글 폰트는 이탤릭 변형이 거의 없고 기울이기 흉내는
  인쇄 품질을 해친다. 이탤릭 변형 폰트를 직접 등록한 경우 폰트 선택으로 대응.
- **샘플 값**: 양식 파일에 선택 필드 `sampleValues` 추가 — 미리보기용 시험 데이터를 양식에
  보관한다(발행·무결성과 무관, 전표 생성 시 미포함).
- **요소 그룹화**: 요소에 그룹 식별 필드 추가(0.2.0에 포함). 그룹 편집 UI는 고급 편집 묶음에서.
- 동적 표 **셀 병합**과 **표 중첩**은 설계 난도가 높아(PDF 엔진의 표가 병합을 직접 지원하지
  않음 — 고정 그리드처럼 분해 렌더 방식 검토 필요) 0.2.0에 밀어 넣지 않고 **별도 개정
  (0.3.0)**으로 고급 편집 묶음에서 처리한다.

### 디자이너 UX 확정

- **요소 생성**: 툴바에서 도구를 고른 뒤 **캔버스 드래그 = 위치·크기 지정 생성**, 클릭만 하면
  그 위치에 기본 크기로 생성. 기존 "버튼 누르면 즉시 생성"은 대체한다.
- **툴바**: 아이콘 버튼 + 툴팁. 정렬 등 택일 속성은 아이콘 토글 그룹.
- **색 입력**: 팔레트 견본 + 브라우저 색상판 + 직접 입력 병행, 투명도 슬라이더(#RRGGBBAA) 포함.
- **캔버스**: 글자 크기·정렬·색을 즉시(근사) 반영. 인쇄와 픽셀 일치하는 화면은 PDF 미리보기가
  담당하는 구조(ADR-012)는 유지. 선의 캔버스 대각선 표시 버그(실제 PDF는 직선)는 v2 첫 작업.
- **속성 패널**: 가로 스크롤 제거. 요소 미선택 시 "양식 설정"(제목·용지 크기·방향·여백 4방향)
  표시 — v1 요구(§10 용지 설정)의 미이행분 이행.
- **왼쪽 사이드바 신설**: ① 페이지 썸네일(클릭 이동·추가·삭제) ② 요소(레이어) 목록
  ③ 바인딩 값 목록. 화면은 "사이드바 + 캔버스 + 속성 패널" 3단.
- **표 내부 편집**: 고정 그리드 — 행·열 수 변경, 셀 클릭 텍스트 입력, 병합/해제. 동적 표 —
  열 추가·삭제, 제목·데이터 키·너비 편집(콤마 나열 입력 폐지). 새 동적 표는 빈 제목 3열로 시작.
- **이미지**: 파일 업로드(base64 내장, 큰 파일은 에셋 등록 안내) + URL 입력 + `asset://` 재사용.
- **수식 편집 모달**: 함수 29종을 분류·설명·클릭 삽입, 바인딩 값 목록 동시 표시, 실시간 문법
  검사(파서 오류 위치 활용), 샘플 값이 있으면 결과 미리 계산.
- **미리보기 샘플 데이터**: `sampleValues`를 편집해 동적 표 행을 채운 상태로 PDF 미리보기.
- **전표 작성폼 신설**: `<slip-form>` — 양식의 필드를 입력폼으로 펼쳐 값 입력, 동적 표 행
  추가, 수식 즉시 계산, 발행(무결성 기록)까지. 값 채움~발행 구간을 GUI로 제공한다.
- **프리셋·양식 관리**: 호스트가 프리셋 배열을 주입하는 공개 API + "현재 양식을 내 양식으로
  저장"(저장소 어댑터 경유) + 제목별 목록에서 불러오기. 양식 제목 편집 UI 포함, 파일 내보내기
  기본 파일명 = 양식 제목.
- **데모 개선**: 자동 저장·복원(브라우저 보관), 사용자 문구에서 기술 용어(IndexedDB 등) 제거.

## ADR-032: 파일 포맷 0.2.0 상세 확정 — 표 열 구조·자유 선·도형·글자 스타일·바인딩 정의부

- 상태: 확정 (2026-08-20). ADR-031이 정한 0.2.0 범위의 세부를 확정한다.
  각 항목은 PDF 변환 계층(pdfme 6.x)이 실제로 그리는지 직접 렌더해 확인한 결과를 따른다
  (화면·PDF 일치 원칙, ADR-012/016).

### PDF 변환 지원 확인 결과 (2026-08-20 직접 렌더 확인)

| 기능 | 결과 | 방식 |
|---|---|---|
| 기울어진 선(사선) | 지원 | line 스키마 + rotate(중심 회전) |
| 타원 | 지원 | ellipse 플러그인 |
| 삼각형 | 지원 | svg 플러그인(polygon) |
| 사각형 모서리 반경 | 지원 | rectangle 스키마 radius |
| 밑줄·취소선 | 지원 | text 스키마 underline/strikethrough |
| 굵게 | 지원 | 굵은 폰트로 전환(동봉 Pretendard-Bold) |
| 파선·점선 | **직선만 지원** | svg의 stroke-dasharray는 무시됨(실선으로 그려짐). 변환 계층이 짧은 선분 여러 개로 분해해 그리면 정상 — 직선(선 요소·사각형 테두리·고정 그리드선)에만 적용 가능, 곡선(타원) 테두리는 실선 고정 |

### 스키마 변경 (0.1.1 → 0.2.0, 마이그레이션 1단계)

- **동적 표 열 구조**: `head: string[]` + `headWidthPercentages: number[]` →
  `columns: { key, title, widthPercentage }[]` (물리 데이터 키·표시 제목·너비 분리).
  행 데이터는 `key`로 읽고 머리행에는 `title`을 표시한다. `key` 중복 금지, 너비 합 100±0.01.
  마이그레이션: `columns[i] = { key: head[i], title: head[i], widthPercentage: headWidthPercentages[i] }`
  — 기존 전표 값(제목=키)과 그대로 호환된다.
- **선 방향**: 선 요소에 `lineDirection: 'horizontal' | 'vertical' | 'down' | 'up'`
  (기본 horizontal). down = 좌상→우하 대각선, up = 좌하→우상 대각선 — 상자(position·width·height)의
  두 모서리를 잇는다. ADR-031의 "시작점·끝점 좌표" 의도를 유지하되, 임의 선분은 상자+방향으로
  1:1 표현 가능하므로 **위치·크기 공통 필드와 중복되는 좌표를 두지 않는 인코딩**으로 확정.
  드래그 생성·크기 조절·스냅 등 기존 상자 편집이 그대로 동작한다.
  - 기각: `start`/`end` 좌표 필드 — 요소 공통 position·width·height와 같은 정보를 두 번 저장하게
    되어 불일치 여지가 생긴다.
- **도형을 독립 요소 타입 4종으로 분리**: `shape` 요소를 없애고 `line`·`rect`·`ellipse`·
  `polygon`을 각각 요소 타입으로 둔다 (요소 6종 → 9종). 종류마다 의미 있는 스타일이 다르기
  때문이다 — 선은 색·굵기·형태·방향만, 사각형은 배경·테두리·반경, 타원·정다각형은 배경·테두리
  (실선 고정). 잘못된 조합(선의 배경색 등)이 스키마 차원에서 불가능해지고, 속성 패널도 타입별로
  정확한 항목만 보여줄 수 있다.
  - **정다각형은 `sides`(변 수 3~12) 필드 하나로 일반화** — 3=삼각형, 5=오각형, 6=육각형처럼
    변 수만 바꿔 여러 도형을 표현한다. 오각형·육각형을 이름별 타입으로 늘리면 타입이 계속
    불어나므로 기각. 꼭짓점은 첫 점 위쪽으로 상자에 꽉 차게 정규화(삼각형 = 위 꼭짓점·아래 밑변).
  - 타원·정다각형은 상자에 내접.
  - 기각: `shape` 필드 하나에 4종을 담는 방식 — 종류별 전용 필드를 검증 규칙으로 막아야 하고,
    "도형 종류를 선→사각형으로 바꾸는" 어색한 전환이 생긴다.
  - UI: 툴바도 선·사각형·타원·다각형 4개 도구로 분리. 선 도구는 드래그한 시작점→끝점 방향
    그대로 사선이 생기고, 캔버스에서 선·타원·다각형은 상자 테두리 없이 도형만 보인다.
    다각형 도구의 기본은 삼각형(변 3), 변 수는 속성 패널에서 3~12로 조절. **도형 선택 메뉴**
    (도형 버튼 → 삼각형·오각형·육각형 등 선택지 펼침, 프리셋 메뉴와 같은 방식)는 C-11에서.
- **사각형 모서리 반경**: 사각형 요소에 `radius?`(mm). 파선·점선 테두리와 동시 지정 금지
  (모서리 곡선 구간은 분해 렌더가 불가능) — 검증에서 거부.
- **테두리 형태 렌더 규칙**: 기존 `borderStyle`(solid/dashed/dotted) 필드는 유지하고 0.2.0에서
  **렌더 의미를 확정**한다: 선 요소·사각형(radius 미지정)·고정 그리드선에만 적용(분해 렌더),
  그 밖(텍스트·필드 테두리, 동적 표, 타원·삼각형)은 실선 고정. 파선 = 2.4mm 선 + 1.2mm 간격,
  점선 = 0.4mm 점 + 0.8mm 간격.
- **글자 스타일**: 텍스트·필드·고정 그리드 셀에 `bold`·`underline`·`strikethrough`(boolean, 선택).
  밑줄·취소선은 PDF 엔진 직접 지원. 굵게는 **폰트 전환 규칙**: 유효 폰트 이름(요소 fontName,
  없으면 대체 폰트)에 대해 `<이름>-Bold` 폰트가 렌더 옵션에 있으면 그 폰트로 그린다.
  없으면 굵게는 PDF에서 무시된다(SPEC에 명시) — 동봉 기본 폰트는 Pretendard-Bold가 있어 항상 적용된다.
- **샘플 값**: 양식 본문에 `sampleValues?: Record<string, JSON값>` — 미리보기용 시험 데이터.
  발행·무결성과 무관, 전표 생성 시 복사하지 않는다.
- **요소 그룹**: 요소 공통 선택 필드 `group?: string`(그룹 식별자) — 그룹 편집 UI는 E-18.
- **바인딩 정의부**: 양식 본문에 `bindings?: { key, label? }[]` — **물리명(key)** 은 파일·수식·
  백엔드 연동에, **논리명(label)** 은 화면 표시에 쓴다. key 중복 금지. 정의부는 보조 정보로,
  요소가 미등록 바인딩 키를 쓰는 것도 허용한다(등록 강제 없음 — 기존 문서 호환).
- **동봉 프리셋**: 바인딩을 camelCase 물리명 + 한국어 논리명으로 전환하고 bindings 정의부를 채운다.

### 함께 확정한 표시 규칙

- 디자이너 캔버스의 선은 `lineDirection`대로 그린다(사선 포함) — v2 A-1에서 확인된 캔버스 선
  미표시 문제를 이 개정과 함께 해소한다.
- 캔버스의 파선·점선·모서리 반경·글자 스타일은 CSS 근사 표시, 픽셀 일치는 PDF 미리보기 담당(ADR-012).

## ADR-033: 고정 그리드 셀별 테두리 렌더 규칙 (C-11)

- 날짜: 2026-08-20
- 상태: 확정

### 결정

- 고정 그리드 **셀의 `borderColor`·`borderWidth`·`borderStyle`을 실제 렌더에 반영**한다
  (0.1.0부터 스키마에 있었으나 렌더는 요소 값만 쓰던 것을 C-11에서 이행 — 포맷 변경 없음).
- 적용 범위: 셀 값은 **그 셀(병합 범위)의 둘레 변**에 적용된다. 셀에 없는 값은 요소 값
  (그것도 없으면 기본 0.2mm 검정 실선)을 쓴다.
- **공유 변 충돌 규칙**: 이웃한 두 셀이 공유하는 변은 **유효 굵기가 더 큰 쪽 설정**을 따른다.
  굵기가 같으면 **아래·오른쪽 셀** 설정을 따른다. `borderWidth: 0`은 "그 변을 그리지 않음"이다.
- 변 단위로 유효 테두리를 계산해 같은 스타일 구간끼리 한 선으로 이어 그린다. 병합 범위 내부
  경계선을 그리지 않는 기존 규칙은 유지.
- 디자이너: 선택 셀 섹션에서 테두리색·굵기·형태를 편집한다. 캔버스는 셀마다 자기 테두리를
  그리는 CSS 근사 표시(픽셀 일치는 PDF 미리보기 담당, ADR-012).

### 근거

- 대표 사용 사례: **마지막 행 왼쪽 칸들의 테두리를 지우고 오른쪽 한 칸만 합계 박스로 남기는**
  전표 하단 표현 — 별도 요소를 겹치지 않고 표 하나로 만들 수 있다.
- 굵은 쪽 우선은 CSS `border-collapse`의 충돌 해소와 같은 방향이라 예측하기 쉽고,
  "테두리를 지운 셀 옆의 살아 있는 셀은 자기 테두리를 온전히 유지한다"는 기대와 일치한다.

### 기각한 대안

- 변(edge) 단위 테두리 필드 추가(`borderTop` 등 4방향): 표현력은 높지만 스키마 개정이 필요하고
  편집 UI가 복잡해진다. 셀 단위 + 충돌 규칙으로 대표 사용 사례가 전부 풀려 보류 (필요해지면 0.3.0 후보).
- 먼저 선언된 셀 우선: cells 배열 순서에 의존해 편집 순서에 따라 결과가 달라진다 — 기각.

## ADR-034: 요소와 바인딩을 분리한다 — 왼쪽은 목록, 오른쪽은 편집 (F 묶음)

- 날짜: 2026-08-20
- 상태: 확정

### 결정

- **바인딩은 요소와 별개의 1급 항목**이다. 어떤 요소가 쓰든 안 쓰든 목록에 동등하게 존재하며,
  요소는 "어떤 값을 쓸지" 고르기만 한다.
- **왼쪽 사이드바는 목록·선택·추가·삭제만** 한다. 값을 고치는 입력은 두지 않는다.
- **오른쪽 패널이 편집을 전담**하고, 선택 대상이 **요소 | 바인딩 | 표 열** 셋으로 확장된다.
  아무것도 고르지 않으면 지금처럼 양식 설정이 뜬다.
- **페이지는 아직 선택 대상에 넣지 않는다.** 지금 파일 포맷의 페이지에는 `elements`밖에 없어
  페이지 설정 화면에 담을 것이 순서 이동 하나뿐이다. 그 하나 때문에 화면을 새로 만들지 않고
  **순서 이동은 툴바**에 둔다(썸네일은 지금처럼 페이지 이동만). 페이지 이름(물리·논리)과 페이지 번호
  표시가 생기는 0.3.0에서 페이지 설정 화면을 만들며 선택 대상에 넣는다 (ADR-035, 사용자 확인 2026-08-21).
- 페이지 추가·삭제처럼 툴바에 이미 있는 조작은 패널에 겹쳐 두지 않고, 요소 수 같은 파생 정보도 두지 않는다.
- 요소 패널의 바인딩은 **등록된 목록에서 고르는 선택 상자**로 한다. 목록이 값의 단일 원천이 되도록
  필드·동적 표를 새로 만들면 그 바인딩을 정의부에 자동 등록하고, 선택 상자에 "새 값 등록"을 둔다.
- 사이드바의 바인딩 추가(+)는 입력을 받지 않고 **기본 이름으로 항목을 즉시 만들고 선택**한다
  (요소를 추가하는 흐름과 같게).
- 표 바인딩은 사이드바에서 **하위 열까지 트리로** 보여 준다. 열을 고르면 오른쪽에 그 열 설정이 뜬다.
- 다중 페이지 대응: **요소 목록은 페이지별로 묶어 전부** 보여 주고(현재 페이지는 펼침),
  **바인딩 패널에는 "쓰는 곳"**(페이지·요소) 목록을 두어 클릭으로 이동한다.

### 근거

- 사이드바 인라인 편집은 취소 수단이 없었다. 고치다 만 값이 바깥 클릭에 그대로 저장되고,
  Esc는 편집칸에 포커스가 없어 듣지 않았다(직접 확인). 편집 위치를 한 곳으로 모으면 이 문제가
  기능 추가 없이 사라진다.
- 요소 패널에 논리명을 끼워 넣는 방식은 바인딩을 요소 안으로 합치는 방향이라, 요소가 없는 바인딩을
  다룰 수 없고 같은 값을 여러 요소가 쓸 때 어디서 고쳐야 할지 모호해진다.
- 선택 대상을 셋으로 넓히면 "왼쪽에서 고르고 오른쪽에서 고친다"는 규칙 하나로 전부 설명된다.

### 함께 정한 화면 규칙

- 속성 패널에서 **펼쳐지는 항목(색 피커·테두리 굵기·형태 등)은 한 번에 하나만** 열린다.
- 패널은 **지금 실제로 적용 중인 값**을 보여 준다. 지정하지 않아 기본값이 쓰이는 항목은 흐린 글씨로
  그 값을 표시하고(예: 글자 크기 10), 상위에서 물려받는 항목은 물려받는 값을 보여 준다.
- 표 너비 편집은 **국소 변경**을 원칙으로 한다 — 열 추가는 마지막 열을 절반씩 나눠 갖고, 삭제는 이웃 열이
  돌려받는다. 손대지 않은 열은 그대로 두어 추가↔삭제가 정확히 원상복구된다.

## ADR-035: 파일 포맷 0.3.0 범위 예고 (G 묶음, 착수 시 확정)

- 날짜: 2026-08-20
- 상태: 예고 (세부는 착수 시 이 ADR을 개정해 확정)

### 담을 것

- **동적 표 렌더러 교체**: 지금 PDF 엔진은 열 단위로 **정렬만** 지원하고 글자 크기·색·배경은 무시한다
  (실제 PDF 렌더로 확인). 열별 스타일·셀 병합·표 중첩이 전부 같은 작업을 요구하므로, 표 렌더러를 우리
  구현으로 갈아 끼우는 것을 이 묶음의 뿌리로 둔다. 착수 시 **페이지 분할·머리행 반복이 유지되는지 먼저 확인**하고
  범위를 정한다. 엔진이 이미 지원하는 머리행·본문 전체 스타일과 열별 정렬은 교체 전에 먼저 열어도 된다.
- **바인딩 값 종류**(글자·수·날짜·참/거짓 등)와 종류에 맞는 함수 유도.
- **글자 조판**: 수직 정렬(상·중·하), 세로쓰기(글자를 한 자씩 쌓는 방식 — 실제 PDF로 동작 확인),
  기울임(자형을 가진 폰트를 등록했을 때만), 줄간격·자간.
- **페이지 번호**: 표시 여부·위치. 총 페이지 수는 렌더 후에 확정되므로 **PDF 후처리로 실제 번호**를 찍고,
  디자이너 캔버스에는 `X / X` 자리표시만 보여 준다(사용자 확인 2026-08-20).
- **페이지 이름**(물리명·논리명): 지금 페이지에는 `elements`뿐이라 이름 칸이 없다. 바인딩과 같은 방식으로
  물리명·논리명을 두면 썸네일·요소 목록에 번호 대신 이름이 보이고, 페이지를 가리켜 다룰 수 있다.
  이때 **페이지를 선택 대상에 넣고 페이지 설정 화면**(이름·번호 표시·순서)을 만든다 (ADR-034).
- 고정 그리드 셀 안 수식·바인딩, 고정 그리드 셀 글자 크기의 표 요소 상속.

### 기각·보류

- 엔진에 기능을 추가하는 방식(업스트림 기여·포크)은 반영 시점이 통제 밖이고 포크는 유지보수를 계속
  떠안는다 — 기각. 표 렌더러를 우리 것으로 두는 편이 이후 병합·중첩까지 한 번에 풀린다.
