# SlipKit 기본설계

최종 갱신: 2026-09-28

## 개요

이 디렉터리는 SlipKit의 화면, 기능, 데이터, 인터페이스와 오류 처리 설계를 관리합니다. 설계서는
소스 코드의 구조를 옮겨 적지 않고 사용자, 호스트 애플리케이션과 각 패키지 사이에서 입력이 어떻게
처리되고 어떤 상태와 출력으로 이어지는지를 설명합니다.

설계 기준은 `main`의 `e4fcd22b8b6c56e566c40140163b51161db8ab82`입니다. 구현이 바뀌면 관련
설계서와 추적표를 같은 변경에서 갱신합니다.

등록한 74개 설계서와 실제 화면 자산을 이 구조로 관리합니다. 화면 설계는 실제 Chromium 화면과 출력
PDF를 근거로 갱신합니다.

## 처음 읽는 순서

1. [용어 해설](GLOSSARY.md)에서 양식·전표, 양식 페이지·출력 페이지, 그리드·격자처럼 혼동하기
   쉬운 개념을 확인합니다.
2. [시스템 개요](00-common/SYS-001-system-overview.md)에서 SlipKit과 호스트 애플리케이션의 역할을
   확인합니다.
3. 만들려는 부분에 따라 화면(`SCR`), 기능(`FNC`), 데이터(`DAT`), 인터페이스(`IF`), 오류(`ERR`)
   설계서를 함께 읽습니다. 한 종류의 문서만으로는 화면과 내부 처리 전체를 구현할 수 없습니다.
4. 문서에 연결된 관련 설계와 근거에서 세부 조건을 확인합니다.

## 작성 순서

1. [설계 대상 등록부](90-management/design-register.md)에서 대상, 근거와 담당 묶음을 확인합니다.
2. 대상 유형의 템플릿을 복사하고 제목, 최종 갱신 날짜, 개요와 변경 이력을 먼저 작성합니다.
3. 실제 구현, `REQUIREMENTS.md`, `SPEC.md`, `DECISIONS.md`와 `ARCHITECTURE.md`를 함께 대조합니다.
4. 관련 화면·기능·데이터·인터페이스·오류 식별자를 서로 연결합니다.
5. [추적표](90-management/traceability.md)를 갱신하고 `pnpm verify:design`을 실행합니다.

## 작성 원칙

- 버튼이나 함수 하나가 아니라 독립적인 목적과 처리 흐름을 가진 단위로 문서를 나눕니다.
- 설계서를 읽는 사람은 소스 코드가 아니라 문서에 적힌 화면, 데이터와 처리 규칙을 기준으로 같은
  프로그램을 구현할 수 있어야 합니다. 코드 이름을 동작 설명 대신 사용하지 않습니다.
- 현재 구현된 동작만 기록하며 계획이나 희망 동작을 현재 설계처럼 쓰지 않습니다.
- 필드와 JSON Schema 전체를 복사하지 않고 설계상 의미, 관계, 조건과 생명주기를 설명합니다.
- 설명문보다 표, Mermaid 흐름도·시퀀스·상태 전이를 우선합니다.
- 화면 설계서는 소스 코드를 다시 읽지 않아도 화면 구조, 표시 조건, 모든 사용자 동작, 상태, 오류와
  전이를 구현할 수 있게 작성합니다. `src`, `kind`, 프로퍼티명과 이벤트명은 인터페이스 설계에서
  정의하고 화면 설명에서는 "편집할 양식", "양식 변경 알림"처럼 사용자가 이해할 수 있는 이름을
  사용합니다.
- 상위 화면 설계서는 영역의 배치와 영역 사이의 변화를 정의합니다. 하위 도구 모음이나 패널을 별도
  설계서로 분리했다면 상위 문서에 그 내부 버튼과 입력 동작을 반복하지 않습니다.
- 하위 화면 설계서는 자신이 맡은 영역을 알아볼 수 있게 확대하거나 잘라 촬영하고, 내부 버튼·입력·
  목록에 새 번호를 붙입니다. 상위 화면 이미지의 영역 번호를 내부 항목 번호로 재사용하지 않습니다.
- 화면 설계에는 해당 화면 또는 상태를 실제로 확인한 이미지를 사용합니다. 다른 화면의 진입 버튼을
  대신 싣지 않습니다.
- 화면 이미지에는 주요 영역 번호를 표시하고 화면 구성 표의 번호와 일치시킵니다. 한 이미지로 서로
  다른 상태를 설명할 수 없으면 상태별 이미지를 추가합니다.
- 화면 항목과 사용자 동작은 한 행에 하나씩 적습니다. 추가와 삭제, 적용과 취소처럼 결과가 다른
  항목을 한 행에 묶지 않습니다. 실행 조건은 결과와 함께 적고 같은 조건을 별도 열에서 반복하지
  않습니다.
- `관련 설정`, `현재 상태에 따라`처럼 구현자가 대상을 추측해야 하는 표현을 쓰지 않고, 실제 항목과
  조건을 이름으로 밝힙니다.
- 기능 설계는 입력과 출력의 이름만 나열하지 않고 처리 순서, 분기 기준, 변경하는 값, 실패했을 때
  유지하는 값과 재시도 지점을 정의합니다.
- 데이터 설계는 필드명뿐 아니라 자료형, 필수 여부, 기본값, 허용 범위, 다른 데이터와의 관계와
  생성·변경·삭제 시점을 정의합니다.
- 인터페이스 설계는 호출 형식, 반환값, 이벤트 발생 시점, 비동기 순서, 여러 번 호출할 때의 동작과
  오류 전달 방식을 정의합니다.
- 오류 설계는 오류 종류를 나열하는 데 그치지 않고 검출 위치, 사용자·호출자에게 전달할 정보,
  실패 시 보존하는 데이터와 복구 절차를 정의합니다.
- 한국어는 자연스러운 합니다체로 작성하고 작업 경위, 방어적 표현과 중복 설명을 남기지 않습니다.
