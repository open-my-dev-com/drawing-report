# SlipKit 기본설계

최종 갱신: 2026-09-28

## 개요

이 디렉터리는 SlipKit의 화면, 기능, 데이터, 인터페이스와 오류 처리 설계를 관리합니다. 설계서는
소스 코드의 구조를 옮겨 적지 않고 사용자, 호스트 애플리케이션과 각 패키지 사이에서 입력이 어떻게
처리되고 어떤 상태와 출력으로 이어지는지를 설명합니다.

설계 기준은 `main`의 `e4fcd22b8b6c56e566c40140163b51161db8ab82`입니다. 구현이 바뀌면 관련
설계서와 추적표를 같은 변경에서 갱신합니다.

## 문서 구조

| 경로 | 내용 |

| `00-common/` | 시스템 구성, 실행 환경과 공통 제약 |
| `10-screen/` | 디자이너, 작성 폼, 뷰어와 독립 화면 |
| `20-function/` | 입력·처리·분기·출력을 가진 기능 |
| `30-data/` | `.slip`과 런타임 데이터의 구조·관계·생명주기 |

| `50-error/` | 오류 분류, 전달, 표시와 복구 |

식별자는 한 번 부여하면 다른 대상에 다시 사용하지 않습니다. 파일명은
`SCR-001-designer-main.md`처럼 식별자와 짧은 영문 이름으로 구성합니다.

## 작성 순서

1. [설계 대상 등록부](90-management/design-register.md)에서 대상, 근거와 담당 묶음을 확인합니다.
2. 대상 유형의 템플릿을 복사하고 제목, 최종 갱신 날짜, 개요와 변경 이력을 먼저 작성합니다.
3. 실제 구현, `REQUIREMENTS.md`, `SPEC.md`, `DECISIONS.md`와 `ARCHITECTURE.md`를 함께 대조합니다.
4. 관련 화면·기능·데이터·인터페이스·오류 식별자를 서로 연결합니다.
5. [추적표](90-management/traceability.md)를 갱신하고 `pnpm verify:design`을 실행합니다.

## 작성 원칙

- 버튼이나 함수 하나가 아니라 독립적인 목적과 처리 흐름을 가진 단위로 문서를 나눕니다.
- 현재 구현된 동작만 기록하며 계획이나 희망 동작을 현재 설계처럼 쓰지 않습니다.
- 필드와 JSON Schema 전체를 복사하지 않고 설계상 의미, 관계, 조건과 생명주기를 설명합니다.
- 설명문보다 표, Mermaid 흐름도·시퀀스·상태 전이를 우선합니다.
- 화면 설계에는 실제 화면을 확인한 이미지를 사용하고 영역 번호와 표의 항목을 일치시킵니다.
- 한국어는 자연스러운 합니다체로 작성하고 작업 경위, 방어적 표현과 중복 설명을 남기지 않습니다.
