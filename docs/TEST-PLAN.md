# 테스트 계획

SlipKit의 공개 전 품질 확인 범위와 방법을 정리합니다.

문서 구성은 ISO/IEC/IEEE 29119-3의 테스트 계획 항목(문맥·전략·기준·범위·일정·위험)을 따르고, 보안 항목은 OWASP ASVS 5.0과 치트시트, 접근성 항목은 WCAG 2.2 AA를 기준으로 합니다.

확정된 요구사항은 [요구사항](./REQUIREMENTS.md), 파일 형식은 [파일 형식 명세](./SPEC.md), 설계 배경은 [설계 결정 기록](./DECISIONS.md)을 참고합니다.

최종 갱신: 2026-08-31

## 1. 테스트 대상과 문맥

SlipKit은 호스트 애플리케이션에 끼워 쓰는 임베드형 패키지입니다. 서버도 계정도 없고, 실행되는 곳은 사용자의 브라우저(또는 호스트의 Node 프로세스)입니다. 그래서 "동시 접속자"보다 **한 사람의 브라우저에서 큰 문서를 다룰 때 화면이 멈추지 않는지**가 부하 시험의 실제 관심사입니다.

| 대상 | 실행 환경 | 신뢰 경계 |
|---|---|---|
| `@omdc-slipkit/core` | 브라우저·Node (순수 TS) | 외부에서 들어온 `.slip` 파일과 전표 값 |
| `@omdc-slipkit/elements` | 브라우저 (Lit) | 사용자 입력, 이미지 파일, IndexedDB |
| `@omdc-slipkit/react`·`vue` | 브라우저 | 호스트가 넘기는 속성·이벤트 |
| `@omdc-slipkit/mcp` | 로컬 Node (stdio) | 작업 디렉터리, AI가 보내는 도구 인자, 로컬 HTTP 요청 |

## 2. 테스트 수준과 종류

| 수준·종류 | 무엇을 확인하나 | 방법 | 현재 상태 |
|---|---|---|---|
| 단위 | 함수·클래스 단위 동작과 경계값 | Vitest | 662건 통과 |
| 통합 | 패키지 사이 연결(core↔elements↔래퍼) | Vitest + happy-dom | `integration.test.ts` |
| 시스템 | 사용자 흐름 전체(양식 작성 → 전표 발행 → PDF) | 브라우저에서 데모 직접 확인 | 자동화 없음 |
| 회귀 | 이미 고친 문제가 다시 나오지 않는지 | 검증 게이트 | 커밋마다 훅으로 강제 |
| 부하·성능 | 큰 문서에서 응답 시간과 메모리 | 벤치마크 스크립트 | 이 문서 6절 |
| 보안 | 외부 입력·암호화·파일 접근·로컬 서버 | 코드 점검 + 단위 시험 | 이 문서 7절 |
| 사용성·접근성 | 키보드 조작, 화면 낭독기, 좁은 화면 | 수동 점검 + 일부 단위 시험 | 이 문서 8절 |

## 3. 시작·종료 기준

**시작 기준** — 검증 게이트(`pnpm lint && pnpm -r typecheck && pnpm -r build && pnpm -r test`)가 통과한 상태.

**종료 기준**

- 게이트 4단계 전부 통과
- 치명·높음 등급 결함 0건
- 코드 커버리지가 아래 목표 이상
- 8절의 수동 점검 항목을 모두 확인

| 패키지 | 구문 커버리지 목표 | 측정값 (2026-08-31) |
|---|---|---|
| `core` | 90% | 93.2% |
| `elements` | 85% | 90.5% |
| `mcp` | 80% | 85.2% |

측정: `pnpm test:coverage`

## 6. 부하·성능 시험

### 6.1 방법

호스트가 없는 라이브러리라 초당 요청 수(TPS) 같은 서버 지표는 의미가 없습니다. 대신 **입력 크기를 늘리며 처리 시간이 어떻게 늘어나는지**를 봅니다. 브라우저의 주 스레드를 막는 구간이 있으면 화면이 그만큼 멈춥니다.

기준선: 항목 수를 100 → 1,000 → 5,000 → 20,000으로 늘리며 `planSourcePage`, `parseSlipFile`, 수식 평가, 암호화 시간을 측정.

### 6.2 판정 기준

| 작업 | 기준 | 근거 |
|---|---|---|
| 페이지 계획 | 입력이 20배 늘 때 시간은 40배 미만 | 사실상 선형에 가까워야 큰 문서를 다룰 수 있음 |
| 한 번의 주 스레드 점유 | 200ms 이하 | 이 이상이면 조작이 끊기는 느낌이 남 |
| 암호화 키 파생 | 100~300ms | OWASP가 제시하는 KDF 비용 구간 |

### 6.3 측정값 (2026-08-31, 컨테이너 Node 22)

| 작업 | 항목 100 | 1,000 | 5,000 | 20,000 |
|---|---|---|---|---|
| 페이지 계획 (개선 전) | 1.9ms | 13.7ms | 49.0ms | 787.4ms |
| 페이지 계획 (개선 후) | 2.3ms | 1.9ms | 10.5ms | 118.0ms |

개선 전에는 페이지마다 남은 항목 전체를 훑어 입력의 제곱에 가깝게 늘었습니다. 남은 항목이 이미 넘치면 더 세지 않도록 고쳐 20,000건에서 6.7배 빨라졌습니다.

| 그 밖의 작업 | 측정값 |
|---|---|
| `parseSlipFile` (4.4KB) | 0.22ms |
| `parseFormula` 10,000회 | 40ms |
| `evaluateFormula` 1,000회 (항목 1,000건 합계) | 53ms |
| 암호화 (PBKDF2 600,000 + AES-GCM) | 115ms |
| 암호화 (원시 키) | 0.6ms |

### 6.4 남은 과제

- 조각마다 누계 항목 배열을 복사해 페이지 수 × 항목 수만큼 복사가 일어납니다. 공개 형태(`carriedItems: number[]`)를 바꿔야 없앨 수 있어 별도 결정이 필요합니다.
- 큰 이미지를 많이 넣은 양식의 메모리 사용량은 아직 측정하지 않았습니다.

## 7. 보안 시험

### 7.1 위협 모델

| 공격자 | 할 수 있는 것 | 노리는 것 |
|---|---|---|
| 악의적인 `.slip` 파일 제공자 | 사용자가 여는 파일의 내용을 마음대로 만듦 | 코드 실행, 정보 유출, 화면 멈춤 |
| 로컬 컴퓨터의 다른 프로그램 | MCP 링크 서버 포트에 접속 | 작업 디렉터리의 PDF 열람 |
| 사용자가 방문한 웹 페이지 | 브라우저로 로컬 주소에 요청 | 같은 목적 (DNS 리바인딩) |
| 암호화 파일을 훔친 사람 | 봉투 파일 확보 | 암호 추측으로 내용 복호화 |

### 7.2 점검 항목과 결과

| 항목 | 확인 방법 | 결과 (2026-08-31) |
|---|---|---|
| 임의 코드 실행 | `eval`·`new Function`·문자열 동적 import 검색 | 0건 (ADR-010) |
| DOM 주입 | `innerHTML`·`unsafeHTML`·`document.write` 검색 | 0건 (Lit 템플릿만 사용) |
| 프로토타입 오염 | `__proto__`·`constructor[` 검색 | 0건 |
| SVG 속성 주입 | 도형 SVG에 들어가는 값의 검증 여부 | 색은 `#RRGGBB` 정규식으로 제한됨 |
| 입력 크기 제한 | `SLIP_LIMITS`, 수식 길이·중첩 상한 | 페이지·요소·셀·항목·수식 모두 상한 있음 |
| 키 파생 강도 | 봉투의 반복 횟수와 실제 소요 시간 | 600,000회 / 115ms (OWASP 권고 충족) |
| 인증 암호화 | 변조·잘못된 키의 구분 없는 실패 처리 | AES-256-GCM, 실패 메시지 동일 |
| 경로 이탈 | MCP 저장소의 상대 경로 처리 | `resolveInRoot`로 차단. 심볼릭 링크는 미해석 |
| 로컬 서버 노출 | 바인딩 주소, 메서드·확장자 제한, Host 검사 | 127.0.0.1 · GET · `.pdf`만. Host 검사 추가함 |
| 의존성 취약점 | `pnpm audit` | 알려진 취약점 0건 |
| 외부 자원 로딩 | 양식이 참조하는 `http(s)://` 이미지 | 허용됨 — 호스트가 CSP로 통제해야 함 |

### 7.3 보안 시험 케이스

| 케이스 | 기대 결과 |
|---|---|
| 봉투의 암호문 1바이트 변조 | 복호화 실패 (변조와 오답을 구분하지 않음) |
| 봉투의 `iterations`를 상한 밖 값으로 변경 | 키 파생 거부 |
| 봉투의 `v`를 2로 변경 | 지원하지 않는 버전으로 거부 |
| `../` 이 섞인 저장 키 | 작업 디렉터리 밖이라 거부 |
| 링크 서버에 `.slip` 요청 | 404 |
| 링크 서버에 다른 도메인 Host로 요청 | 403 |
| 상한을 넘는 페이지·요소·항목 수 | 스키마 검증에서 거부 |
| 10,000자를 넘는 수식 | 파서가 거부 |

## 8. 사용성·접근성 시험

WCAG 2.2 AA를 기준으로 하되, 자동 검사로 잡히지 않는 항목은 직접 조작해 확인합니다.

| 항목 | 기준 | 확인 방법 |
|---|---|---|
| 키보드만으로 조작 | SC 2.1.1 | 마우스를 쓰지 않고 양식 하나를 끝까지 작성 |
| 모달의 초점 관리 | SC 2.4.3 | 열면 안으로 들어가고, Tab이 밖으로 새지 않고, 닫으면 제자리로 |
| 초점 잠김 없음 | SC 2.1.2 | Escape로 언제나 빠져나올 수 있음 |
| 이름·역할·값 | SC 4.1.2 | `role`·`aria-label`·`aria-modal` 표시 |
| 대비 | SC 1.4.3 | 글자와 배경 대비 4.5:1 이상 |
| 확대 | SC 1.4.4 | 200% 확대에서 조작 가능 |
| 로케일별 길이 | — | 한국어·영어·일본어에서 문구가 잘리지 않음 |
| 좁은 화면 | — | 태블릿 가로 폭에서 패널이 겹치지 않음 |

## 9. 자동화 범위와 한계

| 자동화된 것 | 자동화되지 않은 것 |
|---|---|
| 단위·통합 시험 (Vitest) | 실제 브라우저에서의 화면 확인 |
| 타입 검사·빌드·주석 형식 검사 | PDF 출력물의 시각적 대조 |
| 커버리지 측정 | 화면 낭독기 확인 |
| 의존성 취약점 검사 | 긴 시간 사용 중의 메모리 증가 |

현재 이 검증은 개발자 컴퓨터의 커밋 훅에서만 돌아갑니다. 저장소에 CI 설정(`.github/workflows`)이 없어 PR에서는 아무 검사도 실행되지 않습니다.

## 10. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| PR 자동 검증이 없음 | 게이트를 건너뛴 변경이 병합될 수 있음 | CI 워크플로 추가 |
| 브라우저 실제 확인이 수동 | 회귀를 놓칠 수 있음 | 공개 전 체크리스트로 대신하고, 필요하면 E2E 도입 |
| 화면과 PDF의 글꼴 측정 환경이 다름 | 줄바꿈 위치가 어긋날 수 있음 | 로드맵의 보류 항목으로 관리 |
| 디자이너가 한 파일 9,500줄 | 변경 영향 범위를 가늠하기 어려움 | 소스 코드 검토에서 분리 대상 판단 |

## 11. 실행 방법

```bash
# 검증 게이트 4단계
pnpm lint
pnpm -r typecheck
pnpm -r build
pnpm -r test

# 커버리지
pnpm test:coverage

# 의존성 취약점
pnpm audit

# 데모 실행 (브라우저 확인용)
pnpm demo
```
