# 테스트 계획

SlipKit의 공개 전 품질 확인 범위와 방법을 정리합니다.

문서 구성은 ISO/IEC/IEEE 29119-3의 테스트 계획 항목(문맥·전략·기준·범위·일정·위험)을 참고했고, 보안 점검 항목은 OWASP ASVS 5.0과 치트시트를, 접근성 점검 항목은 WCAG 2.2 AA를 참고했습니다. 각 표준을 전부 준수한다는 뜻은 아니며, 이 프로젝트에 필요한 항목만 골라 썼습니다.

이 문서는 **계획과 판정 기준**만 담습니다. 측정값은 실행할 때마다 달라지므로 여기에 적지 않고, 아래 명령으로 그때그때 확인합니다. 확정된 요구사항은 [요구사항](./REQUIREMENTS.md), 파일 형식은 [파일 형식 명세](./SPEC.md), 설계 배경은 [설계 결정 기록](./DECISIONS.md)을 참고합니다.

최종 갱신: 2026-09-06

## 1. 테스트 대상과 실행 환경

SlipKit은 자체 계정이나 원격 서비스를 제공하지 않습니다. Core와 UI 패키지는 호스트 애플리케이션 안에서 실행되고, `@omdc-slipkit/mcp`는 로컬 Node.js 프로세스로 동작하며 선택적으로 루프백 전용 PDF 링크 서버를 엽니다.

| 대상 | 실행 환경 | 신뢰 경계 |
|---|---|---|
| `@omdc-slipkit/core` | 브라우저와 Node.js (순수 TS) | 외부에서 들어온 `.slip` 파일과 전표 값 |
| `@omdc-slipkit/elements` | 브라우저 (Lit) | 사용자 입력, 이미지 파일, IndexedDB |
| `@omdc-slipkit/react`·`vue` | 브라우저 | 호스트가 넘기는 속성·이벤트 |
| `@omdc-slipkit/mcp` | 로컬 Node.js (stdio) | 작업 디렉터리, AI가 보내는 도구 인자, 루프백 HTTP 요청 |

실행 환경이 둘이므로 성능 시험도 두 갈래로 나눕니다 (6절).

| 사용성·접근성 | 키보드 조작, 화면 낭독기, 최소 지원 화면 | 수동 점검 + 일부 단위 시험 | 8절 |

## 3. 시작·종료 기준

**시작 기준** — 검증 게이트(`pnpm verify`)가 통과한 상태. 배포 패키지를 확인할 때는 Playwright
Chromium도 설치되어 있어야 합니다.

**종료 기준**

- 게이트 4단계 전부 통과
- 공개 전 배포 검증에서는 `pnpm verify:packages` 통과
- 치명·높음 등급 결함 0건
- 코드 커버리지가 아래 목표 이상 (`pnpm test:coverage`로 측정)
- 8절의 수동 점검 항목을 모두 확인

| 패키지 | 구문 커버리지 목표 |
|---|---|
| `core` | 90% |
| `elements` | 85% |
| `mcp` | 80% |

### 5.1 파일 형식과 검증

### 5.5 배포 패키지

`pnpm verify:packages`는 워크스페이스 연결이나 기존 `dist` 산출물에 기대지 않고, 배포될 파일을
실제 소비자 관점에서 확인합니다.

| 항목 | 확인할 것 |
|---|---|
| 새 빌드와 패킹 | 기존 `packages/*/dist`를 제거하고 다시 빌드한 뒤 다섯 패키지의 실제 tarball을 만드는지 |
| 공개 파일과 메타데이터 | tarball에 필요한 파일만 들어가며 `workspace:` 의존성이 없고 `publint`·`attw`를 예외 없이 통과하는지 |
| npm·pnpm 설치 | 서로 분리된 깨끗한 소비자 프로젝트가 tarball만 설치하고, pnpm 소비자는 Corepack의 pnpm 10.33.0을 사용하는지 |
| Node.js 공개 API | ESM·CommonJS·JSON Schema·PDF·MCP CLI가 공개 진입점으로 동작하고 내부 `dist` 경로는 거부되는지 |
| 브라우저 공개 API | Elements·React·Vue 소비자가 빌드되고 Chromium에서 만든 PDF가 `%PDF`로 시작하는지 |
| 실패 진단 | 실패 단계와 명령을 표시하고 요청 시 임시 디렉터리를 보존하는지 |

### 5.6 PR과 배포 워크플로

| 항목 | 확인할 것 |
|---|---|
| 지원 Node.js | `verify`와 `verify:packages`가 Node.js 22.13과 최신 LTS에서 모두 실행되는지 |
| JSON Schema | 재생성 뒤 수정 파일뿐 아니라 미추적 파일도 실패로 잡는지 |
| Windows MCP | 다른 드라이브·UNC·상위 경로 이탈을 거부하고 정상 하위 경로를 읽고 쓰는지 |
| 최소 권한 | CI는 `contents: read`, 실제 배포만 `id-token: write`를 사용하고 checkout 자격 증명을 남기지 않는지 |
| 외부 설정 차단 | `main`, `dry_run=false`, `npm-publish` Environment와 저장소 변수가 모두 맞을 때만 실제 배포하는지 |
| 산출물 무결성 | 준비 작업이 만든 tarball과 SHA-256 목록을 내려받아 검증하고 다시 빌드하거나 pack하지 않는지 |
| 순서와 재개 | `core` → `elements` → `react` → `vue` → `mcp` 순서를 지키고 E404·같은 SRI·다른 SRI·조회 오류를 구분하는지 |
| 결과 보고 | dry-run과 외부 설정 미완료를 실제 배포 성공과 구분해 Job Summary에 남기는지 |

## 6. 부하·성능 시험

### 6.1 두 갈래로 나눠 본다

| 범위 | 관심사 | 지표 |
|---|---|---|
| 브라우저 | 조작이 끊기지 않는지 | 주 스레드 점유 시간, 큰 이미지·문서의 메모리 사용량 |
| Node.js 서버 | 서버에서 여러 전표를 동시에 만들 때 버티는지 | 단일 렌더 시간, 동시 렌더 수, 처리량, 메모리 사용량 |

이번 공개 전 점검에서는 **Node.js 기준선**과 Designer 편집 조작(6.6)을 측정합니다. 브라우저 실측 일부와 서버 동시 처리량은 아직 측정하지 않았습니다 (6.4).

### 6.2 측정 방법

`pnpm bench`(`scripts/benchmark.mjs`)를 실행합니다. 이 명령은 Core 빌드까지 함께 실행하므로 명령 하나로 재현됩니다. 스크립트는 다음을 지킵니다.

- 작업마다 워밍업을 먼저 돌린 뒤 본 측정을 반복하고 **중앙값**을 적습니다. 가비지 수집이나 다른 프로세스 때문에 드물게 튀는 값이 평균을 끌어올리는 것을 피하기 위해서입니다.
- 반복 횟수는 작업마다 스크립트에 적혀 있고 출력에도 함께 나옵니다.
- 입력 데이터는 색인에서 만들어 실행할 때마다 같습니다.
- 실행 환경(Node 버전, CPU 모델, 코어 수, 메모리)을 출력 첫 줄에 함께 찍습니다.
- 한 번의 호출이 측정 오차보다 짧은 작업은 한 측정 안에서 여러 번 돌리고 호출당 시간과 초당 호출 수를 함께 적습니다. 워밍업도 본 측정과 같은 횟수만큼 돌립니다.
- 동기 함수는 측정 반복문에서 그대로 호출하고, 암호화처럼 비동기인 것만 `await`합니다. 동기 함수를 `await`하면 호출마다 Promise를 만들고 마이크로태스크로 넘어가는 비용이 함께 측정되어, 호출이 짧은 작업일수록 실제 함수 시간보다 크게 나옵니다.
- 공유 환경에서는 같은 코드도 실행할 때마다 값이 크게 달라집니다. 서로 다른 실행의 값을 비교하지 말고, 한 번의 실행 안에서 비교합니다.

입력 크기를 100 → 1,000 → 5,000 → 20,000건으로 늘리며 처리 시간이 어떻게 늘어나는지 봅니다. 워밍업 없이 한 번만 재면 첫 측정이 부풀려져 작은 입력이 큰 입력보다 느리게 나오므로, 이 스크립트를 거치지 않은 값은 기록하지 않습니다.

### 6.3 판정 기준

| 작업 | 기준 | 근거 |
|---|---|---|
| 페이지 계획 | 입력이 20배 늘 때 시간은 40배 미만 | 사실상 선형에 가까워야 큰 문서를 다룰 수 있음 |
| 한 번의 주 스레드 점유 | 200ms 이하 | 이 이상이면 조작이 끊기는 느낌이 남 |
| 암호화 키 파생 | 1초 미만 | OWASP Password Storage Cheat Sheet가 제시하는 상한. 반복 횟수는 알고리즘별 권고치(PBKDF2-HMAC-SHA256 600,000회)를 따르고, 소요 시간은 그 결과로 본다 |

주 스레드 점유 기준은 브라우저 기준입니다. `pnpm bench`는 Node.js 값이므로 브라우저 응답성 판단에 그대로 쓸 수 없습니다.

### 6.4 아직 측정하지 않은 것

- 브라우저에서의 실제 주 스레드 점유 시간
- 브라우저·모바일에서의 키 파생 소요 시간
- Node.js 서버의 동시 렌더 수와 처리량
- 큰 이미지를 많이 넣은 양식의 메모리 사용량

### 6.5 알려진 병목

페이지 계획은 조각마다 누계 항목 배열을 복사하지 않고 `carriedCount`만 저장합니다. 60,000개 항목
계획에서 시간과 힙 증가량을 측정하고, `@carried`가 렌더링 시 접두 범위를 같은 결과로 집계하는지
회귀 시험으로 확인합니다.

### 6.6 Designer 편집 조작

`pnpm bench:designer`(`scripts/bench-designer.mjs`)는 Core·Elements를 빌드한 뒤 Node.js와 happy-dom에서
`<slip-designer>`를 붙여 포인터 드래그 한 제스처(120회 pointermove 뒤 pointerup)를 측정합니다.

- 양식: 작은 양식(1페이지·요소 20개)과 대형 양식(10페이지·요소 1,000개·현재 페이지 반복 그리드 샘플 500행)
- 반복: 5회 예열 뒤 30회 측정, median·p95를 적습니다
- 계수: 문서 크기(1만 자 이상) 직렬화 호출 수·문자 수, `structuredClone` 호출 수, `planSourcePage` 계산 수,
  되돌리기 스냅샷 수·바이트와 최대 보존량(50개 기준)

## 11. 실행 방법

```bash
# 검증 게이트 — 순서는 루트 package.json의 verify 스크립트에 있다
pnpm verify

# 패키지 소비자 검증 — 첫 실행 전에 관리형 Chromium을 설치한다
pnpm exec playwright install chromium
pnpm verify:packages

# GitHub Actions 워크플로 정적 검사
actionlint .github/workflows/ci.yml .github/workflows/release.yml

# 커버리지
pnpm test:coverage

# 성능 기준선 (Node.js) — Core 빌드까지 함께 실행한다
pnpm bench

# Designer 편집 조작 계측 — Core·Elements 빌드까지 함께 실행한다
pnpm bench:designer

# 의존성 취약점
pnpm audit

# 데모 실행 (브라우저 확인용)
pnpm demo
```

공개 전 검증은 다음 다섯 단계를 순서대로 통과해야 합니다.

1. 고정 의존성 설치: `corepack pnpm install --frozen-lockfile`
2. 저장소 게이트: `pnpm verify`
3. 실제 배포물 소비자 검증: Chromium 설치 후 `pnpm verify:packages`
4. 보강 검증: `pnpm test:coverage`와 `actionlint`
5. 변경 무결성: JSON Schema 재생성 차이와 `git diff --check`

PDF 링크 서버 시험은 토큰 없는 요청, 잘못된 토큰, 올바른 64자리 hex 토큰, 비로컬 Host와
심볼릭 링크를 통한 작업 루트 이탈을 각각 확인합니다. CLI 프로세스는 토큰을 공유하지 않으므로,
같은 작업 디렉터리의 다른 `slipkit-mcp` 링크 서버가 그 포트를 쓰고 있으면 빈 포트에 별도 서버를
시작하는지 검증합니다. 다른 프로그램이나 다른 작업 디렉터리의 서버가 쓰는 포트는 오류로
거부하는지도 확인합니다.
