# 테스트 계획

SlipKit의 공개 전 품질 확인 범위와 방법을 정리합니다.

문서 구성은 ISO/IEC/IEEE 29119-3의 테스트 계획 항목(문맥·전략·기준·범위·일정·위험)을 참고했고, 보안 점검 항목은 OWASP ASVS 5.0과 치트시트를, 접근성 점검 항목은 WCAG 2.2 AA를 참고했습니다. 각 표준을 전부 준수한다는 뜻은 아니며, 이 프로젝트에 필요한 항목만 골라 썼습니다.

이 문서는 **계획과 판정 기준**만 담습니다. 측정값은 실행할 때마다 달라지므로 여기에 적지 않고, 아래 명령으로 그때그때 확인합니다. 확정된 요구사항은 [요구사항](./REQUIREMENTS.md), 파일 형식은 [파일 형식 명세](./SPEC.md), 설계 배경은 [설계 결정 기록](./DECISIONS.md)을 참고합니다.

최종 갱신: 2026-09-02

## 1. 테스트 대상과 실행 환경

SlipKit은 자체 계정이나 원격 서비스를 제공하지 않습니다. Core와 UI 패키지는 호스트 애플리케이션 안에서 실행되고, `@omdc-slipkit/mcp`는 로컬 Node.js 프로세스로 동작하며 선택적으로 루프백 전용 PDF 링크 서버를 엽니다.

| 대상 | 실행 환경 | 신뢰 경계 |
|---|---|---|
| `@omdc-slipkit/core` | 브라우저와 Node.js (순수 TS) | 외부에서 들어온 `.slip` 파일과 전표 값 |
| `@omdc-slipkit/elements` | 브라우저 (Lit) | 사용자 입력, 이미지 파일, IndexedDB |
| `@omdc-slipkit/react`·`vue` | 브라우저 | 호스트가 넘기는 속성·이벤트 |
| `@omdc-slipkit/mcp` | 로컬 Node.js (stdio) | 작업 디렉터리, AI가 보내는 도구 인자, 루프백 HTTP 요청 |

실행 환경이 둘이므로 성능 시험도 두 갈래로 나눕니다 (6절).

## 2. 테스트 수준과 종류

| 수준·종류 | 무엇을 확인하나 | 방법 | 현재 상태 |
|---|---|---|---|
| 단위 | 함수·클래스 단위 동작과 경계값 | Vitest | 자동화됨 |
| 통합 | 패키지 사이 연결(core↔elements↔래퍼) | Vitest + happy-dom | 자동화됨 |
| 시스템 | 사용자 흐름 전체(양식 작성 → 전표 발행 → PDF) | 브라우저에서 데모 직접 확인 | 수동 |
| 회귀 | 이미 고친 문제가 다시 나오지 않는지 | 검증 게이트 | 자동화됨 |
| 부하·성능 | 큰 문서에서 응답 시간과 메모리 | `pnpm bench` (Node.js) + 브라우저 수동 확인 | 6절 |
| 보안 | 외부 입력·암호화·파일 접근·로컬 서버 | 코드 점검 + 단위 시험 | 7절 |
| 사용성·접근성 | 키보드 조작, 화면 낭독기, 최소 지원 화면 | 수동 점검 + 일부 단위 시험 | 8절 |

## 3. 시작·종료 기준

**시작 기준** — 검증 게이트(`pnpm verify`)가 통과한 상태.

**종료 기준**

- 게이트 4단계 전부 통과
- 치명·높음 등급 결함 0건
- 코드 커버리지가 아래 목표 이상 (`pnpm test:coverage`로 측정)
- 8절의 수동 점검 항목을 모두 확인

| 패키지 | 구문 커버리지 목표 |
|---|---|
| `core` | 90% |
| `elements` | 85% |
| `mcp` | 80% |

## 5. 기능 시험 범위

### 5.1 파일 형식과 검증

| 항목 | 확인할 것 |
|---|---|
| 스키마 검증 | 필수 항목 누락과 형식 위반을 거부하고, 스키마에 없는 속성이 정의에 따라 제거되거나 엄격 객체에서 거부되는지 |
| 의미 검증 | 행 구간 규칙, 파라미터 참조, 페이지 방식 조합 |
| 손상 입력 | 잘린 JSON, 다른 형식의 JSON, 매우 깊게 중첩된 값 |
| 외부 생성 파일 | 다른 도구가 만든 `.slip`, 상한을 넘는 값 |
| 암호화 봉투 | 봉투 감지, 버전·KDF 검증, 변조 감지 |

### 5.2 수식

| 항목 | 확인할 것 |

| 파서 | 길이·중첩 상한, 잘못된 토큰, 예약 참조 5종 |
| 평가기 | 타입 엄격성, 0 나누기, 빈 값, 매우 큰 수·소수 |
| 집계 | `@item`·`@group`·`@page`·`@all`·`@carried`의 범위 |

### 5.3 페이지 계획과 렌더링

| 항목 | 확인할 것 |
|---|---|
| 행 구간 배치 | 7종 역할의 순서와 페이지 경계 |
| 페이지 방식 | 자동 확장·고정 페이지, 항목 0건 |

## 6. 부하·성능 시험

### 6.1 두 갈래로 나눠 본다

| 범위 | 관심사 | 지표 |
|---|---|---|
| 브라우저 | 조작이 끊기지 않는지 | 주 스레드 점유 시간, 큰 이미지·문서의 메모리 사용량 |
| Node.js 서버 | 서버에서 여러 전표를 동시에 만들 때 버티는지 | 단일 렌더 시간, 동시 렌더 수, 처리량, 메모리 사용량 |

이번 공개 전 점검에서는 **Node.js 기준선만** 측정합니다. 브라우저 실측과 서버 동시 처리량은 아직 측정하지 않았습니다 (6.4).

### 6.2 측정 방법

`pnpm bench`(`scripts/benchmark.mjs`)를 실행합니다. 이 명령은 Core 빌드까지 함께 실행하므로 명령 하나로 재현됩니다. 스크립트는 다음을 지킵니다.

- 작업마다 워밍업을 먼저 돌린 뒤 본 측정을 반복하고 **중앙값**을 적습니다. 가비지 수집이나 다른 프로세스 때문에 드물게 튀는 값이 평균을 끌어올리는 것을 피하기 위해서입니다.
- 반복 횟수는 작업마다 스크립트에 적혀 있고 출력에도 함께 나옵니다.
- 입력 데이터는 색인에서 만들어 실행할 때마다 같습니다.
- 실행 환경(Node 버전, CPU 모델, 코어 수, 메모리)을 출력 첫 줄에 함께 찍습니다.
- 한 번의 호출이 측정 오차보다 짧은 작업은 한 측정 안에서 여러 번 돌리고 호출당 시간과 초당 호출 수를 함께 적습니다. 워밍업도 본 측정과 같은 횟수만큼 돌립니다.
- 동기 함수는 측정 반복문에서 그대로 호출하고, 암호화처럼 비동기인 것만 `await`합니다. 동기 함수를 `await`하면 호출마다 Promise를 만들고 마이크로태스크로 넘어가는 비용이 함께 측정되어, 호출이 짧은 작업일수록 실제 함수 시간보다 크게 나옵니다.
- 공유 환경에서는 같은 코드도 실행할 때마다 값이 크게 달라집니다. 서로 다른 실행의 값을 비교하지 말고, 한 번의 실행 안에서 비교합니다.

입력 크기를 100 → 1,000 → 5,000 → 20,000건으로 늘리며 처리 시간이 어떻게 늘어나는지 봅니다. 워밍업 없이 한 번만 재면 첫 측정이 부풀려져 작은 입력이 큰 입력보다 느리게 나오므로, 이 스크립트를 거치지 않은 값은 기록하지 않습니다.

### 6.3 판정 기준

| 작업 | 기준 | 근거 |
|---|---|---|
| 페이지 계획 | 입력이 20배 늘 때 시간은 40배 미만 | 사실상 선형에 가까워야 큰 문서를 다룰 수 있음 |
| 한 번의 주 스레드 점유 | 200ms 이하 | 이 이상이면 조작이 끊기는 느낌이 남 |
| 암호화 키 파생 | 1초 미만 | OWASP Password Storage Cheat Sheet가 제시하는 상한. 반복 횟수는 알고리즘별 권고치(PBKDF2-HMAC-SHA256 600,000회)를 따르고, 소요 시간은 그 결과로 본다 |

주 스레드 점유 기준은 브라우저 기준입니다. `pnpm bench`는 Node.js 값이므로 브라우저 응답성 판단에 그대로 쓸 수 없습니다.

### 6.4 아직 측정하지 않은 것

- 브라우저에서의 실제 주 스레드 점유 시간
- 브라우저·모바일에서의 키 파생 소요 시간
- Node.js 서버의 동시 렌더 수와 처리량
- 큰 이미지를 많이 넣은 양식의 메모리 사용량

### 6.5 알려진 병목

조각마다 누계 항목 배열을 복사해 페이지 수 × 항목 수만큼 복사가 일어납니다. 공개 형태(`carriedItems: number[]`)를 바꿔야 없앨 수 있어 별도 결정이 필요합니다.

## 7. 보안 시험

### 7.1 위협 모델

| 공격자 | 할 수 있는 것 | 노리는 것 |
|---|---|---|
| 악의적인 `.slip` 파일 제공자 | 사용자가 여는 파일의 내용을 마음대로 만듦 | 코드 실행, 정보 유출, 화면 멈춤 |
| 로컬 컴퓨터의 다른 프로그램 | MCP 링크 서버 포트에 접속 | 작업 디렉터리의 PDF 열람 |
| 사용자가 방문한 웹 페이지 | 브라우저로 로컬 주소에 요청 | 같은 목적 (DNS 리바인딩) |
| 암호화 파일을 훔친 사람 | 봉투 파일 확보 | 암호 추측으로 내용 복호화 |

### 7.2 점검 항목

| 항목 | 확인 방법 |
|---|---|
| 임의 코드 실행 | `eval`·`new Function`·문자열 동적 import 검색 |
| DOM 주입 | `innerHTML`·`unsafeHTML`·`document.write` 검색 |
| 프로토타입 오염 | `__proto__`·`constructor[` 검색 |
| SVG 속성 주입 | 도형 SVG에 들어가는 값이 스키마에서 제한되는지 |
| 입력 크기 제한 | `SLIP_LIMITS`, 수식 길이·중첩 상한 |
| 키 파생 강도 | 봉투에 기록되는 반복 횟수와 실제 소요 시간 |
| 인증 암호화 | 변조와 잘못된 키를 구분하지 않고 실패하는지 |
| 경로 이탈 | MCP 저장소의 상대 경로 처리 |
| 로컬 서버 노출 | 바인딩 주소, 메서드·확장자 제한, Host 검사 |
| 의존성 취약점 | `pnpm audit` |
| 외부 자원 로딩 | 양식이 참조하는 `http(s)://` 이미지의 처리 |

### 7.3 보안 시험 케이스

| 케이스 | 기대 결과 |
|---|---|
| 봉투의 암호문 1바이트 변조 | 복호화 실패 (변조와 오답을 구분하지 않음) |
| 봉투의 `iterations`를 상한 밖 값으로 변경 | 키 파생 거부 |
| 봉투의 `v`를 2로 변경 | 지원하지 않는 버전으로 거부 |
| 새로 만든 봉투의 반복 횟수 | 권고치와 일치 |
| `../` 이 섞인 저장 키 | 작업 디렉터리 밖이라 거부 |
| 링크 서버에 `.slip` 요청 | 404 |
| 링크 서버에 다른 도메인 Host로 요청 | 403 |
| 링크 서버에 `LOCALHOST`·`[::1]` Host | 200 (대소문자와 IPv6 표기 허용) |
| 링크 서버에 `localhost.attacker.example` Host | 403 |
| 링크 서버에 Host 없는 요청 | 거부 |
| 상한을 넘는 페이지·요소·항목 수 | 스키마 검증에서 거부 |
| 10,000자를 넘는 수식 | 파서가 거부 |

## 8. 사용성·접근성 시험

WCAG 2.2 AA의 관련 성공 기준을 참고하되, 자동 검사로 잡히지 않는 항목은 직접 조작해 확인합니다.

| 항목 | 참고 기준 | 확인 방법 |
|---|---|---|
| 키보드만으로 조작 | SC 2.1.1 | 마우스를 쓰지 않고 양식 하나를 끝까지 작성 |
| 모달의 초점 관리 | SC 2.4.3 | 열면 안으로 들어가고, Tab·Shift+Tab이 밖으로 새지 않고, 닫으면 열기 전 요소로 복귀 |
| 초점 잠김 없음 | SC 2.1.2 | Escape로 언제나 빠져나올 수 있음 |
| 이름·역할·값 | SC 4.1.2 | `role`·`aria-label`·`aria-modal` 표시 |
| 대비 | SC 1.4.3 | 글자와 배경 대비 4.5:1 이상 |
| 확대 | SC 1.4.4 | 200% 확대에서 조작 가능 |
| 로케일별 길이 | — | 한국어·영어·일본어에서 문구가 잘리지 않음 |
| 최소 지원 화면 | — | 1440×810에서 툴바·양쪽 패널·캔버스가 겹치지 않고 수식 모달이 2열로 표시됨 |

## 9. 자동화 범위와 한계

| 자동화된 것 | 자동화되지 않은 것 |
|---|---|
| 단위·통합 시험 (Vitest) | 실제 브라우저에서의 화면 확인 |
| 타입 검사·빌드·주석 형식 검사 | PDF 출력물의 시각적 대조 |
| 커버리지 측정 | 화면 낭독기 확인 |
| 성능 기준선 측정 (`pnpm bench`) | 브라우저 성능과 서버 동시 처리량 |
| 의존성 취약점 검사 | 긴 시간 사용 중의 메모리 증가 |

검증 게이트는 개발자 컴퓨터의 커밋 훅에서 실행됩니다. 훅은 `--no-verify`로 건너뛸 수 있고 새로 받은 작업 환경에서는 설정이 빠져 있을 수도 있으므로, 모든 커밋에서 반드시 실행된다고 볼 수는 없습니다. 저장소에 CI 설정(`.github/workflows`)이 없어 PR에서 독립적으로 검증하는 단계도 아직 없습니다.

## 10. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| PR 자동 검증이 없음 | 게이트를 건너뛴 변경이 병합될 수 있음 | CI 워크플로 추가 |
| 브라우저 실제 확인이 수동 | 회귀를 놓칠 수 있음 | 공개 전 체크리스트로 대신하고, 필요하면 E2E 도입 |
| 브라우저·서버 성능을 측정하지 않음 | 실사용 환경의 응답성과 처리량을 알 수 없음 | 공개 전 브라우저 실측 추가, 서버 사용 사례가 확인되면 동시 처리량 측정 |
| 화면과 PDF의 글꼴 측정 환경이 다름 | 줄바꿈 위치가 어긋날 수 있음 | 로드맵의 보류 항목으로 관리 |
| 디자이너가 한 파일 9천 줄대 | 변경 영향 범위를 가늠하기 어려움 | 소스 코드 검토에서 분리 대상 판단 |

## 11. 실행 방법

```bash
# 검증 게이트 — 순서는 루트 package.json의 verify 스크립트에 있다
pnpm verify

# 커버리지
pnpm test:coverage

# 성능 기준선 (Node.js) — Core 빌드까지 함께 실행한다
pnpm bench

# 의존성 취약점
pnpm audit

# 데모 실행 (브라우저 확인용)
pnpm demo
```
