# 브랜치 · 커밋 · PR 규칙

> 브랜치 전략은 이 파일을 기준으로 한다 (ADR-023/024).

## 작업 시작 절차

1. `docs/ROADMAP.md`에서 현재 상태와 다음 작업을 확인한다.
2. `git fetch origin main` 후 **병합 완료된 최신 `origin/main`에서** 아래 형식의 브랜치를
   새로 만들어 작업한다.
3. 작업·푸시·PR은 규칙 형식 브랜치에서 진행한다.
4. 미병합 브랜치 위에 브랜치·PR을 쌓지 않는다(stack 금지). 자기 PR이 열려 있으면
   병합될 때까지 다음 작업 PR을 만들지 않는다.

## 브랜치 형식: `<type>/<scope>-<topic>`

| 요소 | 값 |
|---|---|
| `type` | `feat`(기능) / `fix`(버그 수정) / `docs`(문서) / `proto`(프로토타입·실험) / `chore`(설정·빌드·잡무) |
| `scope` | 패키지명(`core`, `elements`, `react`, `vue`) 또는 `repo`(리포 전반) |
| `topic` | 작업 내용을 나타내는 짧은 kebab-case |

예: `feat/core-pdf-renderer`, `docs/repo-claude-guide`, `proto/core-formula-parser`

- **형식은 훅이 집행한다** (ADR-058): PreToolUse 훅(`bash-guard.mjs`)이 커밋·푸시 시 현재
  브랜치가 위 형식인지 검사해 어긋나면 차단한다. 규칙에 맞지 않는 브랜치를 써야 할 때
  (환경이 브랜치 이름을 강제하는 경우 등)는 **사용자 확인을 받아**
  `.claude/hooks/branch-guard.json`의 `allowBranches`에 패턴(`*` 와일드카드)을 추가해 허용한다.
  임의로 추가하지 않는다.
- **금지 이름은 허용 목록으로도 열 수 없다** (ADR-058): 자동화 도구 이름을 딴 브랜치
  (`claude*`·`codex*` 등, `branch-guard.json`의 `denyBranches`)는 어떤 경우에도 쓰지 않는다.
  거부 목록이 허용 목록보다 우선한다 — 규칙 형식의 새 브랜치를 만들어 작업을 옮긴다.
- **한 브랜치 = 한 주제.** 서로 다른 주제를 한 브랜치에 섞지 않는다.
- 병합된 브랜치는 재사용하지 않는다(같은 주제의 후속 작업도 새 브랜치).
- `proto/*` 브랜치는 병합하지 않고 결론(문서/ADR)만 남기고 폐기해도 된다.
- 오래 유지되는 브랜치는 주기적으로 `main`을 병합(또는 rebase)해 충돌을 작게 유지한다.

## main 보호 · 병합 방식

- `main` 직접 커밋·푸시 금지. 변경은 PR로만, **스쿼시 머지 전제**.
  (`.claude/settings.json`의 deny 규칙 + PreToolUse 훅(`bash-guard.mjs`)이 main 푸시·커밋을
  차단하고, 커밋 시 검증 게이트를 실행한다.)
- 스쿼시 머지 전제이므로 **브랜치당 커밋 최소화** — 검증까지 마친 뒤 가급적 1커밋으로 푸시한다.

## PR 올리기 전 자가점검 (필수)

PR을 만들거나 갱신하기 전에 아래를 **하나씩 확인하고, 어긴 것이 있으면 고친 뒤에 올린다.**
어겼는데 고칠 수 없는 항목(예: 환경이 브랜치 이름을 강제)은 **PR 본문과 사용자에게 그대로 알린다** —
말없이 넘어가지 않는다.

| # | 확인할 것 | 근거 |
|---|---|---|
| 1 | 브랜치 이름이 `<type>/<scope>-<topic>` 형식인가 | 이 파일 |
| 2 | 병합된 브랜치를 재사용하지 않았는가 | 이 파일 |
| 3 | 한 브랜치에 한 주제만 담았는가 | 이 파일 |
| 4 | 열려 있는 내 PR 위에 쌓지 않았는가 | 이 파일 (ADR-024) |
| 5 | 새로 생긴 쟁점을 `docs/OPEN-QUESTIONS.md`에 다음 Q 번호로 적고 확인받았는가 | CLAUDE.md · `docs.md` |
| 6 | 새 결정을 DECISIONS.md에 ADR로 적고 REQUIREMENTS.md를 맞췄는가 | `docs.md` |
| 7 | 포맷을 바꿨다면 SPEC·`CURRENT_SCHEMA_VERSION`·마이그레이션 **+ 그 테스트**·JSON Schema를 함께 했는가 | `core.md` |
| 8 | 고친 문서의 "최종 갱신" 날짜를 올렸는가 | `docs.md` |
| 9 | 용어를 바꿨다면 `terms.md`의 대상 목록을 전부 훑었는가 (오류 메시지·`strings.ts` 포함) | `terms.md` |
| 10 | 선언 주석이 TSDoc인가, 공개 함수에 `@param`·`@returns`가 있는가 | `comments.md` |
| 11 | `ROADMAP.md`의 현재 상태·다음 작업을 갱신했는가 | CLAUDE.md |
| 12 | 검증 게이트 4단계를 통과했는가 | CLAUDE.md |
| 13 | PR을 새로 만들거나 본문을 크게 다시 쓴다면 모델 상태 확인을 요청했는가 | 아래 「커밋 · PR」 |

## 커밋 · PR

- 커밋은 [Conventional Commits](https://www.conventionalcommits.org/):
  `<type>(<scope>): <제목>` — type은 `feat/fix/docs/refactor/test/chore/eval(평가)`,
  제목은 한국어. 예: `feat(core): .slip 파일 Zod 스키마 정의`
- **PR 제목·커밋 제목은 업무 문서처럼 담백하게 쓴다.**
  작업 항목 이름을 적듯 명사형으로 끝내고, 구어체 서술이나 감상은 넣지 않는다.
  - 좋음: `feat(elements): 이미지 업로드 기능 개발`, `feat(core): .slip 파일 Zod 스키마 정의`
  - 나쁨: `feat(elements): 그림을 올려서 넣을 수 있게`
  - **스쿼시 머지라 main에 남는 커밋 제목은 PR 제목**이다 — 브랜치 커밋 제목은 대체된다.
  - 사용자 관점으로 쓰라는 「언어」 규칙(CLAUDE.md)은 **본문에 적용**한다. 제목까지 풀어 쓰지 않는다.
- PR 본문은 코드·제품 기준의 변경 맥락을 쓴다: 어떤 문제가 있었고, 무엇을 바꿨고,
  결과가 어떻게 달라졌는지.
- 특정 GitHub 이슈 대응이면 이슈 번호와 이슈에서 다룬 문제를 적어도 된다.
- PR 본문에는 근거 ADR 번호와 검증 결과(테스트 수·통과 여부)를 기재한다.
- PR 본문의 코드 스팬(백틱) 안에는 HTML 엔티티를 쓰지 않는다. GitHub이 코드 스팬 안에서는
  엔티티를 해석하지 않아 그대로 노출된다. `&`·`<`·`>`는 있는 그대로 쓴다.
  - 좋음: `` `pnpm lint && pnpm -r typecheck` ``
  - 나쁨: `` `pnpm lint &amp;&amp; pnpm -r typecheck` ``
- **PR 본문에는 꺾쇠(`<` `>`)로 감싼 자리표시자를 쓰지 않는다.** 코드 스팬 안이라도 태그로 보고
  지워져 `type/scope-topic`이 `/-`처럼 남는다. 꺾쇠 없이 `type/scope-topic`으로 쓴다.
  이 규칙은 PR 본문에만 해당한다 — 리포 안 마크다운 파일에서는 그대로 써도 된다.
- PR을 새로 만들거나 본문을 크게 다시 쓸 때는 본문 작성 직전에 사용자에게 모델 상태 확인을 요청한다.
  기존 본문에 검증 결과, 수치, 파일 요약을 보완하는 정도는 직접 처리한다.
- PR 본문·커밋 메시지·로드맵에는 대화 경위, 요청 출처, 피드백 출처를 쓰지 않는다.
  변경 자체의 원인과 결과만 남긴다.
  - 좋음: `이미지 요소가 빈 자리만 생성되던 문제를 고쳐 파일 선택과 미리보기를 추가했다.`
  - 좋음: `Fixes #123: 저장 취소 시 작성 중 전표가 남는 문제를 정리했다.`
  - 나쁨: `사용자 요청으로 이미지 업로드 기능을 추가했다.`
  - 나쁨: `화면 점검 피드백을 반영했다.`
- 소스코드나 문서를 수정한 PR은 변경 내용(무엇이 달라지나) 아래에
  **"수정한 코드 & 문서 요약"** 섹션을 넣는다. 리뷰 전에 어느 파일을 어떻게 고쳤는지
  한눈에 볼 수 있도록 표로 쓰되, 한 파일당 한 줄로 짧게 요약한다:

  | 패스 | 내용 |
  |---|---|
  | `packages/xx/src/yy.ts` | 무엇을 어떻게 수정했는지 한 줄 요약 |
