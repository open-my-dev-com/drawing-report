# 브랜치·커밋·PR 규칙

> 브랜치 전략은 이 파일을 기준으로 합니다(ADR-023/024).

## 작업 시작 절차

1. `docs/ROADMAP.md`에서 현재 상태와 다음 작업을 확인합니다.
2. `git fetch origin main` 후 **병합 완료된 최신 `origin/main`에서** 아래 형식의 브랜치를
   새로 만들어 작업합니다.
3. 작업, 푸시, PR 작성은 규칙에 맞는 브랜치에서 진행합니다.
4. 병합되지 않은 브랜치에서 다른 브랜치나 PR을 시작하지 않습니다. 자신의 PR이 열려 있으면
   병합될 때까지 다음 작업의 PR을 만들지 않습니다.

## 브랜치 형식: `<type>/<scope>-<topic>`

| 요소 | 값 |
|---|---|
| `type` | `feat`(기능) / `fix`(버그 수정) / `docs`(문서) / `proto`(프로토타입·실험) / `chore`(설정·빌드·유지보수) |
| `scope` | 패키지 이름(`core`, `elements`, `react`, `vue`, `mcp`) 또는 저장소 전체를 뜻하는 `repo` |
| `topic` | 작업 내용을 나타내는 짧은 kebab-case |

예: `feat/core-pdf-renderer`, `docs/repo-claude-guide`, `proto/core-formula-parser`

- **훅이 형식을 검사합니다**(ADR-058). PreToolUse 훅(`bash-guard.mjs`)은 커밋과 푸시 전에 현재
  브랜치가 위 형식인지 확인하고, 형식이 다르면 작업을 중단합니다. 환경에서 브랜치 이름을 강제하는
  등 다른 이름이 꼭 필요하면 **사용자 확인을 받은 뒤** `.claude/hooks/branch-guard.json`의
  `allowBranches`에 패턴(`*` 와일드카드)을 추가합니다. 확인 없이 추가하지 않습니다.
- **금지된 이름은 허용 목록에 추가해도 사용할 수 없습니다**(ADR-058). 자동화 도구 이름을 사용한
  브랜치(`claude*`, `codex*` 등)는 `branch-guard.json`의 `denyBranches`에 따라 항상 거부합니다.
  규칙에 맞는 새 브랜치를 만든 뒤 작업을 옮깁니다.
- **한 브랜치에는 한 주제만 담습니다.** 서로 다른 주제를 섞지 않습니다.
- 병합된 브랜치는 재사용하지 않습니다. 같은 주제의 후속 작업도 새 브랜치에서 진행합니다.
- `proto/*` 브랜치는 병합하지 않고 결론을 문서나 ADR에 기록한 뒤 폐기할 수 있습니다.
- 오래 유지하는 브랜치는 `main`을 주기적으로 병합하거나 rebase하여 충돌 범위를 줄입니다.

## main 보호·병합 방식

- `main`에 직접 커밋하거나 푸시하지 않습니다. 변경은 PR을 통해 **스쿼시 병합**합니다.
  `.claude/settings.json`의 deny 규칙과 PreToolUse 훅(`bash-guard.mjs`)은 `main` 커밋·푸시를
  중단하고 커밋 전에 검증 게이트를 실행합니다.
- 스쿼시 병합을 전제로 **브랜치의 커밋 수를 최소화합니다.** 검증을 마친 뒤 가능하면 한 커밋으로
  푸시합니다.

## PR 올리기 전 자가점검 (필수)

PR을 만들거나 갱신하기 전에 아래 항목을 **하나씩 확인하고, 맞지 않는 항목을 수정한 뒤 푸시합니다.**
환경에서 브랜치 이름을 강제하는 경우처럼 수정할 수 없는 항목은 **PR 본문과 사용자에게 명확히
알립니다.**

| # | 확인할 것 | 근거 |
|---|---|---|
| 1 | 브랜치 이름이 `<type>/<scope>-<topic>` 형식인가 | 이 파일 |
| 2 | 병합된 브랜치를 재사용하지 않았는가 | 이 파일 |
| 3 | 한 브랜치에 한 주제만 담았는가 | 이 파일 |
| 4 | 열려 있는 내 PR 위에 쌓지 않았는가 | 이 파일(ADR-024) |
| 5 | 새로 생긴 쟁점을 `docs/OPEN-QUESTIONS.md`에 다음 Q 번호로 적고 확인받았는가 | CLAUDE.md · `docs.md` |
| 6 | 새 결정을 DECISIONS.md에 ADR로 적고 REQUIREMENTS.md를 맞췄는가 | `docs.md` |
| 7 | 포맷을 바꿨다면 SPEC·`CURRENT_SCHEMA_VERSION`·마이그레이션과 관련 시험·JSON Schema를 함께 갱신했는가 | `core.md` |
| 8 | 고친 문서의 "최종 갱신" 날짜를 올렸는가 | `docs.md` |
| 9 | 용어를 바꿨다면 오류 메시지와 `strings.ts`를 포함해 `terms.md`의 대상 목록을 모두 확인했는가 | `terms.md` |
| 10 | 선언 주석이 TSDoc인가, 공개 함수에 `@param`·`@returns`가 있는가 | `comments.md` |
| 11 | `ROADMAP.md`의 현재 상태·다음 작업을 갱신했는가 | CLAUDE.md |
| 12 | 검증 게이트(`pnpm verify`)를 통과했는가 | CLAUDE.md |
| 13 | PR을 새로 만들거나 본문을 크게 다시 쓴다면 모델 상태 확인을 요청했는가 | 아래 `커밋·PR` 절 |

## 커밋·PR

- 커밋은 [Conventional Commits](https://www.conventionalcommits.org/) 형식을 사용합니다.
  `<type>(<scope>): <제목>`에서 type은 `feat/fix/docs/refactor/test/chore/eval(평가)` 중 하나이며,
  제목은 한국어로 작성합니다. 예: `feat(core): .slip 파일 Zod 스키마 정의`
- **PR 제목과 커밋 제목은 업무 문서처럼 간결하게 작성합니다.** 작업 항목 이름처럼 명사형으로
  끝내고 구어체나 감상은 넣지 않습니다.
  - 좋음: `feat(elements): 이미지 업로드 기능 개발`, `feat(core): .slip 파일 Zod 스키마 정의`
  - 나쁨: `feat(elements): 그림을 올려서 넣을 수 있게`
  - 스쿼시 병합 후 `main`에 남는 커밋 제목은 PR 제목입니다. 브랜치의 커밋 제목은 대체됩니다.
  - `CLAUDE.md`의 사용자 관점 작성 규칙은 본문에 적용합니다. 제목은 작업 내용을 간결하게 적습니다.
- PR 본문에는 문제, 변경 내용, 변경 후 동작을 코드와 제품을 기준으로 설명합니다.
- 특정 GitHub 이슈를 처리하는 PR이면 이슈 번호와 해당 문제를 적을 수 있습니다.
- PR 본문에는 관련 ADR 번호와 검증 결과를 포함합니다.
- PR 본문의 코드 스팬 안에는 HTML 엔티티를 사용하지 않습니다. GitHub은 코드 스팬 안의 엔티티를
  해석하지 않으므로 `&`, `<`, `>`를 그대로 작성합니다.
  - 좋음: `` `pnpm lint && pnpm -r typecheck` ``
  - 나쁨: `` `pnpm lint &amp;&amp; pnpm -r typecheck` ``
- **PR 본문에는 꺾쇠(`<`, `>`)로 감싼 자리 표시자를 사용하지 않습니다.** 코드 스팬 안에서도 태그로
  처리되어 `type/scope-topic`이 `/-`처럼 보일 수 있습니다. 꺾쇠 없이 `type/scope-topic`으로 씁니다.
  저장소의 다른 Markdown 문서에는 이 제한을 적용하지 않습니다.
- PR을 새로 만들거나 본문을 크게 다시 작성할 때는 본문 작성 직전에 사용자에게 모델 상태 확인을
  요청합니다. 기존 본문에 검증 결과, 수치, 파일 요약을 추가하는 정도는 직접 처리합니다.
- PR 본문, 커밋 메시지, 로드맵에는 대화 과정이나 요청·피드백의 출처를 기록하지 않습니다.
  변경의 원인과 결과만 남깁니다.
  - 좋음: `이미지 요소가 빈 자리만 생성되던 문제를 고쳐 파일 선택과 미리보기를 추가했습니다.`
  - 좋음: `Fixes #123: 저장 취소 시 작성 중 전표가 남는 문제를 해결했습니다.`
  - 나쁨: `사용자 요청으로 이미지 업로드 기능을 추가했습니다.`
  - 나쁨: `화면 점검 의견을 반영했습니다.`
- 소스 코드나 문서를 수정한 PR은 변경 내용 아래에 **"수정한 코드 & 문서 요약"** 섹션을 둡니다.
  검토자가 파일별 변경 내용을 빠르게 확인할 수 있도록 한 파일당 한 줄의 표로 정리합니다.

  | 경로 | 내용 |
  |---|---|
  | `packages/xx/src/yy.ts` | 무엇을 어떻게 수정했는지 한 줄 요약 |
