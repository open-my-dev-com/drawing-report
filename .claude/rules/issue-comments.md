# GitHub 이슈 코멘트 규칙

Claude와 Codex가 작성하는 GitHub 이슈 코멘트는 이 규칙을 따른다. 두 AI의 규칙 파일은 같은
내용을 유지하며, 하나를 수정하면 다른 하나도 함께 수정한다.

## 머리말

AI가 새 코멘트를 작성할 때는 본문 가장 위에 다음 머리말을 넣는다.

```md
> **코멘트 번호:** 1
> **작성자:** Codex
> **작성 시간:** 2026-09-02T00:49:49+09:00
> **상태:** [x] 확인 요청중 · [ ] 확인 · [ ] 완료
> **상위 코멘트:** 없음
```

- AI가 작성할 때 `작성자`는 `Codex` 또는 `Claude`만 사용한다.
- `작성 시간`에는 작성 시점의 ISO 8601 시각과 UTC 오프셋을 기록한다. 상태가 바뀌어도
  작성 시간은 수정하지 않는다.
- 상태는 세 항목 중 하나만 선택한다.
- `상위 코멘트`에는 직접 이어받은 코멘트 번호를 적는다. 여러 코멘트를 함께 처리하면
  `2, 3`처럼 모두 적고, 독립된 내용이면 `없음`으로 적는다.
- 프로토콜 번호가 없는 사용자 코멘트에 답할 때는 `상위 코멘트`에 해당 GitHub 코멘트
  링크를 적는다. 프로토콜 번호가 있으면 그 번호를 적는다.
- 작성 도구를 알리는 꼬리말은 붙이지 않는다. 작성자는 머리말로 구분한다.
- 사용자가 같은 머리말 형식으로 담당 AI에게 지시할 수 있다. 이 경우 `작성자`에는 사용자가
  적은 이름을 유지하며, 담당 AI는 아래 확인 절차에 따라 상태만 수정한다.

## 코멘트 번호

- 코멘트 번호는 GitHub의 내부 ID가 아니라 각 이슈에서 사용하는 일련번호다.
- 규칙 적용 후 처음 작성하는 AI 코멘트를 1번으로 하고 이후 번호를 1씩 늘린다.
- 새 코멘트를 작성하기 전에 코멘트 전체를 가져와 가장 큰 번호를 확인한다. 최신 코멘트
  하나만 확인하지 않는다.
- 기존 번호를 바꾸거나 완료된 번호를 재사용하지 않는다.
- 동시에 작성해 번호가 겹치면 나중에 등록된 코멘트의 번호와 이를 참조하는 하위
  코멘트를 수정한다.
- 규칙 적용 전에 작성된 코멘트에는 번호를 소급해 붙이지 않는다.

## 상태

### 확인 요청중

상대 AI의 답변, 작업, 검토 또는 확인을 기다리는 상태다. 새 AI 코멘트는 원칙적으로 이
상태로 작성한다.

### 확인

상대 AI가 내용을 읽고 처리 대상을 확인했지만 답변, 구현 또는 검토가 아직 끝나지 않은
상태다.

### 완료

질문에 답했거나 요청한 결과가 검증되어 더 처리할 내용이 없는 상태다. 구현 완료 보고만
으로는 완료로 바꾸지 않는다.

## 확인 절차

1. 이슈를 열면 코멘트 전체를 코멘트 번호순으로 확인한다.
2. 모든 `확인 요청중` 코멘트를 찾고 오래된 번호부터 처리한다.
3. `확인` 상태인 코멘트도 다시 확인해 진행 중인 답변, 구현 또는 검토가 남았는지
   추적한다.
4. 처리할 코멘트를 읽었으면 답변이나 작업을 시작하기 전에 원래 코멘트의 상태를
   `확인`으로 수정한다. 프로토콜 머리말을 사용해 담당 AI에게 남긴 사용자 코멘트도 같은
   방식으로 처리한다.
5. 질문에 확정 답변을 남기면 질문 코멘트를 `완료`로 바꾸고, 답변은 새 번호의
   `확인 요청중` 코멘트로 작성한다.
6. 구현을 시작하면 지시 코멘트를 `확인`으로 바꾼다. 구현과 자체 검증이 끝나면 해당
   지시를 `완료`로 바꾸고, 완료 보고를 새 `확인 요청중` 코멘트로 작성한다.
7. 리뷰를 시작하면 완료 보고를 `확인`으로 바꾼다. 리뷰를 통과하면 `완료`로 바꾸고,
   수정이 필요하면 새 하위 코멘트로 수정 사항을 전달한다.
8. 상태만 알리기 위한 새 코멘트는 작성하지 않는다. 기존 코멘트의 체크 상태를 수정한다.
9. `확인 요청중` 또는 처리 중인 `확인` 코멘트가 남아 있으면 구현 완료, 리뷰 통과,
   이슈 종료 또는 PR 작성 준비가 끝났다고 판단하지 않는다.

## 기존 코멘트 수정

- 상태가 바뀌면 새 코멘트를 작성하지 않고 기존 코멘트의 체크 항목을 수정한다.
- 코멘트 번호, 작성자와 작성 시간은 최초 작성값을 유지한다. 번호가 겹쳤거나 상위 코멘트를
  잘못 적은 경우에만 해당 항목을 바로잡는다.
- 오탈자나 의미가 바뀌지 않는 문장 수정은 기존 코멘트에서 바로 고친다.
- 상대가 이미 `확인`한 지시의 의미를 바꿔야 하면 기존 본문을 조용히 바꾸지 않는다.
  정정 코멘트를 새 하위 번호로 작성하고, 기존 코멘트에 `N번 코멘트로 대체됨`을
  표시한 뒤 `완료`로 바꾼다.
- 프로토콜 머리말 없이 작성된 일반 사용자 코멘트는 수정하지 않는다.
- 사용자가 프로토콜 머리말을 사용해 담당 AI에게 남긴 코멘트는 번호, 작성자, 작성 시간,
  상위 코멘트와 본문을 유지하고 상태 체크 항목만 `확인`, `완료` 순서로 수정한다.
- 프로토콜 형식의 사용자 코멘트라도 다른 AI나 사람에게 전달한 내용이면 수정하지 않는다.
- 다른 계정이 작성해 수정 권한이 없으면 하위 코멘트에서 상태 변경을 요청한다. 원래
  작성자는 다음 확인 때 상태를 수정한다.

## 답변과 리뷰

- 질문에는 결론, 기대 동작, 예외 처리, 허용 범위와 검증 기준을 한 번에 답한다.
- `알아서 처리`, `적절히 반영`, `필요하면 수정`처럼 판단을 상대에게 넘기는 표현을
  쓰지 않는다.
- 제품 요구사항과 기존 결정으로 답할 수 있는 질문은 PM 역할의 AI가 결론을 내려
  답한다. 공개 API, 파일 형식, 데이터 보존 또는 제품 동작을 새로 정해야 할 때만
  사용자에게 확인한다.
- 같은 단계에서 확인할 수 있는 문제는 한 코멘트에 모아 전달한다. 질의와 수정은
  가능하면 세 차례 안에 끝낸다.
- 한국어는 단어만 바꾸지 말고 문장 전체의 자연스러움, 기능과의 일치, 불필요한 설명,
  방어적 표현과 중복까지 확인한다.
- 문구를 지적할 때는 `어색하다`고만 쓰지 않고 현재 문구와 바꿀 문구를 함께 제시한다.
- PR 본문에 들어갈 변경 내용과 작업 중 대화한 내용을 구분한다. 이슈 코멘트의 대화
  경위를 PR 본문에 옮기지 않는다.

## PR과 다음 이슈로 전환

1. 리뷰를 통과하고 처리 중인 코멘트가 모두 끝나면 저장소의 브랜치·PR 규칙에 맞춰 PR을
   먼저 작성한다.
2. PR을 만든 뒤 이슈에 새 프로토콜 코멘트로 PR 링크를 남기고, 상대 AI에게 현재 이슈
   모니터링을 해제한 다음 해당 PR의 CI·수정 요청·병합 상태를 감시하도록 지시한다.
3. PR을 작성하기 전에 이슈 모니터링 해제를 요청하지 않는다. 전환 요청 코멘트는 상대 AI가
   이슈 모니터 해제와 PR 모니터 시작을 모두 확인한 뒤 `완료`로 바꾼다.
4. PR이 병합되기 전에는 다음 이슈의 구현을 시작하거나 구현 담당자에게 시작을 지시하지 않는다.
5. PR이 병합되고 다음 작업 이슈가 정해져 있으면, 다음 이슈의 전체 코멘트를 확인한 뒤 상대
   AI가 그 이슈의 질문과 구현 완료 보고를 감시하도록 전환한다.
6. 다음 작업이 정해지지 않았으면 임의로 고르지 않고 사용자에게 다음 이슈를 확인한다.

## 규칙 변경

- `.claude/rules/issue-comments.md`와 `.codex/rules/issue-comments.md`는 같은 내용을
  유지한다.
- 규칙을 바꾼 뒤 두 파일을 비교하고 `git diff --check`를 실행한다.
